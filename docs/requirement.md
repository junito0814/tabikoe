## 1. はじめに

### 1.1 本書の目的

本書は、要求定義書で定義された利用者要求・システム要求をもとに、開発に着手できる粒度まで仕様を具体化することを目的とする。実装者が本書を読んで判断に迷わないレベルの入出力ルール、データ構造、画面仕様、外部連携仕様、非機能要件を定義する。

### 1.2 適用範囲

本書は、卒業制作として2026年10月7日に提出するバージョン（以下、本リリース）を対象とする。

### 1.3 用語の定義

用語の定義は要求定義書「用語集」に準拠する。ただし、要求定義書で「お気に入り」としていた機能は、本書では「行きたい」に改称する。本書で新たに使用する用語は以下のとおり。

| 用語 | 定義 |
|---|---|
| 行きたい | ユーザーが訪問候補として保存したスポット。投稿の有無を問わず保存できる |
| マイマップ | 自分の投稿があるスポットと「行きたい」保存したスポットを地図上に表示する画面 |
| IdP | Identity Provider（外部認証事業者）。本書ではGoogleを指す |
| アルバムメンバー | アルバム（旅行）に招待され、オーナー／編集者／閲覧者いずれかの権限を持つユーザー |
| スポット写真一覧 | 1つのスポットに投稿された全ての公開投稿の写真を、投稿をまたいで横断的にグリッド表示する画面 |
| Route Handlers | Next.jsが提供するサーバー側APIエンドポイントの仕組み（app/api/.../route.ts）。本書では独自バックエンドAPI層としてこれを利用する |
| Service Role Key | Supabaseが発行する管理者権限キー。RLSを回避してDBへ全アクセスできるため、サーバー側（Route Handlers）でのみ保持する |
| アプリ内通知 | メールを介さず、アプリ内の通知一覧（SC-14）でユーザーに伝える通知の仕組み |
| お知らせ | 運営が全ユーザーに向けて配信する通知。個人向けの通知とは区別して扱う |
| 管理者 | users.is_adminフラグを持つユーザー。管理画面（SC-15〜18）にアクセスできる |
| TBD | To Be Determined（未決定）。本書内で仕様が未確定の箇所を示す |
| 機能ID | 機能を一意に識別するための番号。F-XX-NN形式 |
| 画面ID | 画面を一意に識別するための番号。SC-NN形式 |
| RLS | Row Level Security。Supabaseにおける行単位のアクセス制御機構 |

### 1.4 本書の構成

2章：システム構成／3章：機能要件／4章：画面要件／5章：データ要件／6章：外部インターフェース要件／7章：非機能要件／8章：受入条件／9章：未決定事項

## 2. システム構成

### 2.1 システム方式

本システムは、PWA（Progressive Web App）として実装する。単一のコードベースでスマートフォン・PCブラウザの両方に対応し、ネイティブアプリの個別開発は行わない。

### 2.2 技術構成

| 分類 | 採用技術 | 備考 |
|---|---|---|
| フロントエンド | React（Next.js、App Router） | PWAとして構築 |
| バックエンド（API層） | Next.js Route Handlers（TypeScript） | フロントエンドと同一プロジェクト・同一言語。全てのDBアクセス・外部APIキーの利用はこの層を経由する |
| 認証 | 外部IdP：Googleのみ | パスワードは一切保持しない。Supabase AuthのOAuth連携機能を利用する |
| 管理者認証 | 一般ユーザーと同じGoogle認証＋users.is_adminフラグ | 新しい認証方式は追加しない |
| データベース／ストレージ | Supabase（PostgreSQL、Storage） | Route Handlers内で公式JSクライアントをService Role Keyで初期化して利用する。RLSは二重の防御線として維持する |
| 画像処理 | sharp（Node.js画像処理ライブラリ） | Route Handlers内で、アップロード時のEXIF位置情報除去・縮小画像生成・向き補正を実行する |
| 動画処理 | ffmpeg（またはffmpegのNode.jsラッパー） | Route Handlers内で、アップロード時の先頭フレーム抽出（サムネイル生成）を実行する |
| レート制限 | Supabaseのテーブル（rate_limits）による実装 | Route Handlers内で、直近の時間枠における操作回数をSupabase上で記録・判定する |
| 地図表示 | Google Maps JavaScript API | 無料枠での運用を想定。手動スポット登録（SC-19）の地図表示にも同一コンポーネントを利用する |
| スポット検索・逆ジオコーディング | Google Places API／Google Maps Geocoding API | いずれもRoute Handlers経由で呼び出す |
| ホスティング | Vercel | Next.jsプロジェクトをそのままデプロイする |

### 2.3 対応環境

| 分類 | 対応範囲 |
|---|---|
| スマートフォンOS | iOS 16以降、Android 12以降 |
| ブラウザ | Chrome・Safari・Edgeの最新版および1つ前のメジャーバージョン |

### 2.4 全体構成

```
[ブラウザ]
  Next.js（React）フロントエンド（一般ユーザー画面／管理画面 共通）
       │  HTTPS / JSON（Vercel上で同一オリジン）
       ▼
[Next.js Route Handlers]  ← 認証検証・権限チェック（is_admin含む）・APIキー保持・レート制限判定
       │
       ├─→ [Supabase]（PostgreSQL / Storage、Service Role Keyで接続。RLSも有効）
       │         ├ rate_limits テーブルでレート制限を判定
       │         ├ notifications テーブルへ通知をINSERT
       │         └ system_announcements テーブルへお知らせをINSERT（管理画面から）
       ├─→ [Google Maps JavaScript API]（フロントから直接、表示専用キーで呼び出し可）
       ├─→ [Google Places API]（Route Handlers経由）
       ├─→ [Google Maps Geocoding API]（Route Handlers経由。逆ジオコーディングのみ）
       └─→ [Google OAuth]（Supabase Auth経由でログイン）
```

管理画面は一般ユーザー向け画面と同じNext.jsプロジェクト内に、/admin配下のルートとして実装する。/admin配下へのアクセスは、Route Handlers（Middleware）でusers.is_adminを検証し、falseの場合は404を返す（管理画面の存在自体を一般ユーザーに露出させない）。

### 3.2 アカウント管理機能（F-AC）

#### 3.2.1 サインアップ・ログイン（F-AC-01）

| 項目 | 内容 |
|---|---|
| 概要 | 外部IdPのアカウントを用いてサインアップ・ログインする |
| 利用可能なIdP | Googleのみ |
| 画面構成（v2.8で変更） | アカウント新規作成画面（SC-20）とログイン画面（SC-01）を別画面とする。SC-20には利用規約・個人情報保護方針への同意欄と「アカウントを作成」ボタンを置く。SC-01は同意欄を持たず「ログイン」ボタンのみとする |
| 処理 | ブラウザ→GoogleのOAuth→Supabase Authへのコールバックを、Route Handlers（/api/auth/callback）で受け取りセッションを確立する |
| 初回ログイン時の初期値 | IdPから取得した表示名・アイコン画像を、ユーザー名・アイコンの初期値として設定する |
| 取得する情報 | IdPのユーザー識別子、表示名、アイコンURL、メールアドレスに限る |
| 同意取得 | アカウント新規作成画面（SC-20）で、個人情報保護方針・利用規約への同意を必須とする。同意しない場合はアカウントを作成しない |
| 未登録ユーザーのログイン（v2.8で追加） | いずれの画面から来た場合も、IdP認証の成否だけではアカウントの有無を判別できないため、コールバックでアカウントの存在を確認する。アカウントが無い状態でログイン画面から認証を通った場合は、同意を得ていないためアカウントを作成せず、セッションを破棄した上でアカウント新規作成画面（SC-20）へ誘導する |
| 既存ユーザーの新規作成操作（v2.8で追加） | 既にアカウントがあるユーザーがSC-20から操作した場合は、新規作成せず通常のログインとして扱う（同意日時は初回サインアップ時の値を保持し、上書きしない） |
| 制限 | 同一IPアドレスからのログイン試行は1分間に10回まで（rate_limitsテーブルで判定） |

### 3.3 投稿機能（F-PO）

#### 3.3.1 投稿作成（F-PO-01）

投稿1件に含まれる項目と入力規則は以下のとおり。

| 項目 | 必須 | 入力方式 | 入力規則・制約 |
|---|---|---|---|
| 旅行タイトル | 必須 | オートコンプリート付きテキスト入力 | 200文字まで。3.3.4に準拠。表示範囲は3.3.4のとおり限定する |
| スポット名 | 必須 | オートコンプリート選択または手動登録 | 200文字まで。3.3.5に準拠 |
| カテゴリ | 必須 | 単一選択 | グルメ／観光スポット／体験・アクティビティ／宿泊施設／イベント会場 |
| 日付 | 任意 | カレンダー選択 | 投稿時点までの過去日（当日含む）のみ。未来日は選択不可。JST固定 |
| 滞在時間 | 必須 | 単一選択 | 30分以内／1時間以内／2時間以内／3時間以内／それ以上 |
| 費用 | 任意 | 数値入力（円、整数） | 1人あたりの金額とする。0〜999,999の範囲。負数・小数は不可。無料の場合は0を入力する |
| 星評価 | 必須 | 星アイコンのタップ | 1〜5の整数のみ。小数は許容しない |
| 写真・動画 | 必須（1点以上） | ファイル選択 | 枚数上限なし。写真は1点あたり最大10MB（JPEG／PNG）、動画は1点あたり最大100MB（MP4形式、1分以内）とする |
| 感想 | 任意 | 複数行テキスト入力 | 4,000文字まで |
| 公開設定 | 必須 | 単一選択 | 公開（デフォルト）／非公開。3.3.6に準拠 |

文字数は書記素クラスタ単位でカウントする（絵文字・結合文字は1文字として扱う）。

投稿作成はログイン必須とする。作成頻度は1ユーザーにつき1時間20件までに制限する（rate_limitsテーブルで判定）。

写真アップロードの処理フロー：ブラウザから写真をRoute Handlers（/api/posts/photos）へ送信 → sharpでEXIF位置情報除去・向き補正・縮小画像生成 → Supabase Storageへ保存 → 保存先URLをDBに記録、の順で行う。

動画アップロードの処理フロー（v2.9）：Vercelのリクエスト本文上限（4.5MB）のため、動画本体はRoute Handlersを経由させない。①ブラウザがRoute Handlers（/api/posts/videos/upload-url）から署名付きアップロードURLを受け取る → ②ブラウザからSupabase Storageへ直接アップロード → ③Route Handlers（/api/posts/videos）がStorage上のファイルを取り出し、ffmpegで検証・位置情報メタデータ除去・先頭フレーム抽出を行い、処理済み動画で上書き・サムネイルを保存 → ④投稿作成時にサムネイルと本体のパスをDBに記録（5.4参照）。

#### 3.3.2 費用の入力仕様

| 項目 | 内容 |
|---|---|
| 入力方式 | 数値入力（円）。単位は「1人あたり」とし、入力欄のラベル・プレースホルダーに明記する |
| 検索・絞り込み時の扱い | フィルターでは、保存された数値に対してレンジ判定を行う（例：〜1,000円、〜3,000円、〜5,000円、5,000円〜） |
| 集計 | アルバム画面（SC-09）では、当該アルバムに含まれる投稿の費用（入力済みのもののみ）の合計を表示する |

#### 3.3.3 投稿編集・削除（F-PO-02、F-PO-03）

| 項目 | 内容 |
|---|---|
| 編集可能項目 | 投稿の全項目（旅行タイトル・スポット名・カテゴリ・日付・滞在時間・費用・星評価・写真・動画・感想・公開設定） |
| 写真・動画の編集 | 投稿編集画面で個別に削除・追加が可能。枚数上限はない |
| 投稿日時 | 編集しても投稿日時（新着順の基準）は更新しない |
| 操作権限 | 投稿者本人のみ。共同アルバム内であっても、他ユーザーの投稿は編集・削除できない（オーナーであっても同様） |
| 削除時の連動 | 紐づくコメント・いいね・写真・動画を同時に削除する |
| 削除時のアルバム | 旅行（アルバム）自体は残存する。紐づく投稿が0件になった場合、アルバム一覧に表示しない |
| 削除時のバッジ | 投稿数・いいね数が獲得条件を下回っても、獲得済みバッジは失われない |

#### 3.3.4 旅行タイトルの仕様

| 項目 | 内容 |
|---|---|
| 内部管理 | 旅行は「旅行ID」で管理する。1つの旅行IDに1つの旅行タイトル（表示名）が紐づく |
| 候補表示 | 投稿作成時、当該ユーザーが過去に作成した旅行タイトルをオートコンプリート候補として表示する |
| 既存旅行への追加 | 候補から選択した場合、既存の旅行IDに投稿を追加する |
| 新規旅行の作成 | 候補にない名称を入力した場合、新しい旅行IDを採番して作成する |
| 一致判定 | 前後の空白を除去（トリム）した上での完全一致とする |
| 一意性の範囲 | 同一ユーザー内でのみ一意。他ユーザーの旅行タイトルとは独立して管理する |
| タイトル変更 | オーナーが旅行タイトルを変更できる。変更すると、その旅行IDに紐づく全投稿の表示名に反映される |
| 表示範囲 | 旅行タイトルは、以下の2箇所以外には表示しない<br>・本人のマイページ投稿一覧（SC-06）<br>・アルバム画面（SC-09）：オーナー・アルバムメンバー（編集者・閲覧者）に対して、アルバムの名称として表示する |

投稿カード一覧（SC-04）、投稿詳細（SC-05）、スポット写真一覧（SC-13）、他ユーザーのプロフィール画面には表示しない。

#### 3.3.5 スポット指定の仕様

**候補選択・手動登録の基本仕様**

| 項目 | 内容 |
|---|---|
| 候補表示 | 自前のオートコンプリートUIで、Google Places APIの検索候補とSupabase上の手動登録スポットを統合して表示する。Places APIの呼び出しはRoute Handlers（/api/spots/search）経由で行う |
| 表示順序 | 投稿数が多い順に表示する |
| 表示件数 | Google由来・手動登録あわせて最大5件 |
| 手動登録 | 候補に該当がない場合、スポット名を手動入力し、地図上でピンを立てて位置（緯度経度）を指定する |
| ピンの初期位置 | 現在地を初期値とし、ユーザーが微調整する |
| 手動登録スポットの共有 | Supabaseに保存し、以降は他ユーザーの検索候補にも表示する |
| 重複登録の防止 | 手動登録時、半径50m以内に既存スポットがある場合は新規登録を許可せず、既存スポットの選択を促す |

**スポット手動登録画面（SC-19）の仕様**

投稿作成画面（SC-03）でスポット候補に該当がなかった場合、「候補が見つかりません。地図でスポットを登録する」という導線からSC-19（モーダル）を開く。

| 項目 | 内容 |
|---|---|
| 起動条件 | 投稿作成画面（SC-03）でスポット名を入力し、Google Places APIおよび手動登録済みスポットの候補に該当がなかった場合 |
| 地図の初期位置 | 現在地を初期表示とする（SC-02の全体マップと同じGoogle Mapsコンポーネントを再利用する） |
| ピンの操作 | 画面中央に固定されたピンに対して、地図側をドラッグ・ピンチ操作し、ピンの指す位置を調整する（「中央固定ピン」方式） |
| 現在地ボタン | 右上のボタンで、いつでも現在地に地図を戻せる |
| 確定 | 「この位置でスポットを登録」を押すと、その時点の地図中心の緯度経度でスポットが登録され、投稿作成画面（SC-03）に戻る。この時点で重複登録防止ルール（半径50m以内チェック）を実行する |
| 画面区分 | 独立した画面IDを持つが、SC-03から開くモーダルとして実装し、単体でのURLアクセスは想定しない |

#### 3.3.6 投稿の公開設定

| 項目 | 内容 |
|---|---|
| 設定単位 | 投稿単位（アカウント単位ではない） |
| デフォルト | 公開 |
| 非公開時の扱い | 地図のピン・検索結果・投稿一覧・スポット写真一覧から除外される。本人のマイページ・アルバム・マイマップでのみ表示される |
| アルバム共有時 | アルバムに招待されたメンバーには、そのアルバムに含まれる投稿の公開・非公開にかかわらず、全ての投稿が表示される |
| いいね・コメント | 非公開投稿には、アルバムのメンバー以外はアクセスできないため、いいね・コメントは付かない。アルバムメンバー間でのいいね・コメントも本リリースでは対象外とする（投稿詳細の閲覧のみ） |
| バッジのカウント | 非公開投稿も投稿数としてカウントする |

#### 3.6.1 マイページ（F-RC-01）

| 順序 | 表示内容 |
|---|---|

#### 3.6.2 アルバム（F-RC-02）

| 項目 | 内容 |
|---|---|
| グルーピング単位 | 旅行ID |
| 表示内容 | 当該旅行に紐づく投稿・写真・動画、および3.6.3で定義するメンバー一覧 |

#### 3.6.3 アルバムの共同編集・招待（F-RC-03）

**権限の種類**

| 権限 | できること |
|---|---|
| オーナー | アルバムの作成者。旅行タイトルの変更、招待リンクの発行・無効化、メンバーの権限変更・削除ができる。自分の投稿の追加・編集・削除ができる（他人の投稿は削除できない） |
| 編集者 | そのアルバムに自分の投稿を追加できる。自分の投稿のみ編集・削除できる |
| 閲覧者 | 投稿・写真・メンバー一覧の閲覧のみ可能 |

**アルバム内での公開設定の扱い**

アルバムのメンバー（オーナー・編集者・閲覧者）は、そのアルバムに含まれる投稿について、投稿者が設定した公開／非公開の別にかかわらず、全ての投稿を閲覧できる。これは、アルバム自体がすでに招待制（信頼できるメンバーのみが参加できる空間）であり、その中でさらに個人ごとの非公開設定を維持する必要性が薄いためである。

「非公開」設定は、あくまでアルバムに属さない第三者（地図・検索・スポット写真一覧を見る一般ユーザー）から隠すためのものであり、アルバムメンバー間の可視性を制限するものではない。同行者にも見せたくない内容がある場合は、投稿自体を控える、または別の旅行（アルバム）として扱うことを想定し、投稿単位でのメンバー限定非公開機能は本リリースでは設けない。

**招待の仕組み**

| 項目 | 内容 |
|---|---|
| 招待方法 | オーナーが招待リンクを発行する。発行時に付与する権限（編集者／閲覧者）を選択する |
| 有効期限 | 招待リンクの有効期限は7日間。オーナーはいつでも手動で無効化できる |
| 招待の受諾 | リンクを開いたユーザーがログインすると、指定された権限でアルバムのメンバーに加わる |
| メンバー管理 | オーナーは、参加中のメンバーの権限変更、およびメンバーの削除（アルバムからの除外）ができる |
| メンバーからの退出 | 編集者・閲覧者は、自分の意思でアルバムから退出できる。退出後もそれまでの自分の投稿はアルバムに残る |
| アルバムの終了 | オーナーによる明示的な「アルバム削除」操作は設けない。紐づく投稿が0件になった時点でアルバム一覧から自動的に表示されなくなる |

**オーナー継承ルール**

オーナーが退会した場合、残っているメンバー（編集者・閲覧者）の中から、以下の優先順位で自動的に新オーナーを選出する。

| 優先順位 | 判定基準 |
|---|---|
| 1 | そのアルバムに投稿している件数が最も多いメンバー |
| 2（①で同数の場合） | そのアルバムに参加した日時（招待を受諾した日時）が最も早いメンバー |
| 3（残っているメンバー全員の投稿数が0件の場合） | 投稿数に関係なく、参加した日時が最も早いメンバーを新オーナーとする（①②と同じ判定基準に統一） |

| 項目 | 内容 |
|---|---|
| 選出のタイミング | 旧オーナーの退会処理（F-AC-05）の一部として、同一トランザクション内で自動的に実行する |
| 選出結果の通知 | 新オーナーに選出されたメンバーに、アプリ内通知で知らせる |
| 権限の引き継ぎ | 新オーナーは、旧オーナーが持っていた権限を全て引き継ぐ。旧オーナー自身の投稿はそのまま残るが、投稿者は退会済みユーザーとして匿名化表示される |
| 旧オーナーの扱い（v2.7で追加） | 新オーナーの選出と同時に、旧オーナーのアルバム内権限を閲覧者に変更する。退会後も旧オーナーの投稿はアルバムに残るため、メンバー自体からは除外しない。降格を行わないとオーナーが2人存在する状態になる |
| メンバーが誰も残っていない場合 | 新オーナーを選出できないため、特別な状態にはせず、既存の「投稿0件で自動消滅」と同様の扱いとする。旧オーナー自身の投稿が残っている場合、その投稿はアルバム（旅行ID）に紐づいたまま残るが、アルバムとしての一覧表示（メンバー一覧・招待機能を伴う体裁）は行わない |

#### 3.6.4 「行きたい」保存（F-RC-05）

| 項目 | 内容 |
|---|---|
| 保存単位 | スポット単位（投稿単位ではない） |
| 保存対象 | 投稿の有無を問わない。Google Places API由来のスポットも保存できる |
| 操作起点 | 投稿カード一覧画面（SC-04）、および投稿詳細画面（SC-05）の両方から保存できる |
| 一覧表示 | 「行きたい」スポット一覧画面（SC-08）で確認できる |

| 地図表示 | 全体マップの「行きたい」タブ、およびマイマップで確認できる |

#### 3.6.5 マイマップ（F-RC-06）

| 項目 | 内容 |
|---|---|
| 概要 | 自分の投稿があるスポットと「行きたい」保存したスポットを、地図上に区別して表示する |
| 表示切り替え | 自分の投稿のみ／「行きたい」スポットのみ／両方（デフォルト）から選択する |

### 3.7 ステータスバッジ機能（F-BG）

| バッジ種別 | 獲得条件 |
|---|---|
| 都道府県バッジ | 該当都道府県で1件以上投稿する |
| 投稿数バッジ | 累計投稿数1件／10件／50件／100件 |
| いいね数バッジ | 累計獲得いいね数1件／10件／50件／100件／200件 |

ユーザーは、獲得済み・未獲得のバッジをステータスバッジ画面（SC-10）で一覧確認できる。バッジを新たに獲得した際は、その場でトースト表示を行う（通知一覧には残さない。3.9参照）。投稿削除により条件を下回っても、獲得済みバッジは失われない。

都道府県の判定は、投稿に紐づくスポットの緯度経度をもとに行う。スポット登録時、Route Handlers（/api/spots/{id}/geocode）がGoogle Maps Geocoding APIをサーバー側で呼び出し、逆ジオコーディングの結果をspots.prefectureに一度だけ保存する。APIキーはサーバー側のみで保持し、フロントエンドには一切露出させない。

### 5.3 主要な設計方針

| 項目 | 方針 |
|---|---|
| ユーザー管理 | Supabase Auth の auth.users と public.users を同一IDで1対1に対応させる |
| DBアクセスの経路 | 全てのDBアクセスはNext.js Route Handlers内で、@supabase/supabase-js（Service Role Key）を用いて行う。フロントエンドからSupabaseクライアントを直接呼び出すことはしない。**例外（v2.9）**: 動画本体のStorageへのアップロードのみ、Route Handlersが発行した署名付きアップロードURL（本人のディレクトリ配下・単一パス・有効期限つき）に対してブラウザから直接行う。DBへの書き込みは引き続きRoute Handlersのみ |
| RLSの位置づけ | Route Handlers経由に一本化した上で、RLSも二重の防御線として有効化する。ただしRLSは行単位の制御に限られるため、下記2項目（列単位のアクセス制御・DB関数の実行権限）を必ず併用する（v2.7で補足） |
| 列単位のアクセス制御（v2.7で追加） | 本人が更新してはならない列は、RLSではなく列単位のGRANTで保護する。usersで本人が更新できるのは display_name・avatar_url のみとし、is_admin・is_deleted・email・idp_provider・idp_subject・consented_at・created_at はService Role Key経由でのみ更新する。RLSは行単位の制御しかできないため、これを行わないと本人がPostgRESTへ直接リクエストして自分のis_adminをtrueにでき、下記「管理者判定」のアクセス制御が回避される |
| DB関数の実行権限（v2.7で追加） | RLSを回避する目的でsecurity definerとしたDB関数は、EXECUTE権限をservice_roleのみに絞る（PUBLIC・anon・authenticatedからはrevokeする）。Supabaseはpublicスキーマの関数をPostgRESTのRPCとして公開し、PostgreSQLは新規関数に既定でPUBLICへEXECUTEを付与するため、絞らないとフロントエンドに配布される公開鍵だけで誰でも任意の引数で実行できてしまう |
| 管理者判定 | users.is_admin をRoute Handlers（Middleware）で参照し、管理画面配下のルートへのアクセス制御に用いる。この判定は、上記「列単位のアクセス制御」によりis_adminが本人から書き換えられないことを前提とする（v2.7で補足） |
| 写真・動画の種別管理（v2.6で追加） | post_photos.media_typeで'photo'／'video'を判定する。写真はsharpで縮小画像を、動画はffmpegで先頭フレームのサムネイルを生成し、いずれも同一のstorage_urlカラム（＋動画本体はvideo_urlカラム）に保存する |
| メディアの帰属（v2.9で追加） | 投稿作成・編集で post_photos に紐づけるパスは、Route Handlersが本人のディレクトリ（`<userId>/`）配下であることを検証する。post-media バケットは非公開で配信は署名付きURLのため、検証しないと他人の非公開投稿のファイルパスを自分の公開投稿に紐づけて取り出せてしまう |
| オーナー継承の実装 | album_members.joined_at と、posts側の投稿数集計（trip_idごとのCOUNT）を用いて、退会処理のRoute Handlers内で新オーナーを判定する。判定と owner 権限の更新は同一トランザクションで行う。権限の移譲は、新オーナーのalbum_members.roleを更新するだけでなく、旧オーナーのroleの降格と trips.user_id の付け替えまでを含む（v2.7で補足。trips.user_idはRLSがオーナー判定に用いる列のため、更新しないと新オーナーが実際には操作できない） |
| 通知の実装 | 各機能（招待、コメント、いいね、通報対応等）のRoute Handlers処理の中で、該当するイベント発生時に notifications テーブルへINSERTする |
| お知らせの実装 | system_announcements テーブルへの1件のINSERTのみで全ユーザーに配信される。通知一覧の取得時に notifications と system_announcements の両方をマージして返す |
| レート制限の実装 | Route Handlers内で、対象操作の実行前に rate_limits テーブルを参照し、直近の時間枠における件数が上限を超えていないか判定する |
| 旅行の識別 | trips テーブルの主キー（旅行ID）で識別する |
| アルバム権限 | album_members テーブルで (trip_id, user_id, role, joined_at) を管理する |
| 費用の保持 | posts.cost は整数型（円）。1人あたりの金額として保持する。未入力の場合はNULL |
| 退会時の扱い | users は is_deleted フラグによる論理削除とし、表示名を匿名化する |

### 5.4 画像・動画の取り扱い

| 項目 | 内容 |
|---|---|
| 保存先 | Supabase Storage |
| 写真の受付形式 | JPEG／PNG のみ。Route Handlers側でファイルの実体を検証する |
| 写真のサイズ上限 | 1点あたり10MB |
| 写真の処理の実装場所 | Route Handlers内でsharpライブラリを使用し、アップロード時に以下を実行する |
| EXIF | 位置情報（GPS情報）を除去した上で保存・配信する |
| 縮小画像 | 長辺1200pxの表示用画像を自動生成し、一覧・詳細画面ではそちらを配信する |
| 向き | 元画像の向き情報（EXIF Orientation）を考慮し、正しい向きで縮小画像を生成する |
| 写真の処理フロー | ①ブラウザ→Route Handlersへアップロード ②sharpでEXIF除去・向き補正・縮小画像生成 ③Supabase Storageへ原本・縮小画像の両方を保存 ④URLをDBに記録 |
| 動画の受付形式 | MP4のみ。Route Handlers側でファイルの実体を検証する |
| 動画のサイズ・長さ上限 | 1点あたり最大100MB、再生時間1分以内 |
| 動画のサムネイル | アップロード時に先頭フレームを抽出し、一覧・詳細画面ではそのサムネイル画像を表示する。タップすると動画本体を再生する（4.5.1参照） |
| 動画の処理 | 写真と異なりsharpでは処理できないため、動画の先頭フレーム抽出にはffmpeg（`ffmpeg-static`の同梱バイナリを子プロセスで実行）をRoute Handlers内で利用する。動画のEXIF相当の位置情報メタデータも、サムネイル生成と同じ処理の中で除去する（`-map_metadata -1`、再エンコードなし） |
| 動画の処理フロー（v2.9） | ①ブラウザ→Route Handlersで署名付きアップロードURLを発行（本人のディレクトリ配下に限定） ②ブラウザ→Supabase Storageへ直接アップロード ③Route HandlersがStorageから取り出し、MP4実体（ftypボックス）・100MB・1分以内を検証、メタデータ除去・サムネイル生成、処理済み動画で上書き ④サムネイル（storage_url）と本体（video_url）のパスをDBに記録。検証に失敗したファイルはStorageから削除する |
| メディアの帰属 | 投稿に紐づけるメディアのパスは、アップロードした本人のディレクトリ（`<userId>/`）配下のものに限定する。他人の非公開ファイルを自分の公開投稿に紐づけ、署名付きURLで取り出す抜け道を塞ぐため |
| 添付点数 | 写真・動画あわせて1投稿あたり上限なし（3.3.1参照） |

## 7. 非機能要件

### 7.1 性能

マップ画面の初期表示、および検索・フィルター適用後の再表示を対象とする。4G相当の通信環境、該当エリアの投稿100件程度の条件下で、操作から描画完了まで3秒以内。

### 7.2 セキュリティ

| 項目 | 要件 |
|---|---|
| パスワード保管 | 該当なし（パスワードを保持しないため） |
| APIキー管理 | Google Places API・Geocoding API・Supabase Service Role Keyは、環境変数としてVercel上で管理し、フロントエンドのビルド成果物に含めない |
| 通信 | HTTPSによる暗号化 |
| アクセス制御 | Route Handlers内での権限チェックに加え、RLSでも二重に制御する。管理画面へのアクセスはis_adminフラグで制御する |
| 非公開投稿の保護 | 非公開設定の投稿は、投稿者本人以外が取得できないようRoute Handlers・RLSの両方で制御する |
| 入力安全性 | 感想・コメント等の自由記述欄は、HTMLタグ・スクリプトとして解釈されないようエスケープ処理を行う |
| 画像・動画安全性 | 5.4に準拠する |

### 7.3 不正利用対策（レート制限）

| 対象操作 | 制限 |
|---|---|
| ログイン試行 | 同一IPから1分間に10回 |
| 投稿作成 | 1ユーザーにつき1時間に20件 |
| コメント投稿 | 1ユーザーにつき1分間に5件 |
| 通報 | 1ユーザーにつき1日に20件 |
| アルバム招待リンクの発行 | 1ユーザーにつき1時間に10件 |

実装方式：Supabaseのrate_limitsテーブルで実装する。Route Handlers内で対象操作の実行前に、直近の時間枠におけるカウントを参照・更新し、上限超過時は429エラーを返す。Vercelのサーバーレス関数はインスタンスがリクエストごとに変わりうるため、メモリ内カウンタは使用しない。アカウントロック方式は採用しない。

### 7.4 プライバシー

位置情報はマップ画面の利用時にOS／ブラウザ標準の許可ダイアログで取得する。拒否時は東京駅周辺を初期表示とする。新規登録時に個人情報保護方針・利用規約への同意を必須とする。

### 7.5 運用・保守

| 項目 | 要件 |
|---|---|
| バックアップ | Supabase標準のバックアップ機能を利用する。RPO 24時間、RTOは管理コンソールからの手動復元を前提とする |
| 操作ログ | 対象操作：ログイン成功／失敗、投稿の作成・編集・削除、コメントの投稿・削除、通報、アカウントの登録・退会、管理者による対応操作。保存期間90日。閲覧権限は管理者のみ |
| 稼働率 | 展示・審査期間中の目標稼働率99%（計画的な停止は対象外） |
| デプロイ | VercelのGitHub連携による自動デプロイを用いる |

### 7.6 保守性

投稿カード・ピン・地図・バッジ表示などを共通部品として実装する。地図表示はSC-02・SC-12・SC-13・SC-19で共通のコンポーネントを使用する。Route Handlersについても、Supabaseアクセス・Google API呼び出し・通知送信・画像/動画処理をそれぞれ共通関数として切り出し、重複実装を避ける。

### 7.7 アクセシビリティ

- 画像・動画サムネイルに代替テキスト（alt属性）を設定する
- 情報を色だけで区別せず、アイコンやテキストを併用する
- フォーム入力・ボタン操作をキーボードのみで行えるようにする

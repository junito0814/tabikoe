## 1. はじめに

### 1.1 本書の目的

本書は、要求定義書で定義された利用者要求・システム要求をもとに、開発に着手できる粒度まで仕様を具体化することを目的とする。実装者が本書を読んで判断に迷わないレベルの入出力ルール、データ構造、画面仕様、外部連携仕様、非機能要件を定義する。

### 1.2 適用範囲

本書は、卒業制作として2026年10月7日に提出するバージョン（以下、本リリース）を対象とする。

### 1.3 用語の定義

用語の定義は要求定義書「用語集」に準拠する。ただし、要求定義書で「お気に入り」としていた機能は、本書では「行きたい」に改称する。本書で新たに使用する用語は以下のとおり。

| 用語 | 定義 |
|---|---|
| 行きたい（行きたいスポット） | 旅行が決まっていない場所を仮置きする保存先。投稿の有無を問わず保存できる。しおりとは別枠で 1 つだけあり、マイページから開く |
| あしあと（旧: あしあと） | 自分の投稿・下書きがあるスポットと、保存済み（行きたい・しおり）のスポットを地図上に表示する画面（SC-12） |
| アルバム名（旧: アルバム名） | 投稿時に「アルバム」欄で選ぶ／付ける旅の名称。画面上の呼び名は「アルバム」で統一する。内部は旅行 ID（trips） |
| 日常（v3.1で追加） | アルバム欄を空にした投稿が入る、1 人 1 つのアルバム。最初の投稿時に自動作成。名前変更・削除・招待・しおりは不可 |
| スポットカード（v3.1で追加） | 検索結果（SC-04）の 1 件分。スポット名・代表写真・★の平均・投稿件数・徒歩 N 分・まだあった・最新の感想 1 行・「＋」 |
| スポット登録（v3.2で追加） | 「タビコエだけの場所」（spots.source = manual）を最初の投稿で作ること。最初の投稿者を spots.created_by に記録し、スポット登録バッジの対象にする |
| アプリ内招待（v3.2で追加） | しおり・アルバムに、リンクではなくアプリの中で相手（ユーザー）を選んで招待すること。相手の通知一覧に届き、そこから参加する |
| 返信（v3.2で追加） | コメントに対するコメント（comments.parent_id を持つ行）。親コメントの下に 1 段だけ字下げして時系列に並べる |
| 移動手段（v3.2で追加、2026-09-25 変更） | 探すモードで近くのスポットの範囲と所要時間を決める切替。徒歩（半径 1km）／自転車（3km）／車（10km）／電車（15km）／バス（5km）。車・電車・バスは Routes API の実測、徒歩（80m/分）・自転車（180m/分）は直線距離からの目安 |
| IdP | Identity Provider（外部認証事業者）。本書ではGoogleを指す |
| アルバムメンバー | アルバム（旅行）に招待され、オーナー／編集者／閲覧者いずれかの権限を持つユーザー |
| 検索トップ（ハブ） | ログイン後の着地点（SC-00）。行き先の入力欄、「近くのスポットを探す」「ここを投稿」の 3 つだけを置く |
| 行き先 | 都道府県・市区町村・駅名・スポット名のいずれか。投稿一覧（SC-04）の検索単位 |
| しおり | アルバム名と期間（任意）を持つスポットの集まり。旅行 ID と 1 対 1 で、同じ旅行のアルバムと対になる（旅行前＝しおり、旅行後＝アルバム）。オーナーが招待したメンバーと一緒に編集できる |
| しおりメンバー | しおりに招待され、オーナー／メンバーいずれかの権限を持つユーザー。アルバムメンバーとは独立して管理する |
| Day | しおりの期間の n 日目（Day 1／Day 2／…）。スポットを日ごとに振り分ける単位。タブの左端は ALL（全スポット）で、日付を決めていないスポットは ALL にだけ出る（「未定」タブは置かない） |
| 追加モード | しおり詳細の「＋ スポットを追加」から投稿一覧を開いた状態。カードの「＋」だけでそのしおり（開いていた Day）へ入る |
| 下書き | 投稿画面で「下書きに保存」した、または途中で閉じた投稿。必須項目が空でも成立し、本人にだけ見える |
| まだあった報告 | 投稿詳細で他の利用者が押す「まだあった／無くなっていた」。スポット単位の鮮度情報で、評価ではない |
| タビコエだけの場所 | Google Places に無く、利用者が地図上の位置で登録したスポット（spots.source = manual）に付くラベル |

## 2. システム構成

### 2.1 システム方式

本システムは、PWA（Progressive Web App）として実装する。単一のコードベースでスマートフォン・PCブラウザの両方に対応し、ネイティブアプリの個別開発は行わない。

### 2.2 技術構成

| 分類 | 採用技術 | 備考 |
|---|---|---|
| フロントエンド | React（Next.js、App Router） | PWAとして構築 |
| バックエンド（API層） | Next.js Route Handlers（TypeScript） | フロントエンドと同一プロジェクト・同一言語。全てのDBアクセス・外部APIキーの利用はこの層を経由する |
| 認証 | 外部IdP：Googleのみ | パスワードは一切保持しない。Supabase AuthのOAuth連携機能を利用する |
| 管理者認証 | 一般ユーザーと同じGoogle認証＋users.is_adminフラグ | 新しい認証方式は追加しない |
| データベース／ストレージ | Supabase（PostgreSQL、Storage） | Route Handlers内で公式JSクライアントをService Role Keyで初期化して利用する。RLSは二重の防御線として維持する |
| 画像処理 | sharp（Node.js画像処理ライブラリ） | Route Handlers内で、アップロード時のEXIF位置情報除去・縮小画像生成・向き補正を実行する |
| 動画処理 | ffmpeg（またはffmpegのNode.jsラッパー） | Route Handlers内で、アップロード時の先頭フレーム抽出（サムネイル生成）を実行する |
| レート制限 | Supabaseのテーブル（rate_limits）による実装 | Route Handlers内で、直近の時間枠における操作回数をSupabase上で記録・判定する |
| 地図表示 | Google Maps JavaScript API | 課金は有効化済み（無料枠内での運用を想定）。SC-02・SC-03 上部・SC-08・SC-12 で同一コンポーネントを利用する。POI ラベル非表示等のスタイルを適用する（6.1） |
| スポット検索・地名検索・ジオコーディング | Google Places API（Autocomplete）／Google Maps Geocoding API | スポット候補、行き先候補（駅・市区町村）、都道府県判定。いずれもRoute Handlers経由で呼び出す |
| 配色・テーマ | CSS 変数（globals.css）＋ prefers-color-scheme | ライト／ダークを OS 設定に追従して切り替える。色をコンポーネントに直書きしない |
| ホスティング | Vercel | Next.jsプロジェクトをそのままデプロイする |

### 2.3 対応環境

| 分類 | 対応範囲 |
|---|---|
| スマートフォンOS | iOS 16以降、Android 12以降 |
| ブラウザ | Chrome・Safari・Edgeの最新版および1つ前のメジャーバージョン |

### 2.4 全体構成

```
[ブラウザ]
  Next.js（React）フロントエンド（一般ユーザー画面／管理画面 共通）
       │  HTTPS / JSON（Vercel上で同一オリジン）
       ▼
[Next.js Route Handlers]  ← 認証検証・権限チェック（is_admin含む）・APIキー保持・レート制限判定
       │
       ├─→ [Supabase]（PostgreSQL / Storage、Service Role Keyで接続。RLSも有効）
       │         ├ rate_limits テーブルでレート制限を判定
       │         ├ notifications テーブルへ通知をINSERT
       │         └ system_announcements テーブルへお知らせをINSERT（管理画面から）
       ├─→ [Google Maps JavaScript API]（フロントから直接、表示専用キーで呼び出し可）
       ├─→ [Google Places API]（Route Handlers経由）
       ├─→ [Google Maps Geocoding API]（Route Handlers経由。逆ジオコーディングと行き先の座標化）
       └─→ [Google OAuth]（Supabase Auth経由でログイン）
```

管理画面は一般ユーザー向け画面と同じNext.jsプロジェクト内に、/admin配下のルートとして実装する。/admin配下へのアクセスは、Route Handlers（Middleware）でusers.is_adminを検証し、falseの場合は404を返す（管理画面の存在自体を一般ユーザーに露出させない）。

| 項目 | 必須 | 入力方式 | 入力規則・制約 |

| スポット名 | 必須 | オートコンプリート選択または手動登録 | 200文字まで。3.3.5に準拠 |

#### 3.3.4 アルバム名の仕様

| 項目 | 内容 |

| しおりとの関係（v3.0で追加） | しおりは旅行 ID と 1 対 1 で紐づく（3.11.1）。しおりから投稿した場合、アルバム名はしおりの旅行が入力済みになる |
| タイトル変更 | オーナーがアルバム名を変更できる。変更すると、その旅行IDに紐づく全投稿の表示名に反映される |
| 表示範囲 | アルバム名は、以下の2箇所以外には表示しない<br>・本人のマイページ投稿一覧（SC-06）<br>・アルバム画面（SC-09）：オーナー・アルバムメンバー（編集者・閲覧者）に対して、アルバムの名称として表示する |

投稿カード一覧（SC-04）、投稿詳細（SC-05）、スポット写真一覧（SC-13）、他ユーザーのプロフィール画面には表示しない。

#### 3.3.5 スポット指定の仕様（v3.0で変更）

投稿の位置は、SC-03 上部の地図で決める。スポット手動登録モーダル（SC-19）は廃止し、その役割を SC-03 の地図が兼ねる。

**地図（中央固定ピン）**

| 項目 | 内容 |
|---|---|
| 方式 | ピンは画面中央に固定し、地図側をドラッグ・ピンチ操作してピンの指す位置（＝投稿の位置）を決める |
| 初期位置 | 起点により異なる（3.3.8）。現在地から開いた場合は現在地。位置情報が拒否された場合は東京駅周辺を中心に開き、「地図を動かして場所を合わせてください」と案内する |
| 現在地ボタン | 右上のボタンで、いつでも現在地に地図を戻せる |
| 案内 | 初回だけ「地図を動かしてピンを合わせる」「現地でなければ『変更』から場所を探せます」の 2 行を表示する |
| 既存スポット選択時 | 既存スポットを選んでいるときはピンをそのスポットの位置に固定し、地図を動かしても位置は変わらない。「変更」→「新しい場所」で中央固定ピンに戻る |
| 現地にいない場合（v3.0で追加） | 「変更」の名前検索で選んだ候補は位置が固定されるが、候補の吹き出しの「この付近の新しい場所」で固定を外し、そこから地図を動かして登録の無い場所を決められる。帰宅後の主な入口は しおりの「投稿する」／下書きの「続きを書く」／スポット名で検索してスポット別一覧の「投稿する」 |
| 自宅の保護（v3.0で追加） | 現在地から開いた SC-03 で、地図を動かさず登録スポットも選ばずに「新しい場所」のまま「投稿する」を押したときは、「この位置に新しいスポットを登録して公開します。自宅など公開したくない場所ではありませんか？」と確認ダイアログを出す（「投稿する」「場所を変える」）。地図を動かした場合・既存スポットを選んだ場合・下書きの保存では出さない |

**スポット名欄**

| 項目 | 内容 |
|---|---|
| 初期値 | ピンの位置から自動で決める。半径50m以内に登録済みスポット（Google Places由来・手動登録の双方）があればそれを選択済みにし、無ければ「この場所（新しい場所）」とする |
| 名前で選ぶ | 「変更」を押すと自前のオートコンプリートUIで、Google Places APIの検索候補とSupabase上の手動登録スポットを統合して表示する（投稿数が多い順、最大5件。Places APIの呼び出しはRoute Handlers（/api/spots/search）経由）。候補を選ぶと地図がそのスポットへ移動し、位置は固定される |
| 新しい場所の登録 | 「この場所（新しい場所）」のまま投稿すると、ピンの緯度経度でスポットを新規登録する（spots.source = manual）。スポット名は任意入力で、未入力なら「名前のない場所」とし、あとから編集できる。投稿一覧・詳細では「タビコエだけの場所」ラベルを付ける（3.5.5） |
| 重複登録の防止 | 半径50m以内に既存スポットがある場合は新規登録せず、既存スポットを選択済みにする（利用者が「新しい場所」を選び直しても、投稿時に再判定して既存スポットへ寄せる） |
| 手動登録スポットの共有 | Supabaseに保存し、以降は他ユーザーの候補・ピンにも表示する |
| 登録のタイミング | スポットの新規登録は「投稿する」の時点で行う。下書き（3.3.7）は緯度経度だけを持ち、スポットは作らない |
| 都道府県 | スポット登録時に Geocoding API で逆ジオコーディングし spots.prefecture に保存する（3.7） |

#### 3.3.7 下書き（F-PO-04、v3.0で新設）

### 3.4 検索・投稿一覧・地図機能（F-MP、v3.0で全面改訂）

主導線は「行き先を入れる（SC-00）→ 投稿一覧を眺める（SC-04）→ 地図で位置を確かめる（SC-02）」。地図は「探す場所」ではなく「位置関係を確かめる場所」と位置づけ、検索・絞り込みは SC-00／SC-04 に集約する。

#### 3.4.1 検索トップ（F-MP-02、v3.0で再定義）

| 項目 | 内容 |
|---|---|
| 位置づけ | ログイン後の着地点（SC-00）。置く要素は次の 3 つだけで、地図・一覧・その他の情報は出さない。並びは「行き先の入力欄」→「近くのスポットを探す」→「ここを投稿」 |
| 行き先の入力欄 | プレースホルダ「どこへ行く？」。都道府県名・市区町村名・駅名・スポット名のいずれでも入力できる |
| 候補表示 | 入力中に候補を最大 8 件表示する。順序は ①都道府県（固定リストの前方一致）②駅・市区町村（Google Places Autocomplete を Route Handlers（/api/geocode/suggest）経由で呼び出し、地域・駅の種別に限定）③登録済みスポット名（Supabase、投稿数順）。候補には種別ラベル（都道府県／駅／スポット）を付ける |
| 決定時 | 候補を選ぶ、または入力を決定すると投稿一覧（SC-04）へ遷移する。候補に無い文字列で決定した場合は Geocoding API で座標化し、周辺検索（3.4.2）として扱う。座標化できなければ「見つかりませんでした」と表示する |
| 近くのスポットを探す | 位置情報の許可を求め、地図（SC-02）を探すモード（3.4.6）で開く。拒否時は「行き先を入力してください」と表示し入力欄にフォーカスする |
| ここを投稿 | 位置情報の許可を求め、現在地にピンが刺さった SC-03 を直接開く（地図画面は挟まない）。この画面の主要ボタン（アクセント色）とする。拒否時は東京駅周辺を中心に SC-03 を開き、地図を動かす案内を出す（3.3.5） |
| 案内文 | ボタンの下に説明の文字（「さがす ・ 近くを見る ・ ここに投稿」など）は置かない（v3.1） |
| 未ログイン時 | サービス説明一文（「まだ知られていない場所の、行った人のリアルな声」）と「はじめる」ボタン（SC-01 へ）だけを表示する（v3.2 で「アカウントを作成」「ログイン」の 2 ボタンを 1 つに） |
| 実装方針 | 都道府県リストはアプリ内に静的に持つ。Places Autocomplete は入力の debounce（300ms）とセッショントークンを用い、呼び出し回数を抑える |

#### 3.4.4 ピン操作と地図からの投稿（F-MP-03、v3.0で変更）

#### 3.6.3 アルバムの共同編集・招待（F-RC-03）

**権限の種類**

| 権限 | できること |
|---|---|
| オーナー | アルバムの作成者。アルバム名の変更、招待リンクの発行・無効化、メンバーの権限変更・削除ができる。自分の投稿の追加・編集・削除ができる（他人の投稿は削除できない） |
| 編集者 | そのアルバムに自分の投稿を追加できる。自分の投稿のみ編集・削除できる |
| 閲覧者 | 投稿・写真・メンバー一覧の閲覧のみ可能 |

**アルバム内での公開設定の扱い**

アルバムのメンバー（オーナー・編集者・閲覧者）は、そのアルバムに含まれる投稿について、投稿者が設定した公開／非公開の別にかかわらず、全ての投稿を閲覧できる。これは、アルバム自体がすでに招待制（信頼できるメンバーのみが参加できる空間）であり、その中でさらに個人ごとの非公開設定を維持する必要性が薄いためである。

「非公開」設定は、あくまでアルバムに属さない第三者（地図・検索・スポット写真一覧を見る一般ユーザー）から隠すためのものであり、アルバムメンバー間の可視性を制限するものではない。同行者にも見せたくない内容がある場合は、投稿自体を控える、または別の旅行（アルバム）として扱うことを想定し、投稿単位でのメンバー限定非公開機能は本リリースでは設けない。

**招待の仕組み**

| 項目 | 内容 |
|---|---|
| 招待方法 | オーナーが**アプリ内招待**または招待リンクで招待する。いずれも付与する権限（編集者／閲覧者）を選択する |
| アプリ内招待（v3.2で追加） | 招待画面で相手を選ぶ。候補は「自分と同じアルバム・しおりに入ったことがあるユーザー」（自分・既存メンバー・ブロック関係を除く）を先に出し、ユーザー名の部分一致検索（2 文字以上、最大 20 件）でも探せる。送ると album_invitations に invitee_user_id 付きの行を作り、相手に「〈名前〉さんがアルバム『〈アルバム名〉』に招待しました」の通知（3.9.1）を送る。同じ相手への未回答の招待が既にあれば送れない |
| アプリ内招待の受諾 | 通知の「参加する」（または通知から開いた招待画面）で参加し、指定された権限でメンバーに加わる。「辞退」もできる（オーナーには通知しない）。有効期限は 7 日で、オーナーは取り消せる |
| 有効期限 | 招待リンクの有効期限は7日間。オーナーはいつでも手動で無効化できる |
| 招待の受諾 | リンクを開いたユーザーがログインすると、指定された権限でアルバムのメンバーに加わる |
| メンバー管理 | オーナーは、参加中のメンバーの権限変更、およびメンバーの削除（アルバムからの除外）ができる |
| メンバーからの退出 | 編集者・閲覧者は、自分の意思でアルバムから退出できる。退出後もそれまでの自分の投稿はアルバムに残る |
| アルバムの終了 | オーナーによる明示的な「アルバム削除」操作は設けない。紐づく投稿が0件になった時点でアルバム一覧から自動的に表示されなくなる |

**オーナー継承ルール**

オーナーが退会した場合、残っているメンバー（編集者・閲覧者）の中から、以下の優先順位で自動的に新オーナーを選出する。

| 優先順位 | 判定基準 |
|---|---|
| 1 | そのアルバムに投稿している件数が最も多いメンバー |
| 2（①で同数の場合） | そのアルバムに参加した日時（招待を受諾した日時）が最も早いメンバー |
| 3（残っているメンバー全員の投稿数が0件の場合） | 投稿数に関係なく、参加した日時が最も早いメンバーを新オーナーとする（①②と同じ判定基準に統一） |

| 項目 | 内容 |
|---|---|
| 選出のタイミング | 旧オーナーの退会処理（F-AC-05）の一部として、同一トランザクション内で自動的に実行する |
| 選出結果の通知 | 新オーナーに選出されたメンバーに、アプリ内通知で知らせる |
| 権限の引き継ぎ | 新オーナーは、旧オーナーが持っていた権限を全て引き継ぐ。旧オーナー自身の投稿はそのまま残るが、投稿者は退会済みユーザーとして匿名化表示される |
| 旧オーナーの扱い（v2.7で追加） | 新オーナーの選出と同時に、旧オーナーのアルバム内権限を閲覧者に変更する。退会後も旧オーナーの投稿はアルバムに残るため、メンバー自体からは除外しない。降格を行わないとオーナーが2人存在する状態になる |
| メンバーが誰も残っていない場合 | 新オーナーを選出できないため、特別な状態にはせず、既存の「投稿0件で自動消滅」と同様の扱いとする。旧オーナー自身の投稿が残っている場合、その投稿はアルバム（旅行ID）に紐づいたまま残るが、アルバムとしての一覧表示（メンバー一覧・招待機能を伴う体裁）は行わない |

#### 3.6.4 「行きたい」保存と保存先の 2 択（F-RC-05、v3.0で変更）

| 項目 | 内容 |
|---|---|
| 「＋」ボタン | 投稿カード（SC-04）・投稿詳細（SC-05）・スポット別一覧の見出し・地図のピンの吹き出しに置く。押すと保存先を選ぶシートが 1 枚開く |

### 3.7 ステータスバッジ機能（F-BG）

| バッジ種別 | 獲得条件 |
|---|---|
| 都道府県バッジ | 該当都道府県で1件以上投稿する |
| 投稿数バッジ | 累計投稿数1件／10件／50件／100件 |
| いいね数バッジ | 累計獲得いいね数1件／10件／50件／100件／200件 |
| スポット登録バッジ（v3.2で追加） | 「タビコエだけの場所」（spots.source = manual）を自分が最初に登録した件数（spots.created_by が自分の行数）1件／3件／5件／10件／20件／30件／50件 |

スポット登録バッジは、Google Places に無い位置で新しくスポットを作って投稿を公開した時点で判定する（下書きでは判定しない。Places 由来のスポットへの初投稿は数えない）。既存のスポットには最も古い公開投稿の投稿者を created_by として一括設定する。

ユーザーは、獲得済み・未獲得のバッジをステータスバッジ画面（SC-10）で一覧確認できる。バッジを新たに獲得した際は、その場でトースト表示を行う（通知一覧には残さない。3.9参照）。投稿削除により条件を下回っても、獲得済みバッジは失われない。

都道府県の判定は、投稿に紐づくスポットの緯度経度をもとに行う。スポット登録時、Route Handlers（/api/spots/{id}/geocode）がGoogle Maps Geocoding APIをサーバー側で呼び出し、逆ジオコーディングの結果をspots.prefectureに一度だけ保存する。APIキーはサーバー側のみで保持し、フロントエンドには一切露出させない。

### 3.11 しおり機能（F-IT、v3.0で新設）

しおりは Google マップの「保存リスト」にあたる旅の計画。アルバム名を付けたスポットの集まりで、旅行 ID を通じてアルバム（旅行後の記録）と対になる。名前はアルバムと共通で 1 つ。

#### 3.11.1 しおりの作成・一覧（F-IT-01）

| 項目 | 内容 |
|---|---|
| 作成の起点 | 保存先シートの「＋ 新しいしおりを作る」（3.6.4）、しおり一覧（SC-22）の「＋ 新規」 |
| 入力 | アルバム名（必須、200文字まで、3.3.4 の一意性に従う）、期間（任意。開始日〜終了日。後から設定・変更できる） |
| 旅行IDとの関係 | しおりは旅行（trips）と 1 対 1。作成時に同名の旅行が自分のものとして既にあればそれに紐づけ、無ければ新しい旅行 ID を作る。1 つの旅行にしおりは 1 つまで |
| 作れる人 | 旅行のオーナーのみ。アルバムの編集者・閲覧者はその旅行のしおりを作れず、しおりのオーナーから招待されて参加する |
| アルバムとの導線 | しおり詳細に「アルバムを見る」（同じ旅行 ID のアルバムに投稿があるとき）、アルバム画面に「しおりを見る」（しおりがあり、自分がそのメンバーのとき） |
| アルバム名の変更（v3.1で変更） | しおり詳細のタイトルをタップして変更する（鉛筆マークを添えてよい。「名前を変更」ボタンは置かない）。しおり・アルバムの両方に反映する（同じ旅行 ID のため）。変更できるのは旅行のオーナーのみ |
| 一覧（SC-22） | メニューバーの「しおり」から開く。先頭に「行きたいスポット」への入口（件数つき）。自分がオーナーまたはメンバーのしおりを、期間が近い順（期間未設定は更新日時順）に並べる。各行はアルバム名・期間（年を含む。未設定なら「期間未設定」）・スポット数・済み件数。写真は置かない。期間を過ぎたしおりは末尾に並べ「済」の印と「アルバムを見る」を出す（薄くはしない）。0 件時は「しおりがありません。投稿一覧の「＋」から作れます」 |
| 削除 | オーナーのみ。しおり詳細の右下（4.5 の「削除は右」）。確認ダイアログに「同じ旅行のアルバム（投稿）は残る」旨を書く。削除してもそのスポットが行きたいや他のしおりに入っていればそちらには残る |
| 上限 | 1 ユーザーのしおり数、1 しおりのスポット数に上限は設けない（実装上の安全弁として各 100 件） |

#### 3.11.2 期間と Day（F-IT-02）

| 項目 | 内容 |
|---|---|
| Day タブ（v3.1で変更） | タブの左端は常に **ALL**（全スポット）。期間を設定すると日数分の Day タブ（Day 1／Day 2／…）がその右に並ぶ。1 日なら ALL と Day 1。期間未設定のしおりは ALL だけが出る。「未定」タブは置かない |
| スポットの所属 | 各スポットは 1 つの Day に属するか、日付なし（itinerary_spots.day_index、NULL＝日付なし。ALL にだけ出る）。ALL では Day の順 → 日付なしの順に並べる |
| 期間の表示・変更（v3.1で変更） | 「2026/9/20（金）〜 2026/9/22（日）」のように年を含めて表示する。「期間を変更」ボタンは置かず、期間の表示をタップするとカレンダー（開始日・終了日）が開く。期間を縮めて日が消える場合、その日のスポットは日付なしにする（消さない）。伸ばした場合は空の Day が増える |
| 進捗 | 各 Day タブに「済み／全体」（例：2/4）を表示する |
| Day の移動 | スポットの「Day n ▾」で他の Day／日付なしを選ぶと、そのスポットが移る（時刻があれば時刻順の位置、無ければ末尾）。画面は今の Day に留まり、「Day 2 に移動しました [Day 2 を見る]」のトーストを出す。Day をまたぐドラッグはしない |

#### 3.11.3 到着予定時刻と並び順（F-IT-03）

| 項目 | 内容 |
|---|---|
| 到着予定時刻 | スポットごとに 1 つ、任意。時・分を選ぶ自前のピッカーで、分は 10 分刻み（00／10／20／30／40／50）。ブラウザ標準の時刻入力は iPhone が刻みを無視するため使わない |
| 並び順 | Day 内で、時刻があるスポットは時刻順に自動で並ぶ。無いスポットは手動順（sort_order。**ドラッグ**で入れ替える。上下ボタンは置かない）でその日の末尾にまとめる |
| 行に出さないもの（v3.1） | 値段（★の横の金額・予算目安）は出さない |
| メモ | スポットごとに全角 500 文字まで |
| 削除 | スポットをしおりから外せる（投稿・行きたいには影響しない） |

#### 3.11.4 スポットの追加と追加モード（F-IT-04）

| 項目 | 内容 |
|---|---|
| 通常の追加 | 投稿カード・投稿詳細・地図の「＋」→ 保存先シートでしおり（と Day）を選ぶ（3.6.4）。行きたいスポット（SC-08）の「＋」からも同様 |
| 追加モード | しおり詳細の「＋ スポットを追加」を押すと、投稿一覧（SC-04）を追加モードで開く。行き先はしおりに入っているスポットの都道府県（複数なら最も多いもの）を自動で入れ、しおりが空なら検索トップ（SC-00）を追加モードで開く。追加先は開いていた Day（ALL タブなら日付なし） |
| 追加モードの表示 | 画面上部に「〈アルバム名〉 Day n に追加中 [完了]」を固定表示する。カードの「＋」を押すだけでそのしおりに入り（保存先シートは出さない）、入っているスポットの「＋」はチェック表示にする。「完了」でしおり詳細に戻る。URL は `?itinerary=<id>&day=<n>` |
| 重複 | 同じスポットは 1 つのしおりに 1 回だけ入る（複数のしおりには入れられる） |

#### 3.11.5 チェック（F-IT-05）

| 項目 | 内容 |
|---|---|
| 手動 | 各スポットのチェックボックス（時刻の下）をタップでチェック／解除する。確認は出さない |
| 表示 | 済みはスポット名に取り消し線＋文字を薄くする。位置は動かさない。地図の番号ピンは灰色にする |
| 自動チェック | しおりのメンバー（オーナーを含む）の誰かが、その旅行（同じ旅行 ID）でそのスポットに投稿したら自動でチェックする。しおりのメンバーでない人（アルバムのメンバーであっても）の投稿では変わらない。下書きでは変わらない |
| 状態の共有 | チェックはしおり単位で 1 つ（itinerary_spots.checked_at）。メンバー全員に同じ状態が見える |
| 投稿との関係 | 手でチェックしても投稿は作らない。投稿を削除してもチェックは外さない |

#### 3.11.6 地図表示としおりからの投稿（F-IT-06）

| 項目 | 内容 |
|---|---|
| 地図で見る（v3.1で変更） | しおり詳細の上 1/3 に地図を出し、下 2/3 にスポット一覧を残す（別画面に飛ばない）。地図には開いている Day のスポットだけに訪問順の番号ピンを出し、全体が収まる範囲にする。ALL では全日を Day の色で色分けする。地図をタップすると全画面（SC-02 のしおり表示。「← しおり」で戻る）。もう一度「地図で見る」を押すと地図を閉じる |
| 投稿一覧 | 各スポットの「投稿一覧」でスポット別の投稿一覧（SC-04）へ |
| 投稿する | 各スポットの「投稿する」で、スポット・アルバム名（しおりの旅行）・訪問日（その Day の日付）が入力済みの SC-03 を開く（3.3.8）。投稿済みのスポットには「投稿済み」を表示する |

#### 3.11.7 共有・招待（F-IT-07）

アルバムの招待（3.6.3）と同じ仕組みを、しおり用に独立して持つ。しおりのメンバーとアルバムのメンバーは別に管理し、招待も別々に行う。

| 項目 | 内容 |
|---|---|
| 権限 | オーナー／メンバーの 2 段階。閲覧専用の権限は設けない |
| オーナー | しおりの作成者（＝旅行のオーナー）。招待リンクの発行・無効化、メンバーの削除、期間の変更、アルバム名の変更、しおりの削除ができる。メンバーができることもすべてできる |
| メンバー | スポットの追加・削除・Day と到着予定時刻の変更・並び替え・メモ・チェックができる。自分の意思で退出できる |
| 招待方法 | オーナーが「招待」から**アプリ内招待**（相手を選んで送る。候補と検索の仕様はアルバム 3.6.3 と同じ。itinerary_invitations に invitee_user_id 付きの行を作り、相手に通知する）または招待リンクを発行する。有効期限はどちらも 7 日間で、オーナーはいつでも無効化（取り消し）できる。発行・送信は 1 ユーザーにつき 1 時間 10 件まで（7.3） |
| 受諾 | リンクを開いたユーザーがログインするか、アプリ内招待の通知の「参加する」を押すとメンバーに加わる（「辞退」も可）。参加時に本人・オーナー・既存メンバーへアプリ内通知（3.9.1） |
| 見える範囲 | しおりはオーナーとメンバーにだけ見える。同じ旅行のアルバムのメンバーであっても、しおりに招待されていなければ見えない（アルバム画面の「しおりを見る」も出さない） |
| オーナーの退会 | 旅行のオーナー継承（3.6.3）と同じ処理でしおりのオーナーも新オーナーへ移す。メンバーが誰もいなければしおりは削除する |
| ブロック | ブロック関係にあるメンバー同士でも、しおり内では互いの操作結果が見える（アルバムと同じ扱い） |

#### 3.11.8 データの整合（F-IT-08）

| 項目 | 内容 |
|---|---|
| スポットの削除・統合 | スポットが管理者により削除された場合、しおりからもそのスポットを外す |
| 投稿の削除 | しおりのチェック・スポットは変えない |
| アルバムとの独立 | しおりを削除しても同じ旅行 ID のアルバム（投稿）は残る。アルバムが投稿 0 件でも、しおりは残る |

### 4.5 共通仕様

#### 4.5.1 写真・動画の表示レイアウト

| 点数 | レイアウト |
|---|---|
| 1点 | 全幅表示 |
| 2点 | 左右2分割 |
| 3点 | 左に1点（大）、右を上下2分割 |
| 4点以上 | 2×2グリッド |

5点目以降は、2×2グリッドの右下枠に「+N」の枚数バッジを重ねて表示する。1点目を代表画像とし、グリッド内では左上（または最も大きい枠）に配置する。

動画の表示（v2.6で追加）：動画はサムネイル画像（先頭フレーム）の中央に、再生アイコンを重ねて表示することで写真と区別する。並び替え・代表画像の判定・枚数バッジの扱いは写真と同一のルールに従う（動画が1点目であれば代表サムネイルとなる）。タップすると、投稿詳細画面内でインライン再生する。

写真・動画をタップしたときのモーダル表示（v3.0で追加）：その写真・動画を起点にフルスクリーンで表示し、左右スワイプまたは←→ボタン（パソコンでは矢印キー）で前後へ移動できる。動画はその中で再生する。投稿一覧の写真切替（3.4.5）からは「この投稿を見る」で投稿詳細へ遷移できる。この閲覧方法は写真・動画が表示されるすべての画面で共通とする。

- 個人が特定できる情報（車のナンバー等）が写っていないか確認してください

#### 4.5.5 配色とダークモード（v3.0で新設）

| 項目 | 内容 |

| 基本方針 | 「旅＝空」のイメージで空の青をメインにする。色の値はワイヤーフレーム「配色」を正とする |

### 5.3 主要な設計方針

| 項目 | 方針 |
|---|---|
| ユーザー管理 | Supabase Auth の auth.users と public.users を同一IDで1対1に対応させる |
| DBアクセスの経路 | 全てのDBアクセスはNext.js Route Handlers内で、@supabase/supabase-js（Service Role Key）を用いて行う。フロントエンドからSupabaseクライアントを直接呼び出すことはしない |
| RLSの位置づけ | Route Handlers経由に一本化した上で、RLSも二重の防御線として有効化する。ただしRLSは行単位の制御に限られるため、下記2項目（列単位のアクセス制御・DB関数の実行権限）を必ず併用する（v2.7で補足） |
| 列単位のアクセス制御（v2.7で追加） | 本人が更新してはならない列は、RLSではなく列単位のGRANTで保護する。usersで本人が更新できるのは display_name・avatar_url のみとし、is_admin・is_deleted・email・idp_provider・idp_subject・consented_at・created_at はService Role Key経由でのみ更新する。RLSは行単位の制御しかできないため、これを行わないと本人がPostgRESTへ直接リクエストして自分のis_adminをtrueにでき、下記「管理者判定」のアクセス制御が回避される |
| DB関数の実行権限（v2.7で追加） | RLSを回避する目的でsecurity definerとしたDB関数は、EXECUTE権限をservice_roleのみに絞る（PUBLIC・anon・authenticatedからはrevokeする）。Supabaseはpublicスキーマの関数をPostgRESTのRPCとして公開し、PostgreSQLは新規関数に既定でPUBLICへEXECUTEを付与するため、絞らないとフロントエンドに配布される公開鍵だけで誰でも任意の引数で実行できてしまう |
| 管理者判定 | users.is_admin をRoute Handlers（Middleware）で参照し、管理画面配下のルートへのアクセス制御に用いる。この判定は、上記「列単位のアクセス制御」によりis_adminが本人から書き換えられないことを前提とする（v2.7で補足） |
| 写真・動画の種別管理（v2.6で追加） | post_photos.media_typeで'photo'／'video'を判定する。写真はsharpで縮小画像を、動画はffmpegで先頭フレームのサムネイルを生成し、いずれも同一のstorage_urlカラム（＋動画本体はvideo_urlカラム）に保存する |
| オーナー継承の実装 | album_members.joined_at と、posts側の投稿数集計（trip_idごとのCOUNT）を用いて、退会処理のRoute Handlers内で新オーナーを判定する。判定と owner 権限の更新は同一トランザクションで行う。権限の移譲は、新オーナーのalbum_members.roleを更新するだけでなく、旧オーナーのroleの降格と trips.user_id の付け替えまでを含む（v2.7で補足。trips.user_idはRLSがオーナー判定に用いる列のため、更新しないと新オーナーが実際には操作できない） |
| 通知の実装 | 各機能（招待、コメント、いいね、通報対応等）のRoute Handlers処理の中で、該当するイベント発生時に notifications テーブルへINSERTする |
| お知らせの実装 | system_announcements テーブルへの1件のINSERTのみで全ユーザーに配信される。通知一覧の取得時に notifications と system_announcements の両方をマージして返す |
| レート制限の実装 | Route Handlers内で、対象操作の実行前に rate_limits テーブルを参照し、直近の時間枠における件数が上限を超えていないか判定する |
| 「日常」アルバム（v3.1で追加） | trips に `is_daily boolean not null default false` を追加し、ユーザーごとに 1 行だけ true（部分ユニーク索引 `(user_id) where is_daily`）。投稿・下書きでアルバムが空なら、その行を（無ければ作ってから）trip_id にする。`is_daily` の行はタイトル変更・削除・招待・しおり作成を API で拒否する。既存の仮タイトル「今日の投稿（M/D）」の旅行は、マイグレーションで各ユーザーの「日常」に統合する |
| 旅行の識別 | trips テーブルの主キー（旅行ID）で識別する |
| アルバム権限 | album_members テーブルで (trip_id, user_id, role, joined_at) を管理する |
| 費用の保持 | posts.cost は整数型（円）。1人あたりの金額として保持する。未入力の場合はNULL |
| 下書きの保持（v3.0で追加） | posts.status が draft の行は、spot_id・category・stay_time・rating・visited_at が NULL でもよい（CHECK 制約は published のときだけ必須項目を検証する）。位置は posts.lat／lng に保持し、公開時にスポットを確定して spot_id を埋める。draft は投稿者本人以外に返さない（RLS・Route Handlers の両方で除外） |
| 投稿の位置（v3.0で追加） | posts.lat／lng は SC-03 の中央固定ピンの座標。公開投稿ではスポットの座標と一致する（既存スポットを選んだ場合はスポットの座標を採用する） |
| しおりと旅行（v3.0で追加） | itineraries.trip_id は UNIQUE。旅行のオーナー（trips.user_id）だけが作成でき、itinerary_members に owner として自動追加する。オーナー継承（3.6.3）の処理で itinerary_members の owner も併せて移す |
| 自動チェックの実装（v3.0で追加） | 投稿の公開処理（Route Handlers）の中で、投稿者がメンバーである同じ trip_id のしおりに同じ spot_id の行があれば checked_at を埋める |
| カテゴリの移行（v3.0で追加） | posts.category の CHECK 制約を 7 値に更新し、既存の「イベント会場」を「エンタメ・イベント」に一括更新するマイグレーションを用意する |
| 「まだあった」の集計（v3.0で追加） | 表示に使うのは spot_id ごとの最新 1 件（reported_at 降順）。投稿一覧の取得時に spots に埋め込んで返す |
| 退会時の扱い | users は is_deleted フラグによる論理削除とし、表示名を匿名化する |
| 滞在時間の移行（v3.2で追加） | posts.duration の CHECK 制約を 7 値（30分以内／1時間以内／2時間以内／3時間以内／半日／1日／宿泊）＋旧値「それ以上」の 8 値に更新する。既存の「それ以上」は書き換えず、新規・編集では 7 値だけを受け付ける。絞り込みで「半日」「1日」「宿泊」を選んだときは「それ以上」も含める |
| スポット登録者（v3.2で追加） | spots.created_by は、そのスポットへの最初の公開投稿を作る Route Handlers で埋める（source = manual のときだけ）。既存行は最も古い公開投稿の投稿者で一括更新する。バッジ判定は投稿の公開処理の中で created_by が自分の行数を数える |
| コメントの返信（v3.2で追加） | comments.parent_id は同じ post_id のコメントを参照する（CHECK で post_id の一致を保証する）。親の削除は deleted_at による論理削除とし、返信が無ければ物理削除する。取得は post_id ごとに parent_id NULL の 20 件＋その返信をまとめて返す |
| アプリ内招待（v3.2で追加） | album_invitations／itinerary_invitations の invitee_user_id が NULL ならリンク招待（token で受諾）、値ありならアプリ内招待（本人だけが受諾・辞退できる）。未回答の同じ相手への招待は部分ユニーク索引 `(trip_id or itinerary_id, invitee_user_id) where status = 'pending'` で 1 件に限る。候補ユーザーは album_members と itinerary_members を自分と同じ trip_id／itinerary_id で結合して求める |

| 項目 | 内容 |
|---|---|
| 保存先 | Supabase Storage |

| 写真の処理フロー | ①ブラウザ→Route Handlersへアップロード ②sharpでEXIF除去・向き補正・縮小画像生成 ③Supabase Storageへ原本・縮小画像の両方を保存 ④URLをDBに記録 |

| 添付点数 | 写真・動画あわせて1投稿あたり上限なし（3.3.1参照） |

## 7. 非機能要件

### 7.1 性能

検索トップから投稿一覧の初回表示、投稿一覧の絞り込み適用後の再表示、および地図の初期表示を対象とする。4G相当の通信環境、該当エリアの投稿100件程度の条件下で、操作から描画完了まで3秒以内。

実装方針（2026-09-22 追記。出典 docs/user-stories/shared-ui/performance.md）: 遅さの主因はブラウザの描画ではなく 1 画面あたり 40 回前後の Supabase 往復だったため、次の順で減らす。(1) 認証確認は `getClaims()` で手元の署名検証にし、Supabase Auth への通信を毎回行わない。リンクの先読みでは関所の users 問い合わせを省き、一覧カードは先読みしない。ページ内の独立したクエリは並列にする。未読件数の再取得は 60 秒に 1 回、直前に見た画面は 30 秒間サーバーへ行かず表示する。(2) `loading.tsx` と Suspense で骨組みを先に出す（保留）。(3) 1 画面 1 クエリ化と署名 URL のキャッシュ（保留）。

### 7.2 セキュリティ

| 項目 | 要件 |
|---|---|
| パスワード保管 | 該当なし（パスワードを保持しないため） |
| APIキー管理 | Google Places API・Geocoding API・Supabase Service Role Keyは、環境変数としてVercel上で管理し、フロントエンドのビルド成果物に含めない |
| 通信 | HTTPSによる暗号化 |
| アクセス制御 | Route Handlers内での権限チェックに加え、RLSでも二重に制御する。管理画面へのアクセスはis_adminフラグで制御する |
| 非公開投稿の保護 | 非公開設定の投稿は、投稿者本人以外が取得できないようRoute Handlers・RLSの両方で制御する |
| 入力安全性 | 感想・コメント等の自由記述欄は、HTMLタグ・スクリプトとして解釈されないようエスケープ処理を行う |
| 画像・動画安全性 | 5.4に準拠する |

### 7.3 不正利用対策（レート制限）

| 対象操作 | 制限 |
|---|---|
| ログイン試行 | 同一IPから1分間に10回 |
| 投稿作成 | 1ユーザーにつき1時間に20件 |
| コメント投稿 | 1ユーザーにつき1分間に5件 |
| 通報 | 1ユーザーにつき1日に20件 |
| アルバム招待リンクの発行 | 1ユーザーにつき1時間に10件（アプリ内招待の送信を含む） |
| しおり招待リンクの発行（v3.0で追加） | 1ユーザーにつき1時間に10件（アプリ内招待の送信を含む） |
| ユーザー名の検索（v3.2で追加） | 1ユーザーにつき1分間に30回 |
| 下書きの保存（v3.0で追加） | 1ユーザーにつき1時間に60件（自動保存を含む） |
| 「まだあった」報告（v3.0で追加） | 1ユーザーにつき1日に50件 |

実装方式：Supabaseのrate_limitsテーブルで実装する。Route Handlers内で対象操作の実行前に、直近の時間枠におけるカウントを参照・更新し、上限超過時は429エラーを返す。Vercelのサーバーレス関数はインスタンスがリクエストごとに変わりうるため、メモリ内カウンタは使用しない。アカウントロック方式は採用しない。

### 7.4 プライバシー

位置情報は「近くのスポットを探す」「ここを投稿」「地図」「徒歩 N 分の表示」を使うときにOS／ブラウザ標準の許可ダイアログで取得する。拒否時は行き先の入力（探す）または東京駅周辺で地図を動かす（投稿）で代替する。端末の位置情報そのものは保存せず、投稿の位置は利用者が地図で合わせたピンの座標とする。下書きは本人以外に一切配信しない。新規登録時に個人情報保護方針・利用規約への同意を必須とする。

### 7.5 運用・保守

| 項目 | 要件 |
|---|---|
| バックアップ | Supabase標準のバックアップ機能を利用する。RPO 24時間、RTOは管理コンソールからの手動復元を前提とする |
| 操作ログ | 対象操作：ログイン成功／失敗、投稿の作成・編集・削除、コメントの投稿・削除、通報、アカウントの登録・退会、管理者による対応操作。保存期間90日。閲覧権限は管理者のみ |
| 稼働率 | 展示・審査期間中の目標稼働率99%（計画的な停止は対象外） |
| デプロイ | VercelのGitHub連携による自動デプロイを用いる |

### 7.6 保守性

投稿カード・ピン・地図・バッジ表示などを共通部品として実装する。地図表示はSC-02・SC-03（上部）・SC-08・SC-12で共通のコンポーネントを使用する。色は CSS 変数に集約し（4.5.5）、ライト／ダークの切替を変数の再定義だけで行えるようにする。Route Handlersについても、Supabaseアクセス・Google API呼び出し・通知送信・画像/動画処理をそれぞれ共通関数として切り出し、重複実装を避ける。

### 7.7 アクセシビリティ

- 画像・動画サムネイルに代替テキスト（alt属性）を設定する
- 情報を色だけで区別せず、アイコンやテキストを併用する
- フォーム入力・ボタン操作をキーボードのみで行えるようにする
- ライト／ダークの両モードで、文字と背景・ボタンのコントラスト比を 4.5:1 以上にする

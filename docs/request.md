# 要求定義書「タビコエ（tabikoe）」

**サービスコンセプト：** みんなの旅の「コエ」を聞いて旅をして、あなたの「コエ」を届ける

## 用語集

本書で使う独自の用語を、開発チームとの認識合わせのためにまとめます。

| 用語 | 定義 |
| --- | --- |
| 投稿 | ユーザーが1つのスポットについて記録する体験談のまとまり（スポット名・カテゴリ・写真・感想などを含む1件のレコード） |
| 旅行タイトル | ユーザーが投稿時に入力する旅の名称。内部的には旅行IDで管理され、同じ旅行IDに紐づく投稿はアルバムとして自動でグルーピングされる。タイトル変更は紐づく全投稿に反映される |
| 旅行ID | 1回の旅行を識別する内部的な識別子。旅行タイトル（表示名）と1対1で紐づき、投稿のグルーピング単位となる |
| スポット | 地図上の1つの場所。Google Places APIの情報と紐づくほか、候補にない場所はユーザーが手動登録できる |
| ピン | 地図上でスポットの位置を示すマーカー。1スポットにつき1つ表示し、投稿があるスポットと「行きたい」スポットに立てる |
| 投稿カード | 投稿の概要（スポット名・カテゴリ・写真・評価等）をまとめて表示するUI部品 |
| 行きたい | ユーザーが訪問候補として保存したスポット。投稿の有無を問わず保存できる |
| アルバム | 同じ旅行に紐づく複数の投稿をまとめて閲覧できる単位 |
| ステータスバッジ | 投稿数・いいね数・訪問都道府県数などの実績に応じて獲得できる称号 |
| 生の声 | 実際にスポットを訪れたユーザー本人による、写真・感想・費用などを含む一次情報 |

## 0. システム概要

### どんなシステムか

旅行や観光で訪れたスポットについて、実際に行った人の「生の声（体験談）」を地図上に投稿・共有できるSNSアプリです。サービス名は「タビコエ」（旅＋声）とします。

対応環境はスマートフォンアプリとWebブラウザの両方です。スマホでもパソコンのブラウザでも同じサービスを利用できるようにします。

### 利用イメージ

大学生の山田さんが地方旅行で小さなカフェを見つけたとします。アプリで「旅行タイトル」「スポット名」「カテゴリ」「星評価」「写真」「感想」を入力して投稿すると、地図上にピンとして表示されます。同じ旅行中の投稿は旅行タイトルのもとに自動でまとめられ、マイページではアルバムとして見返せます。

- **投稿する人：** 自分の旅の記録を残しつつ、他の人の役に立つ情報を共有できる
- **閲覧する人：** 地図から近くの穴場スポットや、実際に行った人の感想を探せる

### 画面一覧（想定）

画面IDは要件定義書「タビコエ（tabikoe）」4.1 画面一覧のSC-XX番号に揃えている。

| 画面ID | 画面名 | 概要 |

| SC-02 | マップ画面 | 投稿スポットのピン、地名検索バー、カテゴリ・距離・費用・滞在時間の絞り込み |
| SC-03 | 投稿作成画面 | 旅行タイトル・スポット名・カテゴリ・写真等を入力して投稿 |
| SC-04 | 投稿カード一覧画面 | カード形式で一覧表示 |
| SC-05 | 投稿詳細画面 | 1件の投稿の詳細情報とコメント欄 |
| SC-06 | マイページ | 投稿一覧・いいね数のサマリー、アルバム・「行きたい」一覧への導線 |

※画面遷移図（ワイヤーフレーム）は別途、画面設計フェーズで作成予定です。

### タビコエの利用サイクル

1. **旅程を組む：** 本アプリ上の投稿を参考に、次の旅行を計画する（アプリ外）
2. **旅行へ行く：** 実際に現地を訪れる
3. **投稿する：** スポットについて、生の声（感想・写真・費用など）を投稿する
4. **他のユーザーが閲覧する：** 旅行を計画しているユーザーが投稿を見る
5. **参考にする：** 次の旅程を組む際の参考にする。1に戻る

このサイクルが回るほど、生の声の量と質が増えていくことが本サービスの核となる価値です。

### なぜこれを作るのか（背景）

現在の旅行情報収集には、次の不満があります。

- SNSは写真や動画中心で、費用・滞在時間などの詳しい体験談が少なく、再検索が必要になる
- 検索エンジンや観光メディアは有名スポットに偏り、穴場が見つけにくい
- 個人の体験談をまとめて見られる場所がなく、複数サービスを行き来する必要がある

本サービスは、生の声を地図と紐づけて蓄積し、旅行前の情報収集を簡単で信頼できるものにすることを目的とします。

## 1. 現在の課題（現状分析）

| 課題 | 具体例 |
| --- | --- |
| ①既存SNSの情報が表面的で「二度手間」が発生 | Instagram・TikTokではスポット名・写真・動画が中心で、費用・滞在時間・感想などが不足している。詳細をGoogleやYahoo!で再検索する必要がある |
| ②既存メディア・検索エンジンが有名スポットに偏っている | 有名な定番スポットばかりが上位に表示され、地元の小さな名所や飲食店が埋もれる |
| ③個人の体験談を蓄積・共有する場がない | Instagram、食べログ、口コミサイトなど複数サービスを行き来する必要がある |

課題に対し、タビコエは次の流れを1つのアプリで完結させます。

1. **投稿：** 実際の生の声を記録する
2. **地図上での可視化：** ピンで場所と紐づける
3. **検索・閲覧：** 探している情報にたどり着く

## 3-1. システム要求（機能）

### 3-1-1. アカウント管理機能 — 要件定義書 3.2 / F-AC

- Googleアカウントで新規登録・ログインできる。パスワードは保持しない
- ログインはブラウザからGoogleのOAuth認可画面に遷移し、Supabase Authの認証コールバックでセッションを確立する方式で行う
- 初回ログイン時は、IdPから取得した表示名・アイコン画像をユーザー名・アイコンの初期値として設定する
- 取得する情報はIdPのユーザー識別子・表示名・アイコンURL・メールアドレスに限る
- 新規登録時に個人情報保護方針・利用規約への同意を必須とする。同意しない場合はアカウントを作成しない
- 同一IPアドレスからのログイン試行は1分間に10回までに制限する
- アクセストークンの有効期限は1時間とし、期限切れ時は操作を中断せず自動的に再発行する。リフレッシュトークンの有効期限は30日とし、最終利用から30日経過すると再ログインを求める
- 手動でログアウトできる
- ユーザー名とアイコン画像を変更できる
- 退会すると、ユーザー名・アイコンを即座に「退会済みユーザー」に置き換え、プロフィールを非表示にする
- 退会後も投稿・コメント・いいねは残す。ただし投稿者表示は匿名化する
- 退会時に、自分が設定した、または設定されたブロック情報を削除する
- 退会済みアカウントの投稿削除依頼は問い合わせ窓口で受け付け、管理者が個別対応する

### 3-1-2. 投稿機能 — 要件定義書 3.3 / F-PO

ユーザーは訪れたスポットについて投稿を作成できます。投稿者本人以外は操作できないようにします。

#### 投稿項目

| 項目 | 必須／任意 | 入力方法 |
| --- | --- | --- |
| 旅行タイトル | 必須 | 既存タイトルから選択、または新規入力（オートコンプリート）。前後の空白を除いた完全一致で判定し、旅行IDで管理する |
| スポット名 | 必須 | Google Places APIの候補とSupabaseの手動登録スポットを表示。候補がなければ名前と位置を手動登録できる |
| カテゴリ | 必須 | グルメ／観光スポット／体験・アクティビティ／宿泊施設／イベント会場から選択 |
| 日付 | 任意 | カレンダーから選択。日本標準時。未来は選択不可 |
| 滞在時間 | 必須 | 30分以内／1時間以内／2時間以内／3時間以内／それ以上から選択 |
| 費用 | 任意 | 数値入力（円、整数）。1人あたりの金額とする |
| 星評価 | 必須 | 星マークで1〜5の整数評価。3.5などは不可 |
| 写真・動画 | 必須（1点以上） | 枚数上限なし |
| 感想 | 任意 | 自由記述 |

費用の入力仕様は以下のとおりです。

- 0〜999,999円の範囲。負数・小数は不可。無料の場合は0を入力する
- 検索・絞り込み時は、入力された数値に対して次のレンジで判定する：〜1,000円／〜3,000円／〜5,000円／5,000円〜

#### データ項目の制限値

文字数は書記素クラスタ単位でカウントします（絵文字・結合文字は1文字として扱う）。

- 旅行タイトル：全角200文字まで
- スポット名：全角200文字まで
- 感想：全角4,000文字まで
- コメント：全角4,000文字まで
- ユーザー名：全角200文字まで
- 写真：1点あたり最大10MB、JPEG／PNGのみ
- 動画：1点あたり最大100MB、MP4形式のみ、再生時間1分以内
- 写真・動画あわせて1投稿あたりの枚数上限は設けない
- 1点目（動画の場合はそのサムネイル）を代表画像とする
- 写真の並び替え機能は設けない
- 写真はアップロード時に表示用の縮小画像を生成し、動画は先頭フレームのサムネイルを生成する。一覧・詳細ではこれらを配信する

#### 旅行タイトルの補足仕様

- 1つの旅行IDに1つの旅行タイトル（表示名）を紐づける
- 投稿作成時、そのユーザーの過去の旅行タイトルを候補表示する
- 候補を選択すると既存の旅行IDに追加し、候補にない名称は新しい旅行IDとして作成する
- 旅行タイトル変更時は、その旅行IDに紐づく全投稿の表示名にも反映する
- 旅行タイトルは同一ユーザー内でのみ一意とする

#### 写真表示

- 1枚：全幅表示
- 2枚：左右2分割
- 3枚：左1枚大＋右2枚
- 4枚以上：2×2グリッド
- 5枚目以降は右下枠に「+1」の枚数バッジを表示する
- 代表画像は1枚目とし、グリッドでは左上または最も大きい枠に配置する
- 1枚しか表示できない箇所では1枚目のみ表示する
- 写真をタップすると、その写真を起点にフルスクリーン表示し、左右スワイプで閲覧できる
- 投稿時に、他人の写り込みへの同意と、車のナンバー等の個人情報確認を促す注意文を表示する
- 個人情報が写り込んだ投稿は問い合わせ窓口で受け付ける

#### 編集・削除

- 自分の投稿の全項目（旅行タイトル・スポット名・カテゴリ・日付・滞在時間・費用・星評価・写真・感想）を編集できる
- 編集しても投稿日時（新着順の基準）は更新しない
- 自分の投稿を削除でき、紐づくコメント・いいねも同時に削除する
- 投稿削除で実績条件を下回っても、一度獲得したステータスバッジは失わない
- 写真を個別に削除・追加できる

### 3-1-3. 地図・検索機能 — 要件定義書 3.4 / F-MP

#### 地図表示・ピン操作

- 投稿スポットをピンで表示する（1スポットにつき1ピン）
- 同一エリアに集中する場合はピンをまとめる
- 検索バーの地名をGoogle Places APIでジオコーディングし、任意のエリアへ移動できる
- ピンをタップすると、そのスポットの投稿一覧を表示する
- 投稿一覧は新着順（デフォルト）・評価順・いいね順で並び替えられる
- 投稿カードから投稿詳細へ遷移できる

#### 検索・絞り込み

- スポット名をキーワード検索できる
- カテゴリ（複数選択可）、距離（500m以内／1km以内／3km以内／5km以内）、費用、滞在時間で絞り込める
- 距離は地図の中心からの距離を基準とする
- 費用未入力の投稿は費用絞り込みの結果から除外する
- 投稿一覧・検索結果は1回20件読み込み、スクロールで追加する
- 表示範囲内のピンは最大100件まで読み込む

### 3-1-4. 閲覧・交流機能 — 要件定義書 3.5 / F-VW

- 投稿カードからスポット名・カテゴリ・写真・感想・費用等を確認できる
- 投稿にコメントを書き込み、コメントを閲覧できる
- 投稿にいいねを付けたり取り消したりできる
- スポットを「行きたい」として保存・取り消しできる
- コメントは1回20件表示し、「もっと見る」で追加読み込みする

本サービスは、アカウント作成・ログイン（SC-01）を除く全ての機能・画面についてログインを必須とする。未ログイン状態で機能画面へ直接アクセスした場合は、ログイン画面（SC-01）へ誘導し、ログイン完了後に元の遷移先へ戻す。

### 3-1-5. 記録・振り返り機能（マイページ） — 要件定義書 3.6 / F-RC

- 自分の投稿一覧を新着順で確認し、旅行ごとに絞り込める
- 同じ旅行IDの投稿をアルバムとして振り返る
- 投稿数と総獲得いいね数を確認する
- オーナーが招待リンクを発行し、編集者／閲覧者いずれかの権限でメンバーを招待できる。招待リンクの有効期限は7日間で、オーナーはいつでも無効化できる
- 編集者はそのアルバムに自分の投稿を追加・編集・削除できる。閲覧者は閲覧のみできる
- メンバーは自分の意思でアルバムから退出できる
- 投稿の有無を問わずスポットを「行きたい」として保存する
- 保存スポットを一覧で確認し、地図上では通常のピンと区別する
- 投稿を削除しても旅行（アルバム）は残す。ただし投稿が0件になったアルバムは一覧に表示しない

### 3-1-6. ステータスバッジ機能 — 要件定義書 3.7 / F-BG

| バッジの種類 | 概要 |
| --- | --- |
| ①都道府県バッジ | その都道府県で1投稿すると獲得するご当地バッジ（例：北海道バッジ） |
| ②投稿数バッジ | 累計投稿数に応じて獲得する（1件、10件、50件、100件など） |
| ③いいね数バッジ | 総獲得いいね数に応じて獲得する（1件、10件、50件、100件、200件） |

獲得済み・未獲得のバッジを一覧で確認できます。

### 3-1-7. 安全・健全性維持機能 — 要件定義書 3.8 / F-SF

- 不適切な投稿・コメントを管理者に通報できる
- 他ユーザーをブロック・解除できる。ブロックしたユーザーの投稿を非表示にする
- 通報対象は、投稿全体／投稿内の個別の写真・動画／投稿の感想テキスト／コメント（個別）／ユーザー（アカウント自体）／スポット／アルバムの7種類とする
- 通報理由は対象に応じて選択肢を出し分ける（不適切な表現／個人情報の掲載／虚偽の情報／著作権・肖像権の侵害／スパム・宣伝目的／なりすまし（ユーザー通報時のみ）／スポット情報の誤り（スポット通報時のみ）／その他）。自由記述は任意
- 同一ユーザーが同一対象を重複通報できない
- 通報対象は管理者の確認まで通常表示し、自動非表示にしない
- 管理者は通報対象を非公開化・削除・問題なしのいずれかで対応する
- 管理者が「削除」で対応した場合のみ、通報者にアプリ内通知を送る。それ以外の対応では通知しない。被通報者への通知は行わない
- ブロックしたユーザーの投稿・コメント・プロフィール・アルバムを非表示にする
- 専用の管理画面を作る

### 3-1-8. 機能の優先順位 — 要件定義書に対応節なし

要件定義書には優先順位を扱う節は設けられていない。また、要件定義書v2.6で新設された通知機能（3.9 / F-NT）・管理者機能（3.10 / F-AD）は、本書には対応する項目がない。

| 優先度 | 内容 |
| --- | --- |
| 最優先 | アカウント管理、投稿の作成・編集・削除、地図・検索、投稿詳細の閲覧、投稿一覧 |
| 優先 | アルバム化、「行きたい」、いいね、コメント、ステータスバッジ、ブロック、通報、アルバム共有 |

#### MVP範囲

「最優先」「優先」は提出（10月7日）までに必ず動作させます。ステータスバッジとコメントについては、中核価値の検証に必須ではないという外部レビューを踏まえ、優先度をメンターと相談します。

## 3-2. システム要求（非機能）

### 最優先

- スマホ・Web両対応（React製PWA、単一コードベース）
- Chrome・Safari・Edgeの最新版および1つ前のメジャーバージョンに対応する
- 新規登録時に個人情報保護方針・利用規約への同意を取得する
- マップ利用時に位置情報の許可を取得し、拒否時は地名検索で代替する
- Google APIキーにリファラー／アプリケーション制限を設定する
- Google Cloudの予算アラートを設定する
- API障害時もアプリ全体を停止させず、地図部分にエラーを表示する
- 画像からEXIFのGPS情報を除去する
- 画像の向き情報を考慮して縮小画像を生成する
- JPEG／PNG以外のファイルを受け付けない

### 優先

- マップ初期表示・検索／フィルター後の再表示を、4G相当・投稿100件程度で3秒以内にする
- 操作ログを記録する
  - 対象：ログイン成功／失敗、投稿の作成・編集・削除、コメントの投稿・削除、通報、登録・退会
  - 内容：操作日時、ユーザーID、操作種別、IPアドレス
  - 保存期間：90日間
  - 閲覧権限：管理者のみ
- バックアップはSupabase標準機能を利用する（RPO 24時間、RTOは手動復元前提）
- 投稿カード・ピン・バッジを共通部品化する
- 感想・コメントはReactの標準描画を使い、HTMLタグやスクリプトとして解釈させない
- 新規登録・パスワード再設定・投稿・コメントにもレート制限を設ける
  - たたき台：登録は同一IPから1時間5件、再設定は同一メールアドレスに1時間3回、投稿は1ユーザー1時間20件、コメントは1ユーザー1分5件
- 外部サービス障害時は次のメッセージを表示する
  - Google Maps API：「地図を読み込めませんでした」
  - Google Places API：「スポット検索が一時的に利用できません」
  - OAuthログイン：「ログインに失敗しました。時間をおいて再度お試しください」
  - Supabase：「データを読み込めませんでした。時間をおいて再度お試しください」および再読み込みボタン
- 障害時も、地図以外の投稿一覧、手動スポット入力、ピン指定など可能な機能は継続する
- 展示・審査期間中の目標稼働率99%を目標とする（計画停止は対象外）
- 画像・動画サムネイルに代替テキスト（alt属性）を設定する
- 色だけに依存せず、アイコンやテキストも併用する
- フォーム入力・ボタン操作をキーボードのみでも行えるようにする

### 結論

企画・利用者要求としては十分ですが、開発着手できる要件としては不足があります。特に、サービスの中核価値である「旅行前の情報収集」と、定義されている機能にずれがあります。

### 最優先で補うべき点

| 重要度 | 問題 | 修正方針 |
| --- | --- | --- |
| 必須 | 旅行前に保存したスポットをまとめる機能がない | 「お気に入り／行きたい」保存をMVPに追加する |
| 必須 | 現在地周辺しか想定されていない | 地名検索、地図移動先検索、指定地点周辺検索を定義する |
| 必須 | 費用・滞在時間が任意入力 | 少なくともどちらかを必須にするか、未入力投稿の扱いを決める |
| 必須 | 「待ち時間」が投稿項目にない | 待ち時間を追加するか、課題文から外す |
| 必須 | 編集・削除の仕様が不足 | 編集項目、削除時のコメント・いいね・アルバムへの影響を定義する |
| 必須 | 旅行タイトルだけで旅行を識別している | 内部に旅行IDを持たせ、同名・年違いの旅行を区別する |
| 必須 | 同一スポットへの複数投稿の表示が不明 | ピン単位、タップ後の一覧、並び順を定義する |
| 必須 | スマホアプリとWebの技術的な意味が不明 | ネイティブ、React Native、PWA、レスポンシブWebから選ぶ |
| 必須 | 未ログインの閲覧範囲が不明 | 詳細、プロフィール、アルバム、コメント、地図の公開範囲を決める |
| 必須 | MVPの境界が曖昧 | 提出時に必ず動く機能と、余裕があれば実装する機能を分ける |

### 中核価値とのずれ

- **複数サービスの往復を減らす：** 費用・滞在時間の絞り込みや並び替えが必要
- **穴場を見つける：** 距離順、新着順、投稿数が少ない場所、情報源タグなどの導線が必要
- **旅程を組む：** 保存、候補リスト、訪問予定管理が不足しているため、最低限お気に入り保存が必要
- **現地ですぐ探す：** 検索半径、距離表示、滞在時間フィルターが必要
- **情報源タグ：** ペルソナ対応表にあるが、投稿項目に存在しない

### 入出力ルールの不足

- 費用・滞在時間の最小値・最大値、負数や小数の可否
- 滞在時間の保存単位（「1時間30分」か「90分」か）
- 星評価を1〜5の整数に限定するか
- 未来日登録の可否、タイムゾーン
- 写真の並び替え、代表画像、削除、圧縮、向き補正
- 10MB画像をそのまま配信するか、表示用画像を生成するか
- 「全角30文字」の定義（半角・絵文字を含む文字数の扱い）
- Google Placesにない穴場を手動登録できるか
- Google Placesの店舗が閉店・移転・削除された場合の扱い
- 投稿一覧・コメント・検索結果のページング件数と並び順
- コメントの編集・削除可否
- いいねを1ユーザー1投稿1件にするか
- 投稿削除時に獲得いいね数やバッジを減らすか
- アルバム名変更・削除、投稿の別アルバムへの移動
- 合計費用を全期間または旅行単位で表示するか
- 宿泊費など複数人分の金額ルール

### アカウント・公開範囲

- ユーザー名・アイコン・プロフィールを匿名化するタイミング
- 投稿写真や感想に含まれる個人情報の扱い
- 退会時にコメント、いいね、通報履歴、ブロック情報を残すか
- 退会後の投稿の削除依頼を受け付けるか
- メールアドレス確認の必須化
- パスワードの最低文字数などの条件
- ログイン状態の有効期間とログアウト機能
- 投稿やアルバムの公開／非公開設定

位置情報の許可は登録時ではなく、地図利用時にOS・ブラウザから取得するのが自然です。拒否時も地名検索などで利用できる仕様が必要です。

### 通報・ブロック・管理機能

- 管理者の認証方法と権限
- 通報理由、自由記述、同一内容への重複通報
- 審査状態（未確認・対応中・削除・問題なし）
- 投稿者・通報者への結果通知
- コメントやユーザー自体を通報できるか
- 削除ではなく非公開化するか、復元可能にするか
- ブロック対象のコメント、プロフィール、アルバムも非表示にするか
- 未ログイン時にブロック対象の投稿が見えることを許容するか

「管理者確認画面は別途検討」としながら、管理者対応を優先機能に含めている点も矛盾しています。

### 非機能要件

合否判定ができるよう、次を数値化・明文化する必要があります。

- 3秒以内の対象画面、通信環境、投稿件数、測定方法、95パーセンタイル
- 目標稼働率と計画停止の扱い
- RPO・RTO
- 操作ログの対象、保存期間、閲覧権限、個人情報の扱い
- 対応ブラウザの基準
- キーボード操作、代替テキスト、色だけに依存しない表示
- API障害時の表示と継続可能な機能
- APIの上限、予算アラート、APIキー制限
- ファイル形式の実体確認、EXIF位置情報の除去、悪意あるファイル対策
- HTML／スクリプト無効化
- 登録、再設定、コメント、投稿へのレート制限

ログイン失敗によるアカウントロックは、第三者が意図的にロックさせる攻撃に利用されます。卒業制作では、アカウントロックよりIP・端末単位のレート制限を優先する方が現実的です。

### 過剰または後回しにすべき要求

1. ステータスバッジ全般
2. コメント機能
3. ブロック機能
4. 高機能な管理者画面
5. ネイティブスマホアプリとWebの同時開発
6. アカウントロック解除メール
7. 詳細な累計サマリー
8. アルバムの外部共有

一方、アルバム共有はメインペルソナの「友人にすぐ紹介したい」という要求に直接対応するため、バッジやコメントより優先度を上げる方が整合的です。また、投稿カード・ピンなどの共通部品化は非機能要件ではなく、設計・実装方針として分離するのが適切です。

### 推奨MVP

1. レスポンシブWebまたはPWA
2. 登録・ログイン・ログアウト
3. 地図の現在地表示と地名検索
4. スポット検索と手動スポット登録
5. 費用・滞在時間・写真を含む投稿の作成・編集・削除
6. 同一スポットの投稿一覧と投稿詳細
7. 距離・カテゴリ・費用・滞在時間による検索・絞り込み
8. お気に入り／行きたい保存
9. 旅行ID単位のアルバム
10. URLによるアルバム共有

いいね、コメント、バッジ、ブロック、本格的な管理画面は第2段階に回すのが妥当です。

この文書は「何を解決したいか」は明確です。実装前には、MVP範囲、旅行・スポットのデータ構造、地図検索の挙動、公開範囲、数値化した受入条件を追加する必要があります。

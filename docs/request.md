## 0. システム概要

### どんなシステムか

**「インスタ × Googleマップ」。** 旅行に行く前に「大阪」「金沢」のように行き先を入れると、実際にそこへ行った人の投稿（写真・星評価・かかった費用・日付）がタイムラインで流れてくる。気になった投稿は地図で「どこにあるか」を確かめ、行きたい場所を「しおり」にまとめて出かける。帰ってきたら自分の投稿を残し、それが次の誰かの参考になる——という旅行情報の SNS です。サービス名は「タビコエ」（旅＋声）とします。

対応環境はスマートフォンとパソコンのWebブラウザです（レスポンシブ対応の単一Webアプリ）。

### 利用イメージ

**見る側（旅行前）**

大学生の山田さんは来月の大阪旅行を計画しています。アプリを開くと検索窓だけの画面が出るので「大阪」と入力します。大阪府のスポットについての投稿が新しい順に並び、1件ずつに「スポット名・星4つ・1人1,200円・9/3・写真3枚」が見えます。予算を「〜3,000円」に絞ると、手頃な店だけが残ります。気になったたこ焼き屋の投稿で「地図で見る」を押すと、地図がその店を中心に開き、ホテルからの距離感がつかめます。「保存」を押すと保存先のしおりを選べるので、「大阪 2泊3日」というしおりを作って入れます。同じように 5 か所ほど集めると、しおりに訪問順で並び、地図上で回る順番を確認できます。迷ったものは既定の「行きたい」に入れておき、あとで振り分けます。

**投稿する側（旅行後）**

旅行から帰った山田さんは、しおりのスポットを開いて「投稿する」を押します。スポット名は埋まっているので、写真・星評価・費用・日付・感想を入れて投稿します。同じ旅行の投稿は「大阪 2泊3日」のアルバムに自動でまとまり、マイページから見返せます。

- **見る人：** 行き先を入れるだけで、費用と日付つきの体験談が並び、地図で位置関係を確かめ、Google マップの保存リストのようにしおりへ集められる
- **投稿する人：** 自分の旅の記録をアルバムとして残しつつ、次に行く人の役に立てる

### 主導線（画面フロー）

```
ログイン（SC-01）
   ↓
検索トップ（SC-00）… 行き先を入力するだけの画面
   ↓ 「大阪」
投稿一覧（SC-04）… その行き先の投稿がタイムラインで流れる。予算・期間・カテゴリで絞る
   ↓ 投稿カードの「地図で見る」            ↓ 投稿カードの「保存」（保存先のしおりを選ぶ）
地図（SC-02）… そのスポットを中心に表示    しおり（SC-23）… 集めたスポットを順番に並べ、地図で確認
   ↓ ピンをタップ
投稿一覧（SC-04）… そのスポットの投稿だけ
```

地図は「探す場所」ではなく「**位置関係を確かめる場所**」と位置づけ、検索・絞り込みは投稿一覧側に集約します。

### タビコエの利用サイクル

1. **行き先を決める：** 検索トップで行き先を入れ、投稿一覧を眺める
2. **旅程を組む：** 気になったスポットをしおりに集め、地図で回る順番を考える（**v2からアプリ内で完結**）
3. **旅行へ行く：** しおりを見ながら現地を訪れる
4. **投稿する：** しおりのスポットから投稿を作る。生の声（感想・写真・費用・日付）を残す
5. **他のユーザーが閲覧する：** 次に同じ行き先を調べる人の投稿一覧に流れる。1に戻る

v1では 2 がアプリ外だった。しおりを加えることで、旅行前から旅行後までがアプリ内で一周する。

### なぜこれを作るのか（背景）

現在の旅行情報収集には、次の不満があります。

- SNSは写真や動画中心で、費用・日付・滞在時間などの詳しい体験談が少なく、再検索が必要になる
- 検索エンジンや観光メディアは有名スポットに偏り、穴場が見つけにくい
- 気になった場所を保存しても、どこにあるか・どう回るかは別のアプリで調べ直す必要がある

本サービスは、生の声を「行き先」で探せるようにし、地図としおりで旅程づくりまでをつなげることで、旅行前の情報収集を簡単で信頼できるものにすることを目的とします。

## 1. 現在の課題（現状分析）

| 課題 | 具体例 |
| --- | --- |
| ①既存SNSの情報が表面的で「二度手間」が発生 | Instagram・TikTokではスポット名・写真・動画が中心で、費用・日付・感想などが不足している。詳細をGoogleやYahoo!で再検索する必要がある |
| ②既存メディア・検索エンジンが有名スポットに偏っている | 有名な定番スポットばかりが上位に表示され、地元の小さな名所や飲食店が埋もれる |
| ③保存した場所を旅程に組み立てる場がない | Instagramで保存し、Googleマップで場所を調べ、メモアプリに順番を書く、と行き来する必要がある |

v1 の実装をメンターに見せた結果、さらに次の課題が見つかった（メンタリング6）。

| 課題 | 具体例 |
| --- | --- |
| ④何ができるアプリなのかが伝わりにくい | 初期画面が地図で、ピン・検索・タブが同時に出ていて目的が読み取れない |
| ⑤地図と投稿の距離が遠い | 地図で探す→一覧→詳細と辿らないと内容が分からず、逆に投稿から場所を確かめる導線が無い |

課題に対し、タビコエ v2 は次の流れを1つのアプリで完結させます。

1. **探す：** 行き先を入れると、生の声がタイムラインで流れる
2. **位置を確かめる：** 投稿から地図へ飛び、距離感をつかむ
3. **集める：** しおりに入れて旅程にする
4. **残す：** 旅行後に投稿し、アルバムとして振り返る

## 3-1. システム要求（機能）

### 3-1-0. 主導線：行き先を入れる → 投稿を眺める → 地図で確かめる（v2で新設）

v2 の中核。利用者が最初に触る流れを、この順に固定する。

#### 検索トップ（SC-00）

- ログイン後、最初に表示する画面とする。**行き先の入力欄だけ**を置き、地図・一覧・その他の情報は出さない
- 入力欄には「どこへ行く？」のようなプレースホルダを置き、都道府県名・市区町村名・スポット名・駅名のいずれでも入力できる
- 入力中は候補（都道府県、登録済みスポット名）を表示する
- 候補を選ぶ、または決定すると投稿一覧（SC-04）へ遷移する
- 未ログイン時は、この画面にログインボタンだけを表示する（サービス説明は一文にとどめる）

#### 投稿一覧（SC-04）— タイムライン形式

- 検索した行き先に関する投稿を、**投稿日時の新しい順に縦一列**で表示する（X（Twitter）のタイムラインに近い見え方。カードのグリッドにはしない）
- 「行き先に関する投稿」の判定は次のとおり
  - 都道府県で検索：投稿のスポットが属する都道府県が一致するもの
  - 市区町村・駅名で検索：その地点の周辺（半径5km以内）にあるスポットの投稿
  - スポット名で検索：そのスポットの投稿（スポットが複数候補ある場合は選ばせる）
- 投稿カードには次を**必ず**表示する：スポット名、星評価（黄色）、予算（1人あたりの費用。未入力なら「費用未記入」）、日付（訪問日。未入力なら投稿日）、写真（1〜4枚のレイアウト、動画はサムネイル）、投稿者、**「地図で見る」ボタン**、**「保存」ボタン**（保存先のしおりを選ぶ）、いいね、コメント件数
- 感想は冒頭数行を表示し、カードをタップすると投稿詳細（SC-05）へ遷移する
- 絞り込み：**予算**（〜1,000円／〜3,000円／〜5,000円／5,000円〜。費用未入力は除外）、**期間**（訪問日の範囲。例：「9月」「先月」「日付指定」）、カテゴリ（複数選択）、滞在時間
- 並び替え：新着順（既定）／評価順／いいね順
- 1回20件を読み込み、スクロールで追加する
- ピンから開いた場合（スポット別一覧）も同じ画面を使い、見出しにスポット名と「地図で見る」「保存」「写真一覧（SC-13）」を置く

#### 投稿から地図へ（SC-04／SC-05 → SC-02）

- 投稿カード・投稿詳細の「地図で見る」を押すと、地図画面（SC-02）へ遷移し、**そのスポットを中心に、ピンを強調して**表示する
- 地図画面には「一覧に戻る」を置き、押すと**直前の投稿一覧に、スクロール位置と絞り込み条件を保ったまま**戻る

### 3-1-1. アカウント管理機能 — 要件定義書 3.2 / F-AC

- Googleアカウントでログインできる。パスワードは保持しない
- **認証の入口はログイン画面（SC-01）のみ**とする。「新規登録」ボタンは置かない
- ログイン後にアカウントが存在しない場合は、自動で同意・新規登録画面（SC-20）へ遷移し、個人情報保護方針・利用規約への同意を得てアカウントを作成する。同意しない場合はアカウントを作成しない
- 取得する情報はIdPのユーザー識別子・表示名・アイコンURL・メールアドレスに限る。初回はIdPの表示名・アイコンを初期値にする
- 同一IPアドレスからのログイン試行は1分間に10回までに制限する
- アクセストークンの有効期限は1時間とし、期限切れ時は自動的に再発行する。リフレッシュトークンは30日とし、最終利用から30日経過すると再ログインを求める
- 手動でログアウトできる。退会（アカウント削除）ができる
- ログイン後の着地点は検索トップ（SC-00）とする（v1 では地図）

### 3-1-2. 投稿機能 — 要件定義書 3.3 / F-PO

ユーザーは訪れたスポットについて投稿を作成できます。投稿者本人以外は操作できないようにします。

#### 投稿の起点（v2で追加）

投稿作成画面（SC-03）へは次の3か所から入れる。

| 起点 | スポット名の扱い |
| --- | --- |
| メニューバーの「投稿」 | 空欄から入力する（v1と同じ） |
| しおり（SC-23）のスポットの「投稿する」 | そのスポットが入力済みの状態で開く |
| 地図（SC-02）の「ここに投稿」 | 地図の中心位置で手動登録モーダル（SC-19）を開き、登録したスポットが入力済みの状態で開く |

#### 投稿項目

| 項目 | 必須／任意 | 入力方法 |
| --- | --- | --- |
| 旅行タイトル | 必須 | 既存タイトルから選択、または新規入力（オートコンプリート）。前後の空白を除いた完全一致で判定し、旅行IDで管理する |
| スポット名 | 必須 | Google Places APIの候補とSupabaseの手動登録スポットを表示。候補がなければ名前と位置を手動登録できる |
| カテゴリ | 必須 | グルメ／観光スポット／体験・アクティビティ／宿泊施設／イベント会場から選択 |
| 日付 | **必須（v2で変更）** | カレンダーから選択。日本標準時。未来は選択不可。投稿一覧・詳細に必ず表示する |
| 滞在時間 | 必須 | 30分以内／1時間以内／2時間以内／3時間以内／それ以上から選択 |
| 費用 | 任意 | 数値入力（円、整数）。1人あたりの金額とする。投稿一覧では「予算」として表示する |
| 星評価 | 必須 | 星マークで1〜5の整数評価。表示は**黄色**で統一する |
| 写真・動画 | 必須（1点以上） | 枚数上限なし |
| 写真の説明 | 任意（**v2で追加**） | 写真・動画ごとに全角100文字までの説明文を付けられる（例：「限定メニューの〇〇」）。投稿詳細のモーダル表示で写真の下に出す。※7章の要確認事項 |
| 感想 | 任意 | 自由記述 |

費用の入力仕様は以下のとおりです。

- 0〜999,999円の範囲。負数・小数は不可。無料の場合は0を入力する
- 検索・絞り込み時は、入力された数値に対して次のレンジで判定する：〜1,000円／〜3,000円／〜5,000円／5,000円〜

#### データ項目の制限値

文字数は書記素クラスタ単位でカウントします（絵文字・結合文字は1文字として扱う）。

- 旅行タイトル：全角200文字まで
- スポット名：全角200文字まで
- 感想：全角4,000文字まで
- コメント：全角4,000文字まで
- 写真の説明：全角100文字まで
- しおりのタイトル：全角100文字まで、しおり内のメモ：全角500文字まで
- ユーザー名：全角200文字まで
- 写真：1点あたり最大10MB、JPEG／PNGのみ
- 動画：1点あたり最大100MB、MP4形式またはiPhone標準カメラのMOV形式、再生時間1分以内（MOVはサーバー側でMP4に変換して保存する）
- 写真・動画あわせて1投稿あたりの枚数上限は設けない
- 1点目（動画の場合はそのサムネイル）を代表画像とする
- 写真の並び替え機能は設けない
- 写真はアップロード時に表示用の縮小画像を生成し、動画は先頭フレームのサムネイルを生成する。一覧・詳細ではこれらを配信する
- 写真・動画とも、位置情報（GPS）などのメタデータを除去してから保存・配信する
- 動画はサイズが大きいため、ブラウザから保存先（Supabase Storage）へ直接アップロードし、サーバー側で受け取り後に検証・サムネイル生成を行う

#### 旅行タイトルの補足仕様

- 1つの旅行IDに1つの旅行タイトル（表示名）を紐づける
- 投稿作成時、そのユーザーの過去の旅行タイトルと、参加中のアルバムの旅行タイトルを候補表示する
- 候補を選択すると既存の旅行IDに追加し、候補にない名称は新しい旅行IDとして作成する
- 旅行タイトル変更時は、その旅行IDに紐づく全投稿の表示名にも反映する
- 旅行タイトルは同一ユーザー内でのみ一意とする
- しおりから投稿する場合、しおりのタイトルを旅行タイトルの初期値にする

#### 写真表示

- 1枚：全幅表示
- 2枚：左右2分割
- 3枚：左1枚大＋右2枚
- 4枚以上：2×2グリッド
- 5枚目以降は右下枠に「+N」の枚数バッジを表示する
- 代表画像は1枚目とし、グリッドでは左上または最も大きい枠に配置する
- 写真・動画をタップすると、その写真・動画を起点にフルスクリーン（モーダル）表示し、左右スワイプまたは←→ボタン（パソコンでは矢印キー）で前後へ移動できる。動画はその中で再生する。写真の説明があればモーダル内に表示する
- この閲覧方法は、写真・動画が表示されるすべての画面で共通とする
- 投稿時に、他人の写り込みへの同意と、車のナンバー等の個人情報確認を促す注意文を表示する

#### 編集・削除

- 自分の投稿の全項目を編集できる。編集しても投稿日時（新着順の基準）は更新しない
- 自分の投稿を削除でき、紐づくコメント・いいねも同時に削除する
- 投稿削除で実績条件を下回っても、一度獲得したステータスバッジは失わない
- 写真を個別に削除・追加でき、写真の説明も個別に編集できる

### 3-1-3. 検索・投稿一覧 — 要件定義書 3.4 / F-MP（v2で「地図」から「検索」中心に再編）

- 行き先（都道府県・市区町村・駅名・スポット名）で投稿を検索できる（3-1-0）
- 予算（費用レンジ）・期間（訪問日の範囲）・カテゴリ（複数選択可）・滞在時間で絞り込める
- 費用未入力の投稿は予算絞り込みの結果から除外する
- 投稿一覧は1回20件読み込み、スクロールで追加する
- 投稿一覧・投稿詳細から地図（SC-02）へ遷移し、対象スポットを中心に表示する
- 投稿一覧・投稿詳細から「保存」（しおりへの追加）ができる
- 距離（500m以内／1km以内／3km以内／5km以内）による絞り込みは、市区町村・駅名・スポット名で検索した場合にのみ表示する（基準点があるため）

### 3-1-4. 地図 — 要件定義書 3.4 / F-MP（v2で情報量を整理）

- 地図画面（SC-02）に置くのは次の要素**だけ**とする：地図、ピン、「みんなの投稿／保存済み」タブ、現在地ボタン、「ここに投稿」ボタン、「一覧に戻る」（投稿一覧から来た場合のみ）
- 検索窓・絞り込みパネル・「投稿を検索」ボタンは置かない（検索は SC-00／SC-04 に集約）
- 投稿スポットをピンで表示する（1スポットにつき1ピン）。同一エリアに集中する場合はまとめる
- タブは「**みんなの投稿**」（公開投稿があるスポット）と「**保存済み**」（自分のしおりに入っているスポット）とし、選択中のタブ名を地図上に表示して、どちらを見ているかが常に分かるようにする。「保存済み」では表示するしおりを選べる（既定は「すべてのしおり」）。ピンの形・色も種別ごとに変え、凡例を出す
- ピンをタップすると、そのスポットの投稿一覧（SC-04）を表示する
- 「ここに投稿」を押すと、地図の中心位置でスポット手動登録モーダル（SC-19）を開き、登録後に投稿作成画面（SC-03）へ進む。既に近く（50m以内）にスポットがあればそれを選ばせる
- 投稿一覧から「地図で見る」で来た場合は、対象スポットを中心に強調表示し、「一覧に戻る」で元の一覧に戻る（3-1-0）
- 初期表示位置は、投稿から来た場合はそのスポット、メニューバーから来た場合は現在地（拒否時は前回表示していた位置、無ければ東京駅周辺）
- 表示範囲内のピンは最大100件まで読み込む

### 3-1-5. 閲覧・交流機能 — 要件定義書 3.5 / F-VW

- 投稿詳細（SC-05）で投稿の全項目（スポット名・カテゴリ・日付・滞在時間・費用・星評価・写真・動画・写真の説明・感想・投稿者・投稿日時）とコメント欄を確認できる。旅行タイトルは表示しない
- 投稿にいいねを付けたり取り消したりできる
- 投稿にコメントを書き込み、閲覧できる。**投稿一覧（SC-04）のカード上でもコメント件数を押すとその場でコメント欄が開き、読み書きできる**（v2で追加。投稿詳細へ移動しなくてよい）
- コメントは1回20件表示し、「もっと見る」で追加読み込みする。編集は不可、削除は本人のみ
- スポットを「保存」してしおりに追加できる。保存先はその場で選び、既定のしおり「行きたい」が先頭に出る。しおりからの削除で取り消せる

本サービスは、ログイン（SC-01）・同意（SC-20）・検索トップの未ログイン表示を除く全ての機能・画面についてログインを必須とする。未ログイン状態で機能画面へ直接アクセスした場合は、ログイン画面へ誘導し、ログイン完了後に元の遷移先へ戻す。

### 3-1-6. 記録・計画機能（マイページ・しおり・アルバム） — 要件定義書 3.6 / F-RC

#### しおり（v2で新設。Google マップの「保存リスト」と同じ使い方）

- しおりはタイトル（例：「大阪 2泊3日」）を持つ**スポットの集まり**で、ユーザーは複数作れる
- **既定のしおり「行きたい」**を全ユーザーに最初から用意する。名前の変更・削除はできない。「とりあえず保存」の受け皿で、仕組みは他のしおりと同じ（v1 の単発の「行きたい」保存はこれに統合し、独立した機能・画面としては持たない）
- スポットを保存できる場所：投稿カード（SC-04）、投稿詳細（SC-05）、スポット別一覧の見出し、地図のピン
- 「保存」を押すと**保存先のしおりを選ぶシート**が開く。既定の「行きたい」が先頭に並び、その場で新しいしおりも作れる。既に入っているしおりにはチェックが付き、外すとそのしおりから削除される（Google マップの保存と同じ操作感）
- 1 つのスポットを複数のしおりに入れられる
- しおり一覧（SC-22）では「行きたい」を先頭に固定し、以降は更新日時の新しい順
- しおり詳細（SC-23）では、スポットを**訪問順**に並べて表示し、上下ボタン（パソコンではドラッグも可）で並び替え、各スポットにメモ（全角500文字）を書ける。スポットの削除ができる
- しおり詳細から地図（SC-02）を開くと、**そのしおりの全スポットにピンと訪問順の番号**を表示し、全体が収まる範囲で表示する
- しおりのスポットには、そのスポットの投稿一覧（SC-04）への導線と、**「投稿する」**（スポット名・旅行タイトルが入力済みの投稿作成）を置く。投稿済みのスポットにはその旨を表示する
- しおりは本人だけが閲覧・編集できる（共有は将来構想。5章）
- しおり（「行きたい」以外）の削除ができる。削除しても、そのスポットが他のしおりに入っていればそちらには残る
- 1ユーザーあたりのしおり数、1しおりあたりのスポット数に上限は設けない（実装上の安全弁として各100件程度を目安とする）

#### マイページ・アルバム

- マイページ（SC-06）に、プロフィール、投稿数・獲得いいね数、しおり・アルバム・マイマップ・バッジへの導線、自分の投稿一覧（旅行で絞り込み）を置く
- 同じ旅行IDの投稿をアルバム（SC-09）として振り返る。アルバム内の写真・動画だけをまとめて一覧（SC-21）で見られる
- オーナーが招待リンクを発行し、編集者／閲覧者いずれかの権限でメンバーを招待できる。招待リンクの有効期限は7日間で、オーナーはいつでも無効化できる
- 編集者はそのアルバムに自分の投稿を追加・編集・削除できる。閲覧者は閲覧のみできる。メンバーは自分の意思で退出できる
- 投稿を削除しても旅行（アルバム）は残す。投稿が0件になったアルバムは一覧に表示しない
- マイマップ（SC-12）で自分の投稿スポットと保存済み（しおり）のスポットを地図で確認できる

### 3-1-7. ステータスバッジ機能 — 要件定義書 3.7 / F-BG

| バッジの種類 | 概要 |
| --- | --- |
| ①都道府県バッジ | その都道府県で1投稿すると獲得するご当地バッジ（例：北海道バッジ） |
| ②投稿数バッジ | 累計投稿数に応じて獲得する（1件、10件、50件、100件など） |
| ③いいね数バッジ | 総獲得いいね数に応じて獲得する（1件、10件、50件、100件、200件） |

獲得済み・未獲得のバッジを一覧で確認できます。投稿の作成・編集の両方で判定します。

### 3-1-8. 安全・健全性維持機能 — 要件定義書 3.8 / F-SF

- 不適切な投稿・写真・感想・コメント・ユーザー・スポット・アルバムを管理者に通報できる。通報理由は対象に応じて出し分け、自由記述は任意。同一対象への重複通報はできない
- 通報対象は管理者の確認まで通常表示し、自動非表示にしない
- 他ユーザーをブロック・解除できる。ブロック関係にあるユーザーの投稿・コメント・プロフィール・アルバムは相互に非表示にする（共同アルバム内は例外）
- 管理者が「削除」で対応した場合のみ、通報者にアプリ内通知を送る。被通報者への通知は行わない

### 3-1-9. 通知・管理者機能 — 要件定義書 3.9・3.10 / F-NT・F-AD（v1に無かった項目）

- コメント・いいね・アルバム参加・権限変更・メンバー削除・新オーナー選出・通報処理結果（削除時）をアプリ内通知で知らせる。メニューバーに未読件数を表示する
- 運営からのお知らせを管理画面から配信し、通知一覧に表示する
- 管理者（`is_admin`）だけが管理画面に入れる。管理者は通報を一覧・絞り込みし、非公開化・削除・問題なしで対応する。ユーザーへの対応はアカウントの一時停止として扱う
- 通知は90日を超えたものを表示しない

### 3-1-10. UI 共通ルール（v2で明記）

メンタリングでの指摘を全画面共通のルールとして定める。

| ルール | 内容 |
| --- | --- |
| 戻るは左、削除は右 | 画面上部の「戻る」「一覧へ」などの戻る系は左端、削除・退出などの破壊的操作は右端に置く。同じ行に並べる場合もこの順を守る |
| 星評価は黄色 | 星は塗りつぶし黄色（未評価分は薄いグレーの輪郭）で統一する。色以外にも「星4」のテキストを併記する |
| 一覧は縦一列 | 投稿一覧は横並びのカードではなく縦に流れるタイムラインとし、1画面に1〜2件が見える大きさにする |
| 地図は最小限 | 地図画面には検索・絞り込み・説明文を置かない。操作はピン・タブ・現在地・投稿の4つに限る |
| どこにいるか分かる | タブ・絞り込み条件・しおり名など「今何を見ているか」を画面上部に常に表示する |
| 主要ボタンは1画面1つ | 各画面で最も期待する操作（検索トップ＝検索、一覧＝地図で見る／しおりに追加、しおり＝投稿する）を目立たせ、それ以外は控えめにする |

### 3-1-11. 機能の優先順位・MVP範囲（v2で改訂）

提出（10月7日）に向けた優先順位。**A→B→C の順に着手し、A が動いていない状態で B 以降に手を付けない。**

## 3-2. システム要求（非機能）

### 最優先

- スマホ・パソコンの Web ブラウザ両対応（レスポンシブ、単一コードベース）
- Chrome・Safari・Edgeの最新版および1つ前のメジャーバージョンに対応する
- 新規登録時に個人情報保護方針・利用規約への同意を取得する
- 地図利用時に位置情報の許可を取得し、拒否時は前回位置または東京駅周辺で代替する
- Google APIキーにリファラー制限を設定し、サーバー専用キー（Places／Geocoding）はブラウザに出さない
- Google Cloudの予算アラートを設定する
- API障害時もアプリ全体を停止させず、地図部分にエラーを表示する
- 画像・動画から位置情報（EXIF GPS 等）のメタデータを除去する
- 画像の向き情報を考慮して縮小画像を生成する
- JPEG／PNG（写真）、MP4／MOV（動画）以外のファイルを受け付けない

### 優先

- 検索トップから投稿一覧の初回表示、および地図の初期表示を、4G相当・投稿100件程度で3秒以内にする
- 操作ログを記録する（ログイン成功／失敗、投稿の作成・編集・削除、コメントの投稿・削除、通報、登録・退会、管理者の対応操作。保存期間90日、閲覧は管理者のみ）
- バックアップはSupabase標準機能を利用する（RPO 24時間、RTOは手動復元前提）
- 投稿カード・ピン・バッジ・地図を共通部品化する
- 感想・コメント・写真の説明・しおりのメモはHTMLタグやスクリプトとして解釈させない
- レート制限：ログインは同一IPから1分10回、投稿は1ユーザー1時間20件、コメントは1分5件、通報は1日20件
- 外部サービス障害時は次のメッセージを表示する
  - Google Maps API：「地図を読み込めませんでした」
  - Google Places API：「スポット検索が一時的に利用できません」
  - OAuthログイン：「ログインに失敗しました。時間をおいて再度お試しください」
  - Supabase：「データを読み込めませんでした。時間をおいて再度お試しください」および再読み込みボタン
- 障害時も、地図以外の投稿一覧、手動スポット入力、しおりの閲覧など可能な機能は継続する
- v1 で保存済みの「行きたい」データは、移行時に既定のしおり「行きたい」へそのまま引き継ぐ
- 展示・審査期間中の目標稼働率99%を目標とする（計画停止は対象外）
- 画像・動画サムネイルに代替テキスト（alt属性）を設定する
- 色だけに依存せず、アイコンやテキストも併用する（ピンの種別、星評価、未読表示）
- フォーム入力・ボタン操作をキーボードのみでも行えるようにする
- データベースの行レベルセキュリティ（RLS）を有効にし、アプリ側の権限判定と二重に守る

## 4. 制約要求

v1 では「React（相談）」としていたが、実装で次の構成に確定した。

- **フレームワーク：** Next.js（App Router）＋ React ＋ TypeScript。画面と API を同じリポジトリで扱う
- **ホスティング：** Vercel
- **データベース・認証・ファイル保存：** Supabase（PostgreSQL、Google OAuth、Storage）
- **地図表示：** Google Maps JavaScript API（無料枠内を前提とし、課金は有効化済み）
- **スポット候補・地名の座標化：** Google Places API、Geocoding API（サーバー側のみで利用）
- **動画処理：** ffmpeg（サーバー側）
- **開発の進め方：** 要求定義 → 要件定義（`docs/requirement.md`）→ ユーザーストーリー → タスク → GitHub Issue → 実装 → Pull Request。本書の変更は必ず要件定義書へ反映してから実装する

## 付録：kenakamu AIからのフィードバック（v1 作成時）

v1 作成時に受けた外部レビュー。指摘のうち MVP 範囲・入出力ルール・公開範囲・通報/ブロック・非機能要件は要件定義書 v2.x で反映済み。「いいね・コメント・バッジ・ブロック・管理画面は第2段階に」という助言は、v1 期間中にすべて実装できたため、v2 では「D. 維持」に位置づける。

以下は参考情報です。納得できる内容はドキュメントへの反映を検討します。

### 結論

企画・利用者要求としては十分ですが、開発着手できる要件としては不足があります。特に、サービスの中核価値である「旅行前の情報収集」と、定義されている機能にずれがあります。

### 最優先で補うべき点

| 重要度 | 問題 | 修正方針 |
| --- | --- | --- |
| 必須 | 旅行前に保存したスポットをまとめる機能がない | 「お気に入り／行きたい」保存をMVPに追加する |
| 必須 | 現在地周辺しか想定されていない | 地名検索、地図移動先検索、指定地点周辺検索を定義する |
| 必須 | 費用・滞在時間が任意入力 | 少なくともどちらかを必須にするか、未入力投稿の扱いを決める |
| 必須 | 「待ち時間」が投稿項目にない | 待ち時間を追加するか、課題文から外す |
| 必須 | 編集・削除の仕様が不足 | 編集項目、削除時のコメント・いいね・アルバムへの影響を定義する |
| 必須 | 旅行タイトルだけで旅行を識別している | 内部に旅行IDを持たせ、同名・年違いの旅行を区別する |
| 必須 | 同一スポットへの複数投稿の表示が不明 | ピン単位、タップ後の一覧、並び順を定義する |
| 必須 | スマホアプリとWebの技術的な意味が不明 | ネイティブ、React Native、PWA、レスポンシブWebから選ぶ |
| 必須 | 未ログインの閲覧範囲が不明 | 詳細、プロフィール、アルバム、コメント、地図の公開範囲を決める |
| 必須 | MVPの境界が曖昧 | 提出時に必ず動く機能と、余裕があれば実装する機能を分ける |

### 中核価値とのずれ

- **複数サービスの往復を減らす：** 費用・滞在時間の絞り込みや並び替えが必要
- **穴場を見つける：** 距離順、新着順、投稿数が少ない場所、情報源タグなどの導線が必要
- **旅程を組む：** 保存、候補リスト、訪問予定管理が不足しているため、最低限お気に入り保存が必要
- **現地ですぐ探す：** 検索半径、距離表示、滞在時間フィルターが必要
- **情報源タグ：** ペルソナ対応表にあるが、投稿項目に存在しない

### 入出力ルールの不足

- 費用・滞在時間の最小値・最大値、負数や小数の可否
- 滞在時間の保存単位（「1時間30分」か「90分」か）
- 星評価を1〜5の整数に限定するか
- 未来日登録の可否、タイムゾーン
- 写真の並び替え、代表画像、削除、圧縮、向き補正
- 10MB画像をそのまま配信するか、表示用画像を生成するか
- 「全角30文字」の定義（半角・絵文字を含む文字数の扱い）
- Google Placesにない穴場を手動登録できるか
- Google Placesの店舗が閉店・移転・削除された場合の扱い
- 投稿一覧・コメント・検索結果のページング件数と並び順
- コメントの編集・削除可否
- いいねを1ユーザー1投稿1件にするか
- 投稿削除時に獲得いいね数やバッジを減らすか
- アルバム名変更・削除、投稿の別アルバムへの移動
- 合計費用を全期間または旅行単位で表示するか
- 宿泊費など複数人分の金額ルール

### アカウント・公開範囲

- ユーザー名・アイコン・プロフィールを匿名化するタイミング
- 投稿写真や感想に含まれる個人情報の扱い
- 退会時にコメント、いいね、通報履歴、ブロック情報を残すか
- 退会後の投稿の削除依頼を受け付けるか
- メールアドレス確認の必須化
- パスワードの最低文字数などの条件
- ログイン状態の有効期間とログアウト機能
- 投稿やアルバムの公開／非公開設定

位置情報の許可は登録時ではなく、地図利用時にOS・ブラウザから取得するのが自然です。拒否時も地名検索などで利用できる仕様が必要です。

### 通報・ブロック・管理機能

- 管理者の認証方法と権限
- 通報理由、自由記述、同一内容への重複通報
- 審査状態（未確認・対応中・削除・問題なし）
- 投稿者・通報者への結果通知
- コメントやユーザー自体を通報できるか
- 削除ではなく非公開化するか、復元可能にするか
- ブロック対象のコメント、プロフィール、アルバムも非表示にするか
- 未ログイン時にブロック対象の投稿が見えることを許容するか

「管理者確認画面は別途検討」としながら、管理者対応を優先機能に含めている点も矛盾しています。

### 非機能要件

合否判定ができるよう、次を数値化・明文化する必要があります。

- 3秒以内の対象画面、通信環境、投稿件数、測定方法、95パーセンタイル
- 目標稼働率と計画停止の扱い
- RPO・RTO
- 操作ログの対象、保存期間、閲覧権限、個人情報の扱い
- 対応ブラウザの基準
- キーボード操作、代替テキスト、色だけに依存しない表示
- API障害時の表示と継続可能な機能
- APIの上限、予算アラート、APIキー制限
- ファイル形式の実体確認、EXIF位置情報の除去、悪意あるファイル対策
- HTML／スクリプト無効化
- 登録、再設定、コメント、投稿へのレート制限

ログイン失敗によるアカウントロックは、第三者が意図的にロックさせる攻撃に利用されます。卒業制作では、アカウントロックよりIP・端末単位のレート制限を優先する方が現実的です。

### 過剰または後回しにすべき要求

1. ステータスバッジ全般
2. コメント機能
3. ブロック機能
4. 高機能な管理者画面
5. ネイティブスマホアプリとWebの同時開発
6. アカウントロック解除メール
7. 詳細な累計サマリー
8. アルバムの外部共有

一方、アルバム共有はメインペルソナの「友人にすぐ紹介したい」という要求に直接対応するため、バッジやコメントより優先度を上げる方が整合的です。また、投稿カード・ピンなどの共通部品化は非機能要件ではなく、設計・実装方針として分離するのが適切です。

### 推奨MVP

1. レスポンシブWebまたはPWA
2. 登録・ログイン・ログアウト
3. 地図の現在地表示と地名検索
4. スポット検索と手動スポット登録
5. 費用・滞在時間・写真を含む投稿の作成・編集・削除
6. 同一スポットの投稿一覧と投稿詳細
7. 距離・カテゴリ・費用・滞在時間による検索・絞り込み
8. お気に入り／行きたい保存
9. 旅行ID単位のアルバム
10. URLによるアルバム共有

いいね、コメント、バッジ、ブロック、本格的な管理画面は第2段階に回すのが妥当です。

この文書は「何を解決したいか」は明確です。実装前には、MVP範囲、旅行・スポットのデータ構造、地図検索の挙動、公開範囲、数値化した受入条件を追加する必要があります。

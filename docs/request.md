# 要求定義書「タビコエ（tabikoe）」v2

**サービスコンセプト：** 「インスタ × Googleマップ」 — 行き先を決めたら、みんなの旅の投稿を眺めて、地図で距離感をつかみ、しおりにまとめて出かける。**本質は「まだ知られていない場所についての、行った人のリアルな声」**。Google マップに載っていない場所への投稿も、載っている場所と同じ重みで扱う

> 2026-09-16 改訂：ワイヤーフレーム（[wireframes.md](wireframes.md)）と画面デザインを描きながら決めた内容（下記「v2 改訂」）を反映した。画面の見た目は wireframes.md を正とする。

## 用語集

本書で使う独自の用語を、開発チームとの認識合わせのためにまとめます。

| 用語 | 定義 |
| --- | --- |
| 行き先 | 利用者がこれから行こうとしている場所。都道府県・市区町村・駅名・スポット名のいずれかで入力する。検索トップ（SC-00）の入力単位 |
| 検索トップ（ハブ） | ログイン後の着地点（SC-00）。「さがす（行き先の入力）」「近くのスポットを探す」「いまいる場所に投稿する」の 3 つだけを置く |
| 投稿 | ユーザーが1つのスポットについて記録する体験談のまとまり（スポット名・カテゴリ・写真・感想・費用・日付などを含む1件のレコード） |
| 投稿一覧 | 行き先に関する投稿を、新しい順に縦に流れるタイムライン形式で表示したもの（X（Twitter）のタイムラインに近い見え方）。SC-04 |
| 投稿カード | 投稿一覧の1件分。スポット名・星評価・予算・日付・写真・地図への導線を持つ |
| 旅行タイトル | ユーザーが投稿時に入力する旅の名称。内部的には旅行IDで管理され、同じ旅行IDに紐づく投稿はアルバムとして自動でグルーピングされる。タイトル変更は紐づく全投稿に反映される |
| 旅行ID | 1回の旅行を識別する内部的な識別子。旅行タイトル（表示名）と1対1で紐づき、投稿のグルーピング単位となる |
| スポット | 地図上の1つの場所。Google Places APIの情報と紐づくほか、候補にない場所はユーザーが手動登録できる |
| ピン | 地図上でスポットの位置を示すマーカー。1スポットにつき1つ表示する |
| しおり | Google マップの「保存リスト」にあたるもの。**旅行タイトル**（例：「大阪旅行」）と**期間**（任意）を持つ**スポットの集まり**で、ユーザーは複数持てる。アルバムと同じ招待リンクでメンバーを招待して一緒に編集できる。スポットは Day（何日目）に振り分け、到着予定時刻・メモ・チェック（行った）を付けられ、地図上で位置関係を確認できる。しおりは旅行タイトルを通じてアルバムと同じ旅行IDにつながり、旅行後にしおりから投稿するとそのアルバムにまとまる |

| 追加モード | しおり詳細の「＋ スポットを追加」から投稿一覧を開いた状態。カードの「＋」を押すだけで、保存先を選ばずにそのしおり（開いていた Day）へ入る |
| 行きたいスポット | 旅行がまだ決まっていない場所を**仮置き**しておく保存先。しおりとは別枠で1つだけあり、名前の変更・削除はできない。保存時に「行きたいスポット」か「しおり」かを選ぶ。マイページから開く。v1 の「行きたい」保存はこれをそのまま引き継ぐ |
| 下書き | 投稿画面で「下書きに保存」した、または途中で閉じた投稿。必須項目が空でも成立する（位置だけの下書きも可）。本人にだけ見え、自分の地図に灰色の破線ピン、マイページの先頭に一覧で出る |
| まだあった報告 | 投稿詳細で他の利用者が押す「まだあった／無くなっていた」。場所の鮮度を保つための報告で、評価ではない。最新の報告を投稿カードに「9月にまだあった」のように表示する |
| タビコエだけの場所 | Google マップ（Places）に無く、利用者が地図上の位置で手動登録したスポットに付くラベル。本サービスの本質（まだ知られていない場所）を表す目印 |
| アルバム | 同じ旅行に紐づく複数の投稿をまとめて閲覧できる単位。**旅行後の記録**（しおりが「旅行前」、アルバムが「旅行後」） |
| ステータスバッジ | 投稿数・いいね数・訪問都道府県数などの実績に応じて獲得できる称号 |
| 生の声 | 実際にスポットを訪れたユーザー本人による、写真・感想・費用などを含む一次情報 |

## 0. システム概要

### どんなシステムか

**「インスタ × Googleマップ」。** 旅行に行く前に「大阪」「金沢」のように行き先を入れると、実際にそこへ行った人の投稿（写真・星評価・かかった費用・日付）がタイムラインで流れてくる。気になった投稿は地図で「どこにあるか」を確かめ、行きたい場所を「しおり」にまとめて出かける。旅先では「いまいる場所」から投稿でき、Google マップに載っていない場所でもその場でピンを刺して残せる。それが次の誰かの参考になる——という旅行情報の SNS です。サービス名は「タビコエ」（旅＋声）とします。

アプリを開いた最初の画面は「さがす・近くのスポットを探す・いまいる場所に投稿する」の 3 つだけを置いたハブで、この 3 つが本サービスでできることのすべてです。

対応環境はスマートフォンとパソコンのWebブラウザです（レスポンシブ対応の単一Webアプリ）。

### 利用イメージ

**見る側（旅行前）**

大学生の山田さんは来月の大阪旅行を計画しています。アプリを開くと検索窓と 2 つのボタンだけの画面が出るので、検索窓に「大阪」と入力します。大阪府のスポットについての投稿が新しい順に並び、1件ずつに「スポット名・星4つ・1人1,200円・9/3・写真3枚」が見えます。予算を「〜3,000円」に絞ると、手頃な店だけが残ります。気になったたこ焼き屋の投稿で「地図で見る」を押すと、地図がその店を中心に開き、ホテルからの距離感がつかめます。「＋」を押すと保存先を選べるので、「大阪旅行」というしおりを作って入れます。しおりに 9/20〜9/22 の期間を入れると Day 1〜3 のタブができ、集めた 5 か所を日ごとに振り分け、到着予定の時刻を入れると時間順に並びます。地図で回る順番も確認できます。行くか決めていない場所は「行きたいスポット」に入れておきます。

**旅行中**

現地では、メニューバーの「しおり」から今日の Day を開き、行った場所にチェックを付けながら回ります。駐車場から見えた夕日がきれいだったので、ハブの「いまいる場所に投稿する」を押すと、現在地にピンが刺さった投稿画面が開きます。Google マップに無い場所ですが、写真と星評価を入れるだけで「タビコエだけの場所」として投稿できます。時間がなければ「下書きに保存」で後回しにします。

**投稿する側（旅行後）**

旅行から帰った山田さんは、しおり「大阪旅行」のスポットを開いて「投稿する」を押します。スポット名も旅行タイトル「大阪旅行」も訪問日も埋まっているので、写真・星評価・費用・感想を入れるだけです。投稿するとしおりのそのスポットに自動でチェックが付き、投稿はアルバム「大阪旅行」にまとまり、マイページから見返せます。しおりとアルバムは同じ名前で行き来できます。

- **見る人：** 行き先を入れるだけで、費用と日付つきの体験談が並び、地図で位置関係を確かめ、「＋」一つで行きたいスポットかしおりへ集められる
- **投稿する人：** いまいる場所からすぐ投稿でき、Google マップに無い場所も残せる。自分の旅の記録をアルバムとして残しつつ、次に行く人の役に立てる

### 主導線（画面フロー）

```
ログイン（SC-01）
   ↓
検索トップ（SC-00）＝ハブ … 「さがす」「近くのスポットを探す」「いまいる場所に投稿する」の 3 つだけ
   │
   ├─ さがす「大阪」 ──→ 投稿一覧（SC-04）… タイムライン。予算・期間・カテゴリで絞る。投稿／写真の切替
   │                        ↓ 「地図で見る」                 ↓ 「＋」（行きたいスポット／しおり＋Day を選ぶ）
   │                     地図（SC-02）… スポットを中心に表示   しおり（SC-23）… Day ごとに並べ、時刻・チェック、地図で確認
   │                        ↓ ピンをタップ                                        ↓ 「投稿する」（スポット・旅行タイトル・訪問日が入力済み）
   │                     投稿一覧（SC-04）… スポット別                          投稿（SC-03）
   │
   ├─ 近くのスポットを探す ──→ 地図（SC-02 探すモード）… 現在地を中心に、近くの声を下に横並び
   │                                ↓ 「ここに投稿」／長押し／既存ピン
   └─ いまいる場所に投稿する ──→ 投稿（SC-03）… 上 1/3 が地図（現在地にピン）、下 2/3 が投稿フォーム。「下書きに保存」
```

地図は「探す場所」ではなく「**位置関係を確かめる場所**」と位置づけ、検索・絞り込みは投稿一覧側に集約します。投稿は「いまいる場所」から 1 タップで始められるようにし、地図を経由させません。

### タビコエの利用サイクル

1. **行き先を決める：** 検索トップで行き先を入れ、投稿一覧を眺める
2. **旅程を組む：** 気になったスポットを「＋」でしおりに集め、Day と到着予定時刻で並べ、地図で回る順番を考える（**v2からアプリ内で完結**）
3. **旅行へ行く：** メニューバーの「しおり」から今日の Day を開き、行った場所にチェックを付けながら回る。見つけた場所は「いまいる場所に投稿する」でその場で投稿（または下書き）
4. **投稿する：** しおりのスポットや下書きから投稿を作る（旅行タイトルはしおりと同じ）。同じ名前のアルバムに自動でまとまり、しおりのスポットにチェックが付く
5. **他のユーザーが閲覧する：** 次に同じ行き先を調べる人の投稿一覧に流れる。1に戻る

v1では 2 がアプリ外だった。しおりを加えることで、旅行前から旅行後までがアプリ内で一周する。

### なぜこれを作るのか（背景）

現在の旅行情報収集には、次の不満があります。

- SNSは写真や動画中心で、費用・日付・滞在時間などの詳しい体験談が少なく、再検索が必要になる
- 検索エンジンや観光メディアは有名スポットに偏り、穴場が見つけにくい
- 気になった場所を保存しても、どこにあるか・どう回るかは別のアプリで調べ直す必要がある

本サービスは、生の声を「行き先」で探せるようにし、地図としおりで旅程づくりまでをつなげることで、旅行前の情報収集を簡単で信頼できるものにすることを目的とします。

## 1. 現在の課題（現状分析）

| 課題 | 具体例 |
| --- | --- |
| ①既存SNSの情報が表面的で「二度手間」が発生 | Instagram・TikTokではスポット名・写真・動画が中心で、費用・日付・感想などが不足している。詳細をGoogleやYahoo!で再検索する必要がある |
| ②既存メディア・検索エンジンが有名スポットに偏っている | 有名な定番スポットばかりが上位に表示され、地元の小さな名所や飲食店が埋もれる |
| ③保存した場所を旅程に組み立てる場がない | Instagramで保存し、Googleマップで場所を調べ、メモアプリに順番を書く、と行き来する必要がある |

v1 の実装をメンターに見せた結果、さらに次の課題が見つかった（メンタリング6）。

| 課題 | 具体例 |
| --- | --- |
| ④何ができるアプリなのかが伝わりにくい | 初期画面が地図で、ピン・検索・タブが同時に出ていて目的が読み取れない |
| ⑤地図と投稿の距離が遠い | 地図で探す→一覧→詳細と辿らないと内容が分からず、逆に投稿から場所を確かめる導線が無い |

課題に対し、タビコエ v2 は次の流れを1つのアプリで完結させます。

1. **探す：** 行き先を入れると、生の声がタイムラインで流れる
2. **位置を確かめる：** 投稿から地図へ飛び、距離感をつかむ
3. **集める：** しおりに入れて旅程にする
4. **残す：** 旅行後に投稿し、アルバムとして振り返る

## 3-1. システム要求（機能）

### 3-1-0. 主導線：行き先を入れる → 投稿を眺める → 地図で確かめる（v2で新設）

v2 の中核。利用者が最初に触る流れを、この順に固定する。

#### 検索トップ（SC-00）＝ハブ

- ログイン後、最初に表示する画面とする。置くのは次の 3 つ**だけ**で、地図・一覧・その他の情報は出さない。並びは「行き先を決めている人」→「今いる場所で探す人」→「今いる場所で投稿する人」の順
  1. **行き先の入力欄**（「どこへ行く？」）：都道府県名・市区町村名・駅名・スポット名のいずれでも入力できる。入力中は候補を「都道府県 → 駅・市区町村 → 登録済みスポット」の順に最大 8 件表示し、候補を選ぶか決定すると投稿一覧（SC-04）へ遷移する
  2. **「近くのスポットを探す」**：位置情報の許可を求め、地図（SC-02）を**探すモード**（現在地を中心に、近くの声を下に横並び）で開く
  3. **「いまいる場所に投稿する」**：位置情報の許可を求め、現在地にピンが刺さった投稿画面（SC-03）を**直接**開く（地図画面は挟まない）。この画面で最も目立たせる主要ボタンとする
- 2・3 で位置情報が拒否されたら、2 は「行き先を入力してください」と入力欄にフォーカスし、3 は東京駅周辺を中心に SC-03 を開いて「地図を動かして場所を合わせてください」と案内する
- 未ログイン時は、この画面にサービス説明一文（「まだ知られていない場所の、行った人のリアルな声」）とログインボタンだけを表示する

#### 投稿一覧（SC-04）— タイムライン形式

- 検索した行き先に関する投稿を、**投稿日時の新しい順に縦一列**で表示する（X（Twitter）のタイムラインに近い見え方。カードのグリッドにはしない）
- 「行き先に関する投稿」の判定は次のとおり
  - 都道府県で検索：投稿のスポットが属する都道府県が一致するもの
  - 市区町村・駅名で検索：その地点の周辺（半径5km以内）にあるスポットの投稿
  - スポット名で検索：そのスポットの投稿（スポットが複数候補ある場合は選ばせる）
- 投稿カードの**見出しはスポット名**とし、その下に感想の冒頭 2 行を引用する。カードには次を**必ず**表示する：スポット名、星評価（黄色）、予算（1人あたりの費用。未入力なら「費用未記入」）、訪問日、写真（1〜4枚のレイアウト、動画はサムネイル）、投稿者、**「地図で見る」ボタン**、**「＋」ボタン**（行きたいスポット／しおりに保存）、いいね、コメント件数
- 現在地が取れているときは「徒歩 N 分」を表示する。最後に「まだあった」報告があった月を「9月にまだあった」のように表示する（3-1-5）。手動登録スポットには「タビコエだけの場所」ラベルを付ける
- カードをタップすると投稿詳細（SC-05）へ遷移する
- **「投稿／写真」の切替**：「写真」にすると、同じ条件の投稿の写真・動画だけをグリッドで表示する（v1 のスポット写真一覧 SC-13 と同じ部品）。並び順は投稿一覧と同じで、写真は元の投稿の順に、同じ投稿の写真は添付順にまとまる。写真をタップするとモーダルで前後に送れ、「この投稿を見る」で SC-05 へ
- 絞り込み（下からのシート）：**予算**（〜1,000円／〜3,000円／〜5,000円／5,000円〜。費用未入力は除外）、**期間**（訪問日の範囲。今月／先月／日付指定）、カテゴリ（複数選択）、滞在時間、距離（駅・スポット名・現在地が基準点のときのみ）
- 並び替え：「新着順 ▾」の**1 つのボタン**を押すとドロップダウンで評価順／いいね順を選べる（3 つを横に並べない）。既定は新着順
- 1回20件を読み込み、スクロールで追加する
- ピンから開いた場合（スポット別一覧）も同じ画面を使い、見出しにスポット名と「地図で見る」「＋」「投稿する」を置く
- しおり詳細から来た場合は**追加モード**（3-1-6）になり、画面上部に「大阪旅行 Day 2 に追加中 [完了]」を出す

#### 投稿から地図へ（SC-04／SC-05 → SC-02）

- 投稿カード・投稿詳細の「地図で見る」を押すと、地図画面（SC-02）へ遷移し、**そのスポットを中心に、ピンを強調して**表示する
- 地図画面には「一覧に戻る」を置き、押すと**直前の投稿一覧に、スクロール位置と絞り込み条件を保ったまま**戻る。地図の表示位置は保持せず、次に「地図で見る」を押したスポットを中心に開き直す

### 3-1-1. アカウント管理機能 — 要件定義書 3.2 / F-AC

- Googleアカウントでログインできる。パスワードは保持しない
- **認証の入口はログイン画面（SC-01）のみ**とする。「新規登録」ボタンは置かない
- ログイン後にアカウントが存在しない場合は、自動で同意・新規登録画面（SC-20）へ遷移し、個人情報保護方針・利用規約への同意を得てアカウントを作成する。同意しない場合はアカウントを作成しない
- 取得する情報はIdPのユーザー識別子・表示名・アイコンURL・メールアドレスに限る。初回はIdPの表示名・アイコンを初期値にする
- 同一IPアドレスからのログイン試行は1分間に10回までに制限する
- アクセストークンの有効期限は1時間とし、期限切れ時は自動的に再発行する。リフレッシュトークンは30日とし、最終利用から30日経過すると再ログインを求める
- 手動でログアウトできる。退会（アカウント削除）ができる
- ログイン後の着地点は検索トップ（SC-00）とする（v1 では地図）

### 3-1-2. 投稿機能 — 要件定義書 3.3 / F-PO

ユーザーは訪れたスポットについて投稿を作成できます。投稿者本人以外は操作できないようにします。

#### 投稿画面の構成（v2 で変更）

- どの入口から入っても同じ画面（SC-03）。**上 1/3 が地図、下 2/3 が v1 で実装済みの投稿フォーム**
- 上の地図は**中央固定ピン**方式（v1 の手動登録モーダル SC-19 と同じ）。ピンは画面中央に固定され、地図をドラッグ・ピンチで動かすとピンが指す位置（＝投稿の位置）が変わる。右上に「現在地に戻す」。初回だけ「地図を動かしてピンを合わせる」と 1 行案内する
- スポット名欄は地図の位置で埋まる（「この場所（新しい場所）」。50m 以内に登録済みスポットがあればそれを選択済みにする）。「変更」で従来どおり名前で検索でき、検索で選ぶと地図がそのスポットへ移動して位置は固定される。「変更」→「新しい場所」で中央固定ピンに戻る
- **帰宅後の投稿と自宅の保護（2026-09-16 追加）**：「いまいる場所に投稿する」は現地用の入口で、帰宅後は しおりの「投稿する」／下書きの「続きを書く」／検索トップでスポット名を検索してスポット別一覧の「投稿する」 のいずれかを使う。現在地から開いた SC-03 で、地図を動かさず登録スポットも選ばずに「新しい場所」のまま投稿しようとしたときは「この位置に新しいスポットを登録して公開します。自宅など公開したくない場所ではありませんか？」と確認する。「変更」の名前検索で選んだ候補は「この付近の新しい場所」ボタンで固定を外し、そこから地図を動かして登録の無い場所を決められる（現地にいなくても投稿できる）。地図の案内文は初回だけ「現地でなければ『変更』から場所を探せます」も出す
- **入力項目・必須条件は v1 のまま変えない**。配置だけを詰めてスクロールを減らす：旅行タイトル・スポット名はラベルと入力欄を横並び、日付／滞在時間と費用／星評価は 2 列、カテゴリと滞在時間はチップ列ではなくドロップダウン、注意文は 1 行に畳んで「詳しく」で全文、感想は 2 行から始めて入力で伸びる、公開設定は感想のラベル行の右端。写真を 1〜3 点選んだ状態なら下 2/3 の中でスクロールなしに全項目が見える
- 写真・動画は「＋」で選ぶとその場にサムネイルが並ぶ（動画は先頭フレームに ▶）。各サムネイルの × で外せる
- 旅行タイトルが空のまま投稿・下書き保存したときは、仮タイトル「今日の投稿（9/16）」で旅行を自動作成する。マイページでは仮タイトルのままの投稿に付け直しを促す
- 下部に固定で「投稿する」と「下書きに保存」。フォーム部分を上に引くと全画面（地図は隠れる）、下に引くと 1：2 に戻る。パソコンでは地図とフォームを左右 1：2 に並べる
- スポット手動登録モーダル（SC-19）は廃止する。候補に無い場所は、ピンの位置がそのまま手動登録スポット（「タビコエだけの場所」）になる

#### 投稿の起点（v2で追加）

投稿画面（SC-03）へは次の入口から入る。メニューバーに「投稿」は置かない。

| 起点 | 地図の初期位置 | スポット名の扱い | その他 |
| --- | --- | --- | --- |
| 検索トップ（SC-00）の「いまいる場所に投稿する」 | 現在地 | 「この場所（新しい場所）」。近くに登録済みがあればそれ | 日付＝今日 |
| 地図（SC-02）の「ここに投稿」（右下に常時表示） | 現在地 | 同上 | 同上 |
| 地図（SC-02）の**長押し**で立てたピンの「ここに投稿」 | 長押しした点 | 同上 | 現在地とずれている・さっき通った場所のため |
| 地図（SC-02）の既存ピンの吹き出し「投稿する」／スポット別一覧の「投稿する」／投稿詳細の「自分も投稿する」 | そのスポット（位置は固定） | そのスポット | — |
| しおり（SC-23）のスポットの「投稿する」 | そのスポット（位置は固定） | そのスポット | 旅行タイトル＝しおりのタイトル、訪問日＝その Day の日付 |
| 下書きの「続きを書く」（マイページ／地図の破線ピン） | 下書きの位置 | 保存していた内容 | 保存していた内容 |
| 自分の投稿の編集 | 投稿のスポット | 投稿のスポット | 「変更」→「新しい場所」で選び直せる |

#### 下書き（v2 で追加）

- 「下書きに保存」は**必須項目が埋まっていなくても押せる**（位置だけの下書きが成立する）。戻る・閉じるで画面を離れた場合も自動で下書きに残す
- 下書きは本人にだけ見え、他人の地図・一覧・検索には一切出ない。自分の地図（SC-02／SC-12）には灰色の破線ピンで表示し、タップ →「続きを書く」で SC-03 を開く。マイページ（SC-06）の先頭に「下書き N 件」の一覧を出す
- 30 日触らなかった下書きは通知で「まだ書きますか？」と知らせる（自動では消さない）
- 下書きを「投稿する」と通常の投稿になり、投稿日時はその時点になる

#### 投稿項目

| 項目 | 必須／任意 | 入力方法 |
| --- | --- | --- |
| 旅行タイトル | 必須 | 既存タイトルから選択、または新規入力（オートコンプリート）。前後の空白を除いた完全一致で判定し、旅行IDで管理する |
| スポット名 | 必須 | Google Places APIの候補とSupabaseの手動登録スポットを表示。候補がなければ名前と位置を手動登録できる |
| カテゴリ | 必須 | グルメ／観光スポット／自然・景勝地／体験・アクティビティ／エンタメ・イベント／ショッピング／宿泊施設 の 7 つから選択（v2 で変更。v1 の「イベント会場」は「エンタメ・イベント」に移行する） |
| 日付（訪問日） | **必須（初期値あり）** | カレンダーから選択。**初期値は今日**（しおりからは その Day の日付）なので、実質は変えたいときだけ触る。日本標準時。未来は選択不可。投稿一覧・詳細に必ず表示する |
| 滞在時間 | 必須 | 30分以内／1時間以内／2時間以内／3時間以内／それ以上から選択 |
| 費用 | 任意 | 数値入力（円、整数）。1人あたりの金額とする。投稿一覧では「予算」として表示する |
| 星評価 | 必須 | 星マークで1〜5の整数評価。表示は**黄色**で統一する |
| 写真・動画 | 必須（1点以上） | 枚数上限なし |
| 感想 | 任意 | 自由記述 |

費用の入力仕様は以下のとおりです。

- 0〜999,999円の範囲。負数・小数は不可。無料の場合は0を入力する
- 検索・絞り込み時は、入力された数値に対して次のレンジで判定する：〜1,000円／〜3,000円／〜5,000円／5,000円〜

#### データ項目の制限値

文字数は書記素クラスタ単位でカウントします（絵文字・結合文字は1文字として扱う）。

- 旅行タイトル：全角200文字まで
- スポット名：全角200文字まで
- 感想：全角4,000文字まで
- コメント：全角4,000文字まで
- しおりのタイトル：全角100文字まで、しおり内のメモ：全角500文字まで
- ユーザー名：全角200文字まで
- 写真：1点あたり最大10MB、JPEG／PNGのみ
- 動画：1点あたり最大100MB、MP4形式またはiPhone標準カメラのMOV形式、再生時間1分以内（MOVはサーバー側でMP4に変換して保存する）
- 写真・動画あわせて1投稿あたりの枚数上限は設けない
- 1点目（動画の場合はそのサムネイル）を代表画像とする
- 写真の並び替え機能は設けない
- 写真はアップロード時に表示用の縮小画像を生成し、動画は先頭フレームのサムネイルを生成する。一覧・詳細ではこれらを配信する
- 写真・動画とも、位置情報（GPS）などのメタデータを除去してから保存・配信する
- 動画はサイズが大きいため、ブラウザから保存先（Supabase Storage）へ直接アップロードし、サーバー側で受け取り後に検証・サムネイル生成を行う

#### 旅行タイトルの補足仕様

- 1つの旅行IDに1つの旅行タイトル（表示名）を紐づける
- 投稿作成時、そのユーザーの過去の旅行タイトルと、参加中のアルバムの旅行タイトルを候補表示する
- 候補を選択すると既存の旅行IDに追加し、候補にない名称は新しい旅行IDとして作成する。しおりの旅行タイトルも同じ旅行IDを指す
- 旅行タイトル変更時は、その旅行IDに紐づく全投稿の表示名にも反映する
- 旅行タイトルは同一ユーザー内でのみ一意とする
- しおりから投稿する場合、旅行タイトルはしおりと同じ旅行IDが入力済みになる

#### 写真表示

- 1枚：全幅表示
- 2枚：左右2分割
- 3枚：左1枚大＋右2枚
- 4枚以上：2×2グリッド
- 5枚目以降は右下枠に「+N」の枚数バッジを表示する
- 代表画像は1枚目とし、グリッドでは左上または最も大きい枠に配置する
- 写真・動画をタップすると、その写真・動画を起点にフルスクリーン（モーダル）表示し、左右スワイプまたは←→ボタン（パソコンでは矢印キー）で前後へ移動できる。動画はその中で再生する
- この閲覧方法は、写真・動画が表示されるすべての画面で共通とする
- 投稿時に、他人の写り込みへの同意と、車のナンバー等の個人情報確認を促す注意文を表示する

#### 編集・削除

- 自分の投稿の全項目を編集できる。編集しても投稿日時（新着順の基準）は更新しない
- 自分の投稿を削除でき、紐づくコメント・いいねも同時に削除する
- 投稿削除で実績条件を下回っても、一度獲得したステータスバッジは失わない
- 写真を個別に削除・追加できる
- 編集時も上 1/3 の地図で位置を選び直せる（「変更」→「新しい場所」）。スポットを変えると、しおり・行きたいの紐づけは変えない

### 3-1-3. 検索・投稿一覧 — 要件定義書 3.4 / F-MP（v2で「地図」から「検索」中心に再編）

- 行き先（都道府県・市区町村・駅名・スポット名）で投稿を検索できる（3-1-0）
- 予算（費用レンジ）・期間（訪問日の範囲）・カテゴリ（複数選択可）・滞在時間で絞り込める。予算・期間はいずれも**投稿単位**（1 人あたりの費用、訪問日）で、旅行全体の合計予算・日数（アルバム単位）で調べる機能は設けない
- 費用未入力の投稿は予算絞り込みの結果から除外する
- 投稿一覧は1回20件読み込み、スクロールで追加する
- 投稿一覧・投稿詳細から地図（SC-02）へ遷移し、対象スポットを中心に表示する
- 投稿一覧・投稿詳細の「＋」から、行きたいスポットまたはしおり（Day 付き）へ保存できる
- 距離（500m以内／1km以内／3km以内／5km以内）による絞り込みは、市区町村・駅名・スポット名で検索した場合と、現在地が取れている場合にのみ表示する（基準点があるため）
- 投稿一覧は「投稿／写真」を切り替えられる（3-1-0）。並び替えは 1 つのボタンのドロップダウンで、写真表示でも同じ並び順が効く

### 3-1-4. 地図 — 要件定義書 3.4 / F-MP（v2で情報量を整理）

- 地図画面（SC-02）に置くのは次の要素**だけ**とする：地図、ピン、凡例、現在地ボタン、「ここに投稿」ボタン（右下に常時表示）、戻る（「ホーム」「一覧に戻る」「しおりに戻る」のいずれか、左上）。**タブは置かない**
- 地図には**投稿専用のモードを設けない**。投稿は「ここに投稿」／長押し／既存ピンのいずれからも SC-03 に直行する（3-1-2）
- **探すモード**（SC-00「近くのスポットを探す」から）：現在地を中心に開き、下 1/3 に近い順の「近くの声」を横並びのカードで出す（見出し＝スポット名、感想の冒頭、徒歩 N 分）。「徒歩圏 ▾」で 500m／1km／3km を切り替える。カードを横にめくると地図のピンが連動して強調され、タップで SC-05
- **長押し**で任意の点にピンを立て、吹き出しの「ここに投稿」で SC-03 へ。ダブルタップは地図のズームに使うため投稿には使わない
- 既存ピンをタップすると吹き出し（スポット名・星・件数・「一覧」「投稿する」）を出す。「一覧」でスポット別の投稿一覧（SC-04）、「投稿する」で SC-03
- 自分の下書きは灰色の破線ピンで表示する（本人にのみ）。タップ →「続きを書く」
- 現在地は青い円で示し、精度が悪いほど円を大きくする
- 検索窓・絞り込みパネル・「投稿を検索」ボタンは置かない（検索は SC-00／SC-04 に集約）
- 投稿スポットをピンで表示する（1スポットにつき1ピン）。同一エリアに集中する場合はまとめる
- 1 つの地図に「**みんなの投稿**」（公開投稿があるスポット）と「**保存済み**」（行きたいスポットと自分のしおりに入っているスポット）を同時に出し、**ピンの色で見分ける：青＝みんなの投稿、赤＝保存済み**（両方に該当するスポットは赤）。自分の下書きは灰色の破線。凡例を地図上に常に出す
- 「ここに投稿」を押すと、現在地にピンが刺さった SC-03 を開く。既に近く（50m以内）にスポットがあればそれを選択済みにする（手動登録モーダルは経由しない）
- 投稿一覧から「地図で見る」で来た場合は、対象スポットを中心に強調表示し、「一覧に戻る」で元の一覧に戻る（3-1-0）
- 初期表示位置は、投稿から来た場合はそのスポット、検索トップの「近くのスポットを探す」から来た場合は現在地（拒否時は検索トップに戻して行き先の入力を促す）
- しおり詳細の「地図で見る」から来た場合は、開いていた Day のスポットだけに訪問順の番号ピンを出し、上に Day タブを重ねて切り替えられる。「すべて」で全日を色分けする。チェック済みのスポットの番号ピンは灰色にする
- 表示範囲内のピンは最大100件まで読み込む
- **Google マップの表示情報を減らす**：地図上の店舗・施設（POI）のラベルは出さない（タビコエのピンだけが場所を示す）。駅名は残す。道路名は拡大したときだけ出す。市区町村などの地名は残す。地図の色を薄くしてピンを目立たせる。3D 表示・建物の立体表示はしない

### 3-1-5. 閲覧・交流機能 — 要件定義書 3.5 / F-VW

- 投稿詳細（SC-05）で投稿の全項目（スポット名・カテゴリ・日付・滞在時間・費用・星評価・写真・動画・感想・投稿者・投稿日時）とコメント欄を確認できる。旅行タイトルは表示しない
- 投稿にいいねを付けたり取り消したりできる
- 投稿にコメントを書き込み、閲覧できる。**投稿一覧（SC-04）のカード上でもコメント件数を押すとその場でコメント欄が開き、読み書きできる**（v2で追加。投稿詳細へ移動しなくてよい）
- コメントは1回20件表示し、「もっと見る」で追加読み込みする。編集は不可、削除は本人のみ
- スポットを「＋」で保存できる。保存先は「行きたいスポット」か「しおり（タイトル別、期間があれば Day も）」をその場で選ぶ。行きたいスポット一覧・しおりからの削除で取り消せる
- **「まだあった／無くなっていた」の報告（v2 で追加）**：投稿詳細に「この場所、まだありますか？」と 2 つのボタンを置き、他の利用者が押せる。1 人 1 回（押し直しは可）。投稿者本人には通知しない（場所の鮮度を保つための報告であり、評価ではない）。最新の報告を投稿カードと投稿詳細に「9月にまだあった」のように表示する
- 投稿詳細に「自分も投稿する」を置き、そのスポットが確定した状態で SC-03 を開く
- 投稿詳細の見出しはスポット名とし、タップするとそのスポットの投稿一覧（SC-04）へ。旅行タイトルは表示しない。非公開投稿にはいいね・コメント欄を出さない

本サービスは、ログイン（SC-01）・同意（SC-20）・検索トップの未ログイン表示を除く全ての機能・画面についてログインを必須とする。未ログイン状態で機能画面へ直接アクセスした場合は、ログイン画面へ誘導し、ログイン完了後に元の遷移先へ戻す。

### 3-1-6. 記録・計画機能（マイページ・しおり・アルバム） — 要件定義書 3.6 / F-RC

#### 保存の2択：「行きたいスポット」と「しおり」（v2で新設）

投稿カード・投稿詳細・スポット別一覧の見出し・地図のピンに置く**「＋」ボタン**から保存する。押すと保存先を選ぶシートが1枚開き、上段に「行きたいスポット」、下段に旅行タイトル別の「しおり」が並ぶ。どちらもチェックを付ける／外すだけで確定し、両方に入れることもできる。しおりにチェックすると、そのしおりに期間があれば **Day の選択**（Day 1／Day 2／…／未定）が展開する（省略時は「未定」）。シートを閉じると「大阪旅行 に保存しました [しおりを見る]」のトーストを出す。

| 保存先 | 役割 | 個数 |
| --- | --- | --- |
| 行きたいスポット | 旅行が決まっていない場所の**仮置き**。名前の変更・削除はできない | 1つ（全ユーザー共通の枠） |
| しおり | 旅行タイトルを付けた**旅の計画**。訪問順・メモを持つ | 複数 |

#### しおり（Google マップの「保存リスト」と同じ使い方。アルバムと旅行タイトルでつながる）

- しおりは**旅行タイトル**（例：「大阪旅行」）と**期間**（開始日〜終了日、任意）を持つスポットの集まりで、ユーザーは複数作れる。シートの「＋ 新しいしおりを作る」またはしおり一覧の「＋ 新規」でその場で作れる（タイトル必須、期間は後からでも設定できる）
- **しおりの旅行タイトルはアルバムの旅行タイトルと共通**とする。しおりを作ると同じタイトルの旅行IDが作られ（既に同名の旅行があればそれに紐づく）、しおりから投稿した投稿はそのアルバムにまとまる。しおり詳細とアルバム画面は互いに導線を持つ（旅行前はしおり、旅行後はアルバム）
- 旅行タイトルの変更はしおり・アルバムの両方に反映する（同じ旅行IDのため）
- 1つのスポットを複数のしおりに入れられる。既に入っているしおりにはシートでチェックが付き、外すとそのしおりから削除される
- **しおり一覧（SC-22）はメニューバーの「しおり」から開く**。各しおりは旅行タイトル・期間（未設定なら「期間未設定」）・スポット数・済み件数だけを表示し、写真は置かない。並び順は期間が近い順（未設定は更新日時順）。期間を過ぎたしおりは末尾に薄く表示し、「アルバムを見る」を出す。「行きたいスポット」への入口はここには置かない（マイページへ）
- **期間と Day タブ**：期間を設定すると日数分の Day タブ（Day 1／Day 2／…）と「未定」タブができる。スポットは 1 つの Day か未定に属する。期間未設定のしおりは「未定」だけが出る。期間を縮めて日が消える場合、その日のスポットは「未定」へ移す（消さない）。各 Day タブに「2/4」のように済み件数を出す
- **到着予定時刻（任意）**：スポットごとに 1 つ。時・分を選ぶピッカーで、分は **10 分刻み**（00／10／…／50）。時刻があるスポットは **Day 内で時刻順に自動で並び**、無いスポットは手動順（上下ボタン、パソコンではドラッグ）でその日の末尾にまとめる。Day をまたぐドラッグはしない
- **Day の移動**：スポットの「Day 1 ▾」を押すと他の Day／未定を選べ、そのスポットがその Day へ移る（時刻があれば時刻順の位置、無ければ末尾）。画面はいまの Day に留まり、「Day 2 に移動しました [Day 2 を見る]」のトーストを出す（続けて振り分けやすいように）
- **チェック**：行った場所をタップでチェックできる。済みはスポット名に取り消し線＋文字を薄くし、位置は動かさない（「次はどこ」が分かるように）。もう一度タップで外せる（確認は出さない）。**自分が**この旅行（同じ旅行ID）でそのスポットに投稿したら自動でチェックする。共同アルバムの他メンバーの投稿では変わらない（しおりは個人の計画のため）。手でチェックしただけでは投稿は作らない
- 各スポットにメモ（全角500文字）を書け、スポットの削除ができる
- しおり詳細の**「＋ スポットを追加」は追加モード**：押すと投稿一覧（SC-04）に遷移し、行き先はしおりに入っているスポットの都道府県を自動で入れる（しおりが空なら検索トップ）。追加先は開いていた Day（未定タブなら未定）。追加モード中は画面上部に「大阪旅行 Day 2 に追加中 [完了]」を表示し、カードの「＋」を押すだけでこのしおりに入る（保存先のシートは出さない）。「完了」でしおりに戻る
- しおり詳細から地図（SC-02）を開くと、**開いている Day のスポットに訪問順の番号ピン**を表示し、全体が収まる範囲で表示する。地図上の Day タブで切り替え、「すべて」で全日を色分けする
- しおりのスポットには、そのスポットの投稿一覧（SC-04）への導線と、**「投稿する」**（スポット名・旅行タイトル・訪問日＝その Day の日付が入力済みの投稿作成）を置く。投稿済みのスポットには「投稿済み」を表示する
- **しおりの共有**：アルバムと同じ方式で、オーナーが招待リンク（7 日間有効、いつでも無効化可）を発行し、リンクを開いた人がメンバーになる。メンバーはスポットの追加・削除、Day と到着予定時刻の変更、メモ、チェックができ、自分の意思で退出できる。**しおりのメンバーとアルバムのメンバーは別**で、アルバムのメンバーであってもしおりに招待されていなければしおりは見えない（招待は別々に行う）
- しおりの削除ができる（右下に置く）。削除しても同じ旅行IDのアルバム（投稿）は残ることを確認ダイアログに書く。そのスポットが他のしおりや行きたいスポットに入っていればそちらにも残る
- 1ユーザーあたりのしおり数、1しおりあたりのスポット数に上限は設けない（実装上の安全弁として各100件程度を目安とする）

#### 行きたいスポット

- 「＋」から仮置きしたスポットの一覧（SC-08）。**マイページの「行きたい」から開く**
- **一覧／地図の切替**を持つ。一覧は投稿ではなくスポットの一覧で、スポット名・代表写真・都道府県・投稿件数を出し、押すとスポット別の投稿一覧（SC-04）へ。地図は SC-02 と同じ地図に行きたいスポットの赤ピンだけを出す
- 各スポットに「＋」があり、押すと**しおりと Day を選ぶシート**が開いてしおりへ振り分けられる（振り分けても行きたいスポットからは消えない。不要になったら「解除」）。地図のピンの吹き出しからも同じ操作ができる

#### マイページ・アルバム

- マイページ（SC-06）に、プロフィール、**下書きの一覧（下書きがあるときだけ先頭に）**、投稿数・獲得いいね数、**行きたい・アルバム・マイマップ・バッジ**の 4 つの導線、自分の投稿一覧（旅行で絞り込み。マイページとアルバムだけ旅行タイトルを表示する）を置く。しおりへの導線はメニューバーに置き、マイページには置かない（「旅行と結びつくもの（しおり）はメニューバー、自分の手元にあるもの（行きたい・アルバム・マイマップ・バッジ）はマイページ」）
- 同じ旅行IDの投稿をアルバム（SC-09）として振り返る。アルバム内の写真・動画だけをまとめて一覧（SC-21）で見られる。同じ旅行タイトルのしおりがあれば、アルバム画面からそのしおりへ遷移できる
- オーナーが招待リンクを発行し、編集者／閲覧者いずれかの権限でメンバーを招待できる。招待リンクの有効期限は7日間で、オーナーはいつでも無効化できる
- 編集者はそのアルバムに自分の投稿を追加・編集・削除できる。閲覧者は閲覧のみできる。メンバーは自分の意思で退出できる
- 投稿を削除しても旅行（アルバム）は残す。投稿が0件になったアルバムは一覧に表示しない
- マイマップ（SC-12）で自分の投稿スポット・下書きと保存済み（しおり）のスポットを地図で確認できる

### 3-1-8. 安全・健全性維持機能 — 要件定義書 3.8 / F-SF

- 不適切な投稿・写真・感想・コメント・ユーザー・スポット・アルバムを管理者に通報できる。通報理由は対象に応じて出し分け、自由記述は任意。同一対象への重複通報はできない
- 通報対象は管理者の確認まで通常表示し、自動非表示にしない
- 他ユーザーをブロック・解除できる。ブロック関係にあるユーザーの投稿・コメント・プロフィール・アルバムは相互に非表示にする（共同アルバム内は例外）
- 管理者が「削除」で対応した場合のみ、通報者にアプリ内通知を送る。被通報者への通知は行わない

### 3-1-9. 通知・管理者機能 — 要件定義書 3.9・3.10 / F-NT・F-AD（v1に無かった項目）

- コメント・いいね・アルバム参加・権限変更・メンバー削除・新オーナー選出・通報処理結果（削除時）をアプリ内通知で知らせる。メニューバーに未読件数を表示する
- 運営からのお知らせを管理画面から配信し、通知一覧に表示する
- 管理者（`is_admin`）だけが管理画面に入れる。管理者は通報を一覧・絞り込みし、非公開化・削除・問題なしで対応する。ユーザーへの対応はアカウントの一時停止として扱う
- 通知は90日を超えたものを表示しない

| ルール | 内容 |

| 星評価は黄色 | 星は塗りつぶし黄色（未評価分は薄いグレーの輪郭）で統一する。色以外にも「星4」のテキストを併記する |

| メニューバーは4項目 | ホーム（＝検索トップ。家のアイコン）・しおり・通知・マイページ。「地図」「投稿」は置かず、検索トップと投稿カードから入る。パソコンでは左サイドバー |
| どこにいるか分かる | 絞り込み条件・しおり名・Day・追加モード・地図の凡例など「今何を見ているか」を画面上部に常に表示する |
| 主要ボタンは1画面1つ | 各画面で最も期待する操作（検索トップ＝いまいる場所に投稿する、一覧＝地図で見る／＋、投稿＝投稿する、しおり＝投稿する）をアクセント色で目立たせ、それ以外は白地に枠線で控えめにする |
| 並び替えは1ボタン | 「新着順 ▾」のように現在の並びを表示した 1 つのボタンを押してドロップダウンで選ぶ。選択肢を横に並べない |
| 配色は空の青 | 旅＝空のイメージ。検索トップだけ上部に空のグラデーション、他の画面は白地。文字は紺、アクセント（主要ボタン・リンク・バッジ・選択状態・みんなの投稿のピン）は空の青、保存済みのピンは赤。完了は緑、星は黄。色の値は wireframes.md「配色」を正とする |
| ダークモード対応 | OS の設定（ライト／ダーク）に追従する。ダークは真っ黒ではなく紺寄りの黒を下地にし、検索トップのグラデーションは夜空、アクセントは一段明るい空の青にする。地図は Google マップのダークスタイル。両モードで文字とボタンのコントラストを確保する |

## 3-2. システム要求（非機能）

### 最優先

- スマホ・パソコンの Web ブラウザ両対応（レスポンシブ、単一コードベース）
- Chrome・Safari・Edgeの最新版および1つ前のメジャーバージョンに対応する
- 新規登録時に個人情報保護方針・利用規約への同意を取得する
- 位置情報は「近くのスポットを探す」「いまいる場所に投稿する」「地図」を使うときに許可を求め、拒否時は行き先の入力（探す）または東京駅周辺で地図を動かす（投稿）で代替する。投稿の位置は端末の位置情報ではなく、利用者が地図で合わせたピンの位置を保存する
- 下書きは本人以外に一切配信しない（一覧・検索・地図・API のすべてで除外する）
- Google APIキーにリファラー制限を設定し、サーバー専用キー（Places／Geocoding）はブラウザに出さない
- Google Cloudの予算アラートを設定する
- API障害時もアプリ全体を停止させず、地図部分にエラーを表示する
- 画像・動画から位置情報（EXIF GPS 等）のメタデータを除去する
- 画像の向き情報を考慮して縮小画像を生成する
- JPEG／PNG（写真）、MP4／MOV（動画）以外のファイルを受け付けない

### 優先

- 検索トップから投稿一覧の初回表示、および地図の初期表示を、4G相当・投稿100件程度で3秒以内にする
- 操作ログを記録する（ログイン成功／失敗、投稿の作成・編集・削除、コメントの投稿・削除、通報、登録・退会、管理者の対応操作。保存期間90日、閲覧は管理者のみ）
- バックアップはSupabase標準機能を利用する（RPO 24時間、RTOは手動復元前提）
- 投稿カード・ピン・バッジ・地図を共通部品化する
- 感想・コメント・しおりのメモはHTMLタグやスクリプトとして解釈させない
- レート制限：ログインは同一IPから1分10回、投稿は1ユーザー1時間20件、コメントは1分5件、通報は1日20件
- 外部サービス障害時は次のメッセージを表示する
  - Google Maps API：「地図を読み込めませんでした」
  - Google Places API：「スポット検索が一時的に利用できません」
  - OAuthログイン：「ログインに失敗しました。時間をおいて再度お試しください」
  - Supabase：「データを読み込めませんでした。時間をおいて再度お試しください」および再読み込みボタン
- 障害時も、地図以外の投稿一覧、手動スポット入力、しおりの閲覧など可能な機能は継続する
- v1 で保存済みの「行きたい」データは、そのまま「行きたいスポット」として引き継ぐ（テーブルは変えない）
- 展示・審査期間中の目標稼働率99%を目標とする（計画停止は対象外）
- 画像・動画サムネイルに代替テキスト（alt属性）を設定する
- 色だけに依存せず、アイコンやテキストも併用する（ピンの種別、星評価、未読表示）
- フォーム入力・ボタン操作をキーボードのみでも行えるようにする
- データベースの行レベルセキュリティ（RLS）を有効にし、アプリ側の権限判定と二重に守る

## 4. 制約要求

v1 では「React（相談）」としていたが、実装で次の構成に確定した。

- **フレームワーク：** Next.js（App Router）＋ React ＋ TypeScript。画面と API を同じリポジトリで扱う
- **ホスティング：** Vercel
- **データベース・認証・ファイル保存：** Supabase（PostgreSQL、Google OAuth、Storage）
- **地図表示：** Google Maps JavaScript API（無料枠内を前提とし、課金は有効化済み）
- **スポット候補・地名の座標化：** Google Places API、Geocoding API（サーバー側のみで利用）
- **動画処理：** ffmpeg（サーバー側）
- **開発の進め方：** 要求定義 → 要件定義（`docs/requirement.md`）→ ユーザーストーリー → タスク → GitHub Issue → 実装 → Pull Request。本書の変更は必ず要件定義書へ反映してから実装する
- **画面設計：** ワイヤーフレーム（`docs/wireframes.md`）と画面デザイン（Claude のキャンバス）を要件定義書 4.3・4.4 の別紙とする。両者は常に同じ内容に保つ
- **v2 で追加するデータ（要件定義で確定）：** 投稿の状態（下書き／公開）、しおり（旅行IDと 1 対 1、期間）、しおりのスポット（Day・到着予定時刻・並び順・メモ・チェック日時）、しおりのメンバーと招待（アルバムと同じ形）、「まだあった」報告（スポット・利用者・状態・日時）

## 付録：kenakamu AIからのフィードバック（v1 作成時）

v1 作成時に受けた外部レビュー。指摘のうち MVP 範囲・入出力ルール・公開範囲・通報/ブロック・非機能要件は要件定義書 v2.x で反映済み。「いいね・コメント・バッジ・ブロック・管理画面は第2段階に」という助言は、v1 期間中にすべて実装できたため、v2 では「D. 維持」に位置づける。

以下は参考情報です。納得できる内容はドキュメントへの反映を検討します。

### 結論

企画・利用者要求としては十分ですが、開発着手できる要件としては不足があります。特に、サービスの中核価値である「旅行前の情報収集」と、定義されている機能にずれがあります。

### 最優先で補うべき点

| 重要度 | 問題 | 修正方針 |
| --- | --- | --- |
| 必須 | 旅行前に保存したスポットをまとめる機能がない | 「お気に入り／行きたい」保存をMVPに追加する |
| 必須 | 現在地周辺しか想定されていない | 地名検索、地図移動先検索、指定地点周辺検索を定義する |
| 必須 | 費用・滞在時間が任意入力 | 少なくともどちらかを必須にするか、未入力投稿の扱いを決める |
| 必須 | 「待ち時間」が投稿項目にない | 待ち時間を追加するか、課題文から外す |
| 必須 | 編集・削除の仕様が不足 | 編集項目、削除時のコメント・いいね・アルバムへの影響を定義する |
| 必須 | 旅行タイトルだけで旅行を識別している | 内部に旅行IDを持たせ、同名・年違いの旅行を区別する |
| 必須 | 同一スポットへの複数投稿の表示が不明 | ピン単位、タップ後の一覧、並び順を定義する |
| 必須 | スマホアプリとWebの技術的な意味が不明 | ネイティブ、React Native、PWA、レスポンシブWebから選ぶ |
| 必須 | 未ログインの閲覧範囲が不明 | 詳細、プロフィール、アルバム、コメント、地図の公開範囲を決める |
| 必須 | MVPの境界が曖昧 | 提出時に必ず動く機能と、余裕があれば実装する機能を分ける |

### 中核価値とのずれ

- **複数サービスの往復を減らす：** 費用・滞在時間の絞り込みや並び替えが必要
- **穴場を見つける：** 距離順、新着順、投稿数が少ない場所、情報源タグなどの導線が必要
- **旅程を組む：** 保存、候補リスト、訪問予定管理が不足しているため、最低限お気に入り保存が必要
- **現地ですぐ探す：** 検索半径、距離表示、滞在時間フィルターが必要
- **情報源タグ：** ペルソナ対応表にあるが、投稿項目に存在しない

### 入出力ルールの不足

- 費用・滞在時間の最小値・最大値、負数や小数の可否
- 滞在時間の保存単位（「1時間30分」か「90分」か）
- 星評価を1〜5の整数に限定するか
- 未来日登録の可否、タイムゾーン
- 写真の並び替え、代表画像、削除、圧縮、向き補正
- 10MB画像をそのまま配信するか、表示用画像を生成するか
- 「全角30文字」の定義（半角・絵文字を含む文字数の扱い）
- Google Placesにない穴場を手動登録できるか
- Google Placesの店舗が閉店・移転・削除された場合の扱い
- 投稿一覧・コメント・検索結果のページング件数と並び順
- コメントの編集・削除可否
- いいねを1ユーザー1投稿1件にするか
- 投稿削除時に獲得いいね数やバッジを減らすか
- アルバム名変更・削除、投稿の別アルバムへの移動
- 合計費用を全期間または旅行単位で表示するか
- 宿泊費など複数人分の金額ルール

### アカウント・公開範囲

- ユーザー名・アイコン・プロフィールを匿名化するタイミング
- 投稿写真や感想に含まれる個人情報の扱い
- 退会時にコメント、いいね、通報履歴、ブロック情報を残すか
- 退会後の投稿の削除依頼を受け付けるか
- メールアドレス確認の必須化
- パスワードの最低文字数などの条件
- ログイン状態の有効期間とログアウト機能
- 投稿やアルバムの公開／非公開設定

位置情報の許可は登録時ではなく、地図利用時にOS・ブラウザから取得するのが自然です。拒否時も地名検索などで利用できる仕様が必要です。

### 通報・ブロック・管理機能

- 管理者の認証方法と権限
- 通報理由、自由記述、同一内容への重複通報
- 審査状態（未確認・対応中・削除・問題なし）
- 投稿者・通報者への結果通知
- コメントやユーザー自体を通報できるか
- 削除ではなく非公開化するか、復元可能にするか
- ブロック対象のコメント、プロフィール、アルバムも非表示にするか
- 未ログイン時にブロック対象の投稿が見えることを許容するか

「管理者確認画面は別途検討」としながら、管理者対応を優先機能に含めている点も矛盾しています。

### 非機能要件

合否判定ができるよう、次を数値化・明文化する必要があります。

- 3秒以内の対象画面、通信環境、投稿件数、測定方法、95パーセンタイル
- 目標稼働率と計画停止の扱い
- RPO・RTO
- 操作ログの対象、保存期間、閲覧権限、個人情報の扱い
- 対応ブラウザの基準
- キーボード操作、代替テキスト、色だけに依存しない表示
- API障害時の表示と継続可能な機能
- APIの上限、予算アラート、APIキー制限
- ファイル形式の実体確認、EXIF位置情報の除去、悪意あるファイル対策
- HTML／スクリプト無効化
- 登録、再設定、コメント、投稿へのレート制限

ログイン失敗によるアカウントロックは、第三者が意図的にロックさせる攻撃に利用されます。卒業制作では、アカウントロックよりIP・端末単位のレート制限を優先する方が現実的です。

### 過剰または後回しにすべき要求

1. ステータスバッジ全般
2. コメント機能
3. ブロック機能
4. 高機能な管理者画面
5. ネイティブスマホアプリとWebの同時開発
6. アカウントロック解除メール
7. 詳細な累計サマリー
8. アルバムの外部共有

一方、アルバム共有はメインペルソナの「友人にすぐ紹介したい」という要求に直接対応するため、バッジやコメントより優先度を上げる方が整合的です。また、投稿カード・ピンなどの共通部品化は非機能要件ではなく、設計・実装方針として分離するのが適切です。

### 推奨MVP

1. レスポンシブWebまたはPWA
2. 登録・ログイン・ログアウト
3. 地図の現在地表示と地名検索
4. スポット検索と手動スポット登録
5. 費用・滞在時間・写真を含む投稿の作成・編集・削除
6. 同一スポットの投稿一覧と投稿詳細
7. 距離・カテゴリ・費用・滞在時間による検索・絞り込み
8. お気に入り／行きたい保存
9. 旅行ID単位のアルバム
10. URLによるアルバム共有

いいね、コメント、バッジ、ブロック、本格的な管理画面は第2段階に回すのが妥当です。

この文書は「何を解決したいか」は明確です。実装前には、MVP範囲、旅行・スポットのデータ構造、地図検索の挙動、公開範囲、数値化した受入条件を追加する必要があります。

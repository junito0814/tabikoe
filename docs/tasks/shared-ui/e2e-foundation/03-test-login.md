## 実装内容

**ログインは Google の画面を経由するので自動化できない。** Google 側が自動操作を弾くし、やるべきでもない（他人の認証基盤を自動で叩くことになる）。そこで**テストのときだけ通れる経路**を作る。

**ここは本番に出てはいけないものを足すタスク**なので、守りを先に決める。

- 経路は `POST /api/e2e/login`。本文で受けるのは**種データの利用者を指す印だけ**（`"user"` または `"admin"`）。任意のメールアドレスや ID は受け取らない
- **`process.env.E2E_TEST === "1"` のときだけ動く。それ以外は 404 を返す**（403 ではなく 404。「あるが断られた」ことすら出さない）
- `E2E_TEST` は **Vercel の Production・Preview のどちらにも設定しない**。[deployment.md](../../../deployment.md) の環境変数の表に「設定しない」と明記する
- 判定は**ファイルの先頭の 1 か所**で行い、純粋関数（`isE2eEnabled()`）に切り出す。単体テストで「未設定・`"0"`・`"true"`・`"1"` 以外はすべて無効」を固定する
- 中では service_role を使って、種データの利用者のセッションを作り、Cookie を返す。**作るのは種データにある 2 名だけ**で、新しい利用者は作らない

あわせて Playwright 側に、**各テストの最初に 1 回ログインして状態を使い回す**仕組みを入れる（`storageState`）。4 本ごとに毎回ログインし直すと、テストの時間がログインで埋まる。

## テスト要件

### 単体テスト

- `isE2eEnabled()` が `"1"` のときだけ true を返すこと（未設定・`""`・`"0"`・`"true"`・`"2"` はすべて false）
- `E2E_TEST` が未設定のとき、`POST /api/e2e/login` が 404 を返すこと

### 結合テスト

- `E2E_TEST=1` のとき、`"user"` でログインでき、以後のリクエストが本人として扱われること
- 本文に種データ以外の指定（任意のメールアドレス）を入れても拒否されること

### E2Eテスト

- なし（Task 5 で使う）

## 関連する受入条件

- テスト専用のログイン経路が `E2E_TEST=1` のときだけ有効で、設定していない環境では 404 を返すこと。単体テストでそれを固定すること

# 受入テスト（E2E）の土台（e2e-foundation）— タスク分割

> カテゴリ: `shared-ui` / ストーリー: [e2e-foundation](../../../user-stories/shared-ui/e2e-foundation.md)
> 要件定義書 9 章 未決定事項 No.12（2026-11-01 に決着）

**土台を作り、主導線の代表 4 本だけを通す。** 閉じてある E2E タスク 36 件は、この土台の上で順に再オープンする。

| # | タスク | 依存 | 内容 |
|---|---|---|---|
| 1 | [Playwright を入れ、CI で動かす](01-playwright.md) | なし | 設定・煙テスト 1 本・CI のジョブ（**落ちてもマージを止めない**） |
| 2 | [ローカル Supabase と種データ](02-local-supabase.md) | なし | `supabase start`・マイグレーション 53 本の適用・E2E 用の種データ |
| 3 | [テスト専用のログイン経路](03-test-login.md) | 2 | `E2E_TEST=1` のときだけ有効。設定していなければ 404 |
| 4 | [Google マップのスタブ](04-maps-stub.md) | 1 | 地図の JavaScript を差し替え、外部 API を 1 回も呼ばない |
| 5 | [主導線の代表 4 本](05-core-flows.md) | 1・2・3・4 | 検索から投稿詳細／投稿の作成／しおりに入れる／未ログインの共有リンク |

**順番は 1 → 2 → 3 → 4 → 5。** 1 と 2 には依存が無いが、**1 を先に入れる**。1 だけなら「Playwright が CI で動くか」をアプリの事情抜きで確かめられ、ここでつまずいたときに原因が 1 つに絞れる。2 を先にすると、落ちたときに Docker の問題かテストの問題か分からない。

3 を 2 の後にするのは、**ログインできたことを確かめるには利用者の行が要る**ため。種データ（2）が無いと、経路（3）が動いたかどうかを見る先が無い。

4 を 5 の前に入れるのは、**4 が無いと 5 が課金される**ため。主導線の 4 本すべてが地図を通る。

各タスクファイルは「依存」「実装内容」「成果物」「テスト要件（単体／結合／E2E）」「関連する受入条件」の構成で統一している（[rule.md](../../../rule.md) のテストルール区分に準拠）。

**このストーリーだけ、テスト要件の書き方が他と違う。** 作っているものがテストの土台なので、「E2E テスト」の欄に書くのは**その土台で動かす E2E 自身**になる。単体テストを書くのは、土台のうち**純粋関数に切り出せる部分と、本番で有効にならないことを固定する部分**だけ（Task 3）。

# Task 3: 場所の確認を共通の部品にし、投稿画面を置き換える

> 要件定義書 3.3.5「場所の確認」（2026-11-07 で追加）・6.2、ワイヤーフレーム決定事項 102・「場所の確認（投稿画面 SC-03 と共通の部品）」
> インデックス: [add-spots-v4](00-index.md)

## 依存

- Task 2（候補が「店か住所か」と住所を持っている）

## 背景

投稿画面には、Google の候補を選んだあとに名前・都道府県を確かめる一手がすでにある（#700。`SpotField` の中の `pending` の分岐）。しおり（Task 4）にも同じものが要る。**別々に作ると 2 つの画面がずれていく**（要件 3.3.5 の理由）ので、投稿画面の分を部品として切り出し、しおりはそれを使う。

切り出すときに、決定事項 102 の変更も入れる。

| | 今（#700） | 直したあと |
|---|---|---|
| 左のボタン | 「やめる」（入力が消える） | **「候補に戻る」**（入力を残したまま候補に戻る） |
| Google マップの表記 | ボタンの下 | **地図のすぐ下**（名前・住所の枠の上端。規約は「Google の内容の上端か下端の近く、同じ枠の中」を求める） |
| 住所 | 出ない | 名前の下に出す（保存しない） |
| 住所で選んだとき | Google の名前（`５丁目` など）が入る | **名前を空にする** |
| 都道府県 | 位置から自動で埋め、直せる | 変えない（利用者が確かめた値として保存するため。要件 6.2） |
| Day | — | しおりのときだけ都道府県の下に出す |

## 実装内容

### 3-1. 部品 `PlaceConfirmPanel` を切り出す

- 置き場所は `src/components/spots/PlaceConfirmPanel.tsx`（投稿にもしおりにも属さないため `spots/`）
- 持つもの: 見出し「ピンの位置と名前を確かめてください」、Google マップの表記（いちばん上）、名前の欄、住所の行、都道府県の欄、**下に差し込む行**（`extraRow`。しおりが Day の行を入れる）、「候補に戻る」と確定のボタン
- 確定のボタンの文字は呼ぶ側が決める（投稿は「この位置で確定」、しおりは「追加」）
- 登録（`POST /api/spots`）と都道府県の引き（`/api/spots/prefecture`）は今の `defaultRegisterSpot`・`defaultFetchPrefecture` を部品の側へ移す。テストで差し替えられる形は残す
- **住所の候補を登録するときは、Place ID を保存せず、50m の寄せもしない**（常に新しく作る）
  - Place ID を保存すると、同じ住所を別の人が入れたときに一意の制約で先の人のスポットが返り、**先の人が付けた名前（「実家」など）が見える**
  - Place ID を保存せずに今の決まり（Place ID が無ければ 50m で寄せる）に乗せると、**住所の近くの別の店に置き換わる**（#1062 と同じこと）
  - だから `POST /api/spots` に「住所で確かめた場所」であることを渡し（`source: "manual"`・`confirmedAddress: true` のような印）、`decideSpotRegistration` に 4 つ目の決まり「住所で確かめた場所は、いつも新しく作る」を足す。同じ場所のスポットが 2 つできることはあるが、別の場所に紐づくよりは害が小さい
  > **要決定**（PR の「決めてほしいこと」4）。上はお勧めの案。
- 地図は持たない。投稿画面は画面の上の地図（`PostLocationMap`）を、しおりはシートの中に置く地図（Task 4）を使い、どちらも**地図の中心＝保存する位置**を `position` で渡す

### 3-2. 判断を純粋関数にする

`src/lib/spots/place-confirm.ts` に置く。

- `initialConfirmName(candidate)`: 店なら Google の名前、住所なら空文字
- `canConfirm({ name, kind })`: 確定のボタンを押せるか

> **要決定**（PR の「決めてほしいこと」9）: 住所で選んで名前を空のまま確定したとき、押せなくするか、「名前のない場所」で登録するか。お勧めは**押せなくする**（しおりに名前の無い行が並んでも、どこか分からないため）。投稿画面も同じ部品なので、答えは両方に効く。

### 3-3. 「候補に戻る」で入力を残す

- 候補の一覧（`SpotAutocompleteInput`）の検索語と結果を、確認に進んでも捨てない。今は `isSearching` を偽にして一覧を畳んでいるので、確認の間も検索語を親（`SpotField`）が持つ形に変える
- 確認の中で直した名前・都道府県は、「候補に戻る」で捨てる（別の候補を選び直すため）。同じ候補をもう一度選んだら、Google の名前から始まる
  > **要決定**（PR の「決めてほしいこと」13）: 要件の「入力を残したまま候補に戻り」（3.3.5）・受入条件 107 の「入力」が、**検索語**だけを指すのか、**確認の中で直した名前**も含むのか。上はお勧めの案（検索語だけ）。

### 3-4. 投稿画面を置き換える

- `SpotField` の `pending` の分岐を `PlaceConfirmPanel` に置き換える。確定したあとの流れ（`onLock`）は今のまま
- 投稿画面の「場所の確認」は、フォームの中のスポット欄の位置に出る（地図は画面の上 1/3）。今のフォームでは、**地図とスポット欄のあいだに見出し「投稿する」と旅行タイトルの欄が挟まる**（`PostFormFields` の並び）。部品のいちばん上に表記を置いても「地図のすぐ下」にならない
  > **要決定**（PR の「決めてほしいこと」10）: 投稿画面で表記を「地図のすぐ下」にするために、確認の間だけ部品をフォームのいちばん上（見出しの上）に出すか、今の位置のまま部品の上端に置くか。

## テスト要件

### 単体テスト
- `initialConfirmName`: 店は Google の名前、住所は空
- `canConfirm`: 決めてほしいこと 9 の答えのとおり
- `decideSpotRegistration`: 住所で確かめた場所は、50m 以内に登録済みがあっても「新しく作る」になること。今の 3 通り（同じ Place ID／違う Place ID が近くにある／Place ID が無い）の結果が変わらないこと
- `PlaceConfirmPanel`: Google マップの表記が名前の欄より上にあること。`extraRow` を渡したときだけ都道府県の下に出ること。確定で `registerSpot` に**地図の中心の位置・直した名前・都道府県・Place ID** が渡り、住所が渡らないこと
- `SpotField`: 「候補に戻る」で検索語と候補の一覧が残っていること。今の `SpotField.confirm.test.tsx` を、文言（「やめる」→「候補に戻る」）以外は書き換えずに通すこと

## 関連する受入条件

- 場所の確認で地図を動かし名前を直して追加すると、その位置と名前で登録されること。「候補に戻る」で入力が残っていること（受入条件 107）
- 投稿画面の「場所の確認」がしおりと同じ部品であり、「候補に戻る」・住所で探す・都道府県の欄・Google マップの表記の位置が同じであること（受入条件 111）
- Google の候補を選んだあとに、50m 以内にある別の店に置き換わらないこと（受入条件 112。#1064 で直したものが、部品を切り出したあとも保たれていること）

# Task 1: 投稿 0 件のスポットを、他の人の候補に出さない

> 出典: [add-spots.md](../../../user-stories/itinerary/add-spots.md)「投稿 0 件の場所」
> 要件定義書 3.3.5「手動登録スポットの共有」（2026-11-07 に変更）・3.11.4「投稿 0 件の場所」
> インデックス: [add-spots-v4](00-index.md)

## 依存

- なし（#1062「Google の候補が 50m 以内の別の店に置き換わる」の修正 PR #1064 はマージ済み。`decideSpotRegistration` をこのタスクで使う）

## 背景

今は、登録されたスポットが**投稿の有無にかかわらず**全員の候補に出る（`/api/spots/candidates`・行き先の候補）。Task 4 でしおりから場所を入れられるようになると、**投稿が 1 件も無いスポット**が増える。しおりは非公開なのに、そこに入れた場所の名前（自宅の住所に「実家」と付けた、など）が他の人の候補に出てしまう。

要件 3.3.5 は 2026-11-07 に、**他の人の候補（投稿画面・行き先・しおりの検索）と地図に出すのは、投稿が 1 件以上あるスポットだけ**と改めた。投稿 0 件のスポットは、入れた人のしおりの中にだけ出る。

## 実装内容

### 1-1. 「出してよいか」の判断を 1 つにまとめる

純粋関数 `isSpotListable` を作り、**候補に出してよいか**をここだけで決める（AGENTS.md 13・14）。

| 入力 | 意味 |
|---|---|
| `publicPostCount` | そのスポットの、いま見られる投稿の件数（`countPublicSpotPosts` と同じ「公開・公開済み・運営が隠していない」） |
| `inViewerItinerary` | 見ている人がメンバーのしおりに、そのスポットが入っているか |

- `publicPostCount >= 1` → 出す
- `inViewerItinerary` → 出す（自分のしおりに入れた場所は、自分には出す）
- どちらでもない → 出さない

> **要決定**（PR の「決めてほしいこと」2）: 「投稿 1 件以上」に**非公開の投稿・下書き**を数えるか、自分のしおりに入っている 0 件のスポットを**自分には**出すか。上はお勧めの案（公開の投稿だけを数える・自分には出す）で書いている。

### 1-2. 候補を返すところに当てる

| 場所 | 今 | 直したあと |
|---|---|---|
| `/api/spots/candidates`（投稿画面の「変更」。Task 4 からはしおりの検索も） | 名前が合えば出す | `isSpotListable` が真のものだけ |
| `src/lib/search/suggest-destinations.ts`（行き先の候補のスポット） | 名前が合えば出す | 同上 |
| `src/lib/map/get-map-pins.ts`（地図） | すでに公開投稿のあるスポットだけ（`posts!inner`） | 変えない。**変えないことをテストで固める** |

- `inViewerItinerary` を出すために、見ている人がメンバーのしおりのスポット ID をまとめて 1 回で取る（`itinerary_members` → `itinerary_spots`）。候補 1 件ごとに問い合わせない
- 投稿数は、今の `posts(count)`（下書き・非公開も数えている）ではなく、公開の投稿だけを数える形にする（`countPublicSpotPosts` と同じ 3 条件。条件の写しを作らない）

### 1-3. 地図のピンの「50m 以内」と、同じ Place ID の扱い

投稿画面は、地図の中心から 50m 以内のスポットを**自動でスポット欄に出す**（`resolve-by-location.ts`）。また、ピンだけで指して投稿すると、50m 以内のスポットに**寄せる**（`POST /api/spots`・`finalize-spot.ts`。要件 3.3.5「重複登録の防止」）。ここに他の人の 0 件のスポットが掛かると、**その名前が出るうえ、自分の投稿がそのスポットに付いて公開される**。

> **要決定**（PR の「決めてほしいこと」3）: 他の人の投稿 0 件のスポットを、50m の照合・寄せから外すか。同じ Place ID の Google の候補を選んだときはどうするか。下はお勧めの案で書いている。

- 50m の照合（自動で出す・寄せる）は、`isSpotListable` が偽のスポットを**無いものとして**判断する。`decideSpotRegistration` に渡す `nearby` を、先に絞ってから渡す（判断の関数そのものは変えない）
- 同じ Place ID のスポットは、0 件でも今までどおり寄せる（`spots.place_id` は一意なので、同じ店をもう 1 つ作れない）。名前が見えるのは店の名前に限られる ── 住所の候補は Place ID を保存しない（Task 3・決めてほしいこと 4）ので、自宅に付けた名前がこの道で出ることはない

## テスト要件

### 単体テスト
- `isSpotListable`: 公開の投稿 1 件以上 → 真／0 件で自分のしおりに入っている → 真／0 件でどこにも入っていない → 偽／下書き・非公開の投稿しか無い → 偽（決めてほしいこと 2 の答えで書き直す）
- 候補の組み立て（`/api/spots/candidates` の中の、取ってきた行から候補を作る部分）が、偽のスポットを落とすこと
- 50m 以内に他の人の 0 件のスポットしか無いとき、`decideSpotRegistration` が「新しく作る」になること（絞ったあとの `nearby` が空になる）

### 結合テスト
- 利用者 A がしおりにだけ入れたスポット（投稿 0 件）が、利用者 B の `/api/spots/candidates` と行き先の候補に出ず、A には出ること
- そのスポットに A が公開投稿を 1 件付けると、B にも出ること

### E2Eテスト
- なし（[Task 6: 受入テスト（E2E）](06-acceptance-e2e.md)でまとめて検証する）

# Task 3: リフレッシュトークンの30日失効ルールとログイン誘導

## 実装内容

- リフレッシュトークンの最終利用日時（Supabase Auth側で管理）が30日を超過している場合、自動リフレッシュを行わず未ログイン状態として扱う
- 30日超過が検知された場合、Cookieを破棄し、ログイン画面（SC-01）へ誘導する
- 元の遷移先を保持し、再ログイン後に復帰できるようにする（F-AC-01のログイン画面`redirect_to`機構と連携）

## 成果物

- 30日失効判定ロジック
- 失効時のログイン誘導処理

## 実装メモ（2026-09-19）

- Supabase のリフレッシュトークンは（無料プランでは）自動で期限切れにならないため、最終利用日時はアプリ側で持つ。`src/proxy.ts` が httpOnly の Cookie `tabikoe-last-active`（epoch ミリ秒）を 1 時間に 1 回書き直し、セッション Cookie があって 30 日を超えていれば `signOut()` で破棄し、`/login?error=expired&redirect_to=<元のパス>` へ送る（API は 401 `session_expired`）。判定は `src/lib/auth/session-activity.ts`（純粋関数）。
- 未ログインのリクエストでは古い記録を消し、次にログインした人が前の記録で締め出されないようにする。記録が無いときは失効とみなさず、その時点から数える。
- ログイン画面（`AuthScreen`）は `error=expired` で「しばらく利用がなかったため、もう一度ログインしてください」を出す。

## テスト要件

### 単体テスト
- リフレッシュトークンの最終利用日時が30日以内のケースで、自動リフレッシュが許可されることを検証する
- 最終利用日時が30日を超過しているケースで、リフレッシュを行わず再ログイン要求に分岐することを検証する

### 結合テスト
- テスト用DB／Supabaseプロジェクトで最終利用日時を30日超過に設定したセッションに対し、リフレッシュAPI呼び出しが拒否され、Cookieが破棄されることを確認する

### E2Eテスト
- 30日以上前の最終利用日時を持つセッションでログイン必須画面にアクセスした場合、ログイン画面へリダイレクトされ、再ログイン後に元の画面へ復帰することを確認する

## 関連する受入条件

- 最終利用から30日経過したセッションでは、再ログインが求められること

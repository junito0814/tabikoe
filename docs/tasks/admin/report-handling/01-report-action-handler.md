# Task 1: 通報対応操作 Route Handler（非公開化／削除／問題なし）

> 出典: [report-handling.md](../../../user-stories/admin/report-handling.md)
> インデックス: [report-handling](00-index.md)

## 依存

- report-list [Task1: 通報一覧取得・絞り込み Route Handler](../../admin/report-list/01-report-list-handler.md)

## 実装内容

- 通報対象に対する対応操作（非公開化／削除／問題なし）を実行するAPIを実装する
  - 非公開化：対象（投稿・コメント等）を一般ユーザーから見えない状態にする。復元可能な形で行う（論理非公開化）
  - 削除：対象を削除する。復元不可
  - 問題なし：通報を却下し、対象の状態は変更しない
- 対象種別による読み替えを行う：ユーザー→アカウントの一時停止、スポット→当該スポットの非公開化、アルバム→当該アルバムの非公開化
- 対応した管理者・対応日時・対応理由（任意メモ）を`reports`テーブルに記録し、`reports.status`を対応状態に更新する
- Supabase管理コンソールからの直接操作を行わない運用を前提とし、本APIを唯一の対応経路とする

## 成果物

- `app/api/admin/reports/[id]/action/route.ts`

## テスト要件

### 単体テスト
- 「非公開化」「削除」「問題なし」の各操作で、対象種別（投稿／コメント／写真・動画／感想／ユーザー／スポット／アルバム）ごとに正しい読み替え処理が呼ばれることを検証する
- 対応した管理者・対応日時・対応理由が`reports`に正しく記録されることを検証する

### 結合テスト
- テスト用DBで各対象種別・各対応操作を実行し、対象データの状態（非公開化フラグ／削除／変化なし）が正しく反映されることを確認する
- 「非公開化」した対象を復元できることを確認する
- 「削除」した対象が復元できないことを確認する

### E2Eテスト
- なし（[Task 4: 受入テスト（E2E）](04-acceptance-e2e.md)でまとめて検証する）

## 関連する受入条件

- 通報対象に対して「非公開化」「削除」「問題なし」のいずれかの対応を実行できること
- 「非公開化」で対応した対象が、一般ユーザーから見えなくなり、かつ復元できること
- 「削除」で対応した対象が削除され、復元できないこと
- 対応した管理者・対応日時・対応理由（任意メモ）が記録されること
- ユーザー・スポット・アルバムへの通報について、それぞれ規定の対応（アカウント一時停止／スポット非公開化／アルバム非公開化）に読み替えられること

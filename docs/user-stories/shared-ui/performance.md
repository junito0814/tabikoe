# 性能改善（performance）

> 出典: [requirement.md](../../requirement.md) 7.1「性能」（2026-09-22 に実装方針を追記）

## ユーザーストーリー

利用者として、画面を開いたり戻ったりしたときに待たされたくない。旅先でスマホから使うので、1 回の操作で 1 秒以上白い画面が続くと使う気が失せるから。

## 現状（2026-09-22 に本番ビルドで測定）

| 項目 | 値 |
|---|---|
| スポット別一覧のサーバー応答 | 0.5〜0.9 秒 |
| 最初に何か見えるまで | 0.9〜1.3 秒 |
| 画面表示の直後に裏で走るリンクの先読み | 20 本超（各 0.07〜0.2 秒） |
| 認証確認 `getUser()` 1 回 | 0.03〜0.13 秒（毎回 Supabase Auth へ通信。1 画面で 3 回、API 1 本で 2 回） |
| 認証確認 `getClaims()` 1 回 | 0.001 秒（手元で署名検証。鍵は 1 度取れば共有） |
| Supabase への往復 1 回 | 約 50ms（東京リージョン） |

ボトルネックはブラウザの描画（0.15 秒）ではなく、1 画面あたり 40 回前後の Supabase 往復。

## 詳細（3 段階。PR 1 → 効果を実機で確認 → 2・3 は保留）

1. **通信の回数を減らす**（Task 1）: 認証確認を手元の署名検証に、先読みでは関所の問い合わせを省く、一覧カードの先読みを切る、ページ内の直列クエリを並列に、未読件数の再取得を 60 秒に 1 回に、直前に見た画面は 30 秒間サーバーへ行かずに表示。
2. **骨組みを先に出す**（Task 2、保留）: `loading.tsx` と Suspense で見出し・地図の枠・カードの灰色の枠を先に出し、一覧を後から流し込む。
3. **サーバーの仕事を減らす**（Task 3、保留）: 1 画面 1 クエリ化（Postgres 関数）、写真の署名 URL のキャッシュ、関所の users 確認を署名付き Cookie に。

## 受入条件

- [ ] 本番ビルドで、スポット別一覧のサーバー応答が 0.4 秒以下、画面表示直後の裏の先読みが 5 本以下、1 画面あたりの Supabase 往復が 10 回以下になること（Task 1）
- [ ] ログイン状態の判定（未ログイン・一時停止・登録待ち・30 日失効）が Task 1 の前と同じ結果になること
- [ ] 直前に見た一覧に戻ったとき、30 秒以内ならサーバーへ行かずに表示されること

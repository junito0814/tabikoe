# F-MP-06 所要時間の実測（travel-time）

> 出典: [requirement.md](../../requirement.md) 3.4.6・4.5.7・6.7・8章 79（2026-09-25 決定）
> 前身: [feedback-0919.md](../shared-ui/feedback-0919.md) の「移動手段」（v3.2。直線距離からの目安だけだった）

## ユーザーストーリー

旅先で「近くのスポットを探す」を使う人として、表示される所要時間が実際に近い値であってほしい。車で 20 分かかる場所が「約 10 分」と出ると、予定が崩れて使えないから。

## 背景（2026-09-25、ステージングの実機確認で判明）

v3.2 では所要時間を「直線距離 ÷ 速度」で出していた。渋谷・新宿で試すと、車の値が実際の半分ほどになる。原因は 2 つ。

1. 直線距離で計算している（実際の道は 1.3 倍前後）
2. 車の速度 500m／分（時速 30km）が、信号・渋滞のある一般道に対して速すぎる

## 詳細

- 移動手段に**電車**と**バス**を加え、5 つにする（徒歩／自転車／車／電車／バス）。半径は 徒歩 1km／自転車 3km／車 10km／電車 15km／バス **8km**（2026-09-26 に 5km から拡大。時間に直すとバスだけ約 25 分と短かったため、約 40 分ぶんに合わせた）。
- **車・電車・バスは Google Routes API の実測**にする。車は渋滞、電車・バスは時刻表（出発時刻は「今」）が反映される。
- **徒歩・自転車は直線距離からの計算**のままにする。徒歩は件数が多く費用がかさむため、自転車は Google が日本で自転車の経路を提供していないため。
  - 徒歩は **60m／分**。不動産広告の「1 分＝80m」は道のりに対する値で、実際の道は直線の約 1.3 倍になる。直線距離のまま使うので 80 ÷ 1.3 ≒ 60 とし、曲がり角・横断歩道の分を織り込む（従来の 80m／分では 3 割ほど短く出ていた）。
  - 自転車は **180m／分**（時速 11km 相当。250m／分から変更）。同じ考え方で道の曲がりと信号待ちを織り込む。
- Routes API が失敗・上限・経路なしのときは直線距離からの目安に切り替える（車 300m／分、電車 400m／分、バス 200m／分）。利用者にエラーは見せない。
- **表示は「〈移動手段〉 約〈N〉分」で統一する**。「徒歩 約 6 分」「自転車 約 12 分」「車 約 12 分」「電車 約 24 分」「バス 約 18 分」。実測か計算かは区別しない。
- 検索結果のスポットカードに出る「徒歩 N 分」も、同じ 60m／分と同じ言い方にそろえる（3.4.2）。
- 費用を抑えるため、現在地を約 100m 単位に丸めて同じ地点・同じ移動手段の結果を 10 分間使い回し、1 回の問い合わせは最大 20 件にする。徒歩・自転車では呼ばない。

## 受入条件

- [ ] 移動手段に電車・バスが増え、選ぶと半径と一覧が変わること
- [ ] 車・電車・バスの所要時間が Routes API の値になり、直線距離の計算よりも実際に近いこと（渋谷で 5km 先の地点で確認）
- [ ] 徒歩が 60m／分、自転車が 180m／分で計算されること（全画面で同じ基準）
- [ ] Routes API を止めた状態でも画面がエラーにならず、目安の時間が出ること
- [ ] 表示が「徒歩 約 6 分」「自転車 約 12 分」「車 約 12 分」のように統一されていること
- [ ] 同じ地点・同じ移動手段で 10 分以内に開き直したとき、Routes API を呼び直さないこと
- [ ] 要件定義書 8 章 79

# F-AD-01 管理者ログイン

> 出典: [requirement.md](../../requirement.md) 3.10.1・7.2

## ユーザーストーリー

管理者として、一般ユーザーと同じ Google ログインで入りつつ、**管理画面に入るときだけ認証アプリの 6 桁を通したい**。なぜなら、Google アカウント 1 つが破られただけで、通報の中身・利用者のメールアドレス・操作の記録に手が届いてしまうから。

## 詳細

### 入場の 3 段階

1. 認証方式の土台は一般ユーザーと同じ Google 認証（F-AC-01）を再利用する。管理者専用のログイン画面は作らない。
2. `/admin` 配下・`/api/admin` 配下は、関所（`src/proxy.ts`）で `users.is_admin` を検証する。false または未ログインなら **404**（管理画面の存在自体を露出させない）。
3. さらに **Supabase Auth の MFA（TOTP）** を通す。ログイン情報（JWT）の `aal` が `aal2` でなければ管理画面に入れない。

### なぜ `aal` で判定するか

`aal` は Supabase の JWT の**必須項目**なので、`getClaims()`（手元での署名検証）だけで読める。Supabase Auth への通信が増えないため、7.1 の「1 画面あたりの往復を減らす」方針を崩さない。

### 二段階確認の画面（SC-32）

- `is_admin` が true で、まだ factor を登録していない管理者には、管理画面の代わりに **SC-32** を出す。QR コードと手入力用の文字列を出し、6 桁を入れて登録を確定させる。
- 登録済みで `aal1` の管理者にも同じ SC-32 を出し、6 桁で `aal2` に上げる。
- SC-32 自体も `is_admin` が true の人にしか出さない。false・未ログインは 404 のまま。
- メニューバーは出さない（利用者向け・管理用のどちらも。要件 4.2）。まだ管理画面に入れていない段階で他の画面への導線を見せる意味がないため。

### 管理セッションの寿命（60 分）

- `aal2` に上げた時刻を持ち、**60 分**を過ぎたら管理画面を開くときに SC-32 で聞き直す。
- **利用者としての 30 日のセッション（3.2.4）は切らない。** ログアウトはさせず、管理画面だけ聞き直す。
- 理由：`aal2` は一度上げるとセッションが切れるまで残るため、これが無いと「30 日間ずっと管理画面が開ける」ことになり、二段階確認がほぼ意味を失う。

### 重い操作の前の再確認（10 分）

取り消せない操作・影響が大きい操作は、**確定の直前**に直近 10 分以内の 6 桁を求める（GitHub の sudo mode と同じ考え方）。対象は次の 4 種類。

| 対象 | 該当節 |
|---|---|
| 投稿・コメントの削除 | 3.10.4 |
| 利用者の停止・解除・仮停止の確定・取り消し | 3.10.9 |
| ストライクの取り消し | 3.10.8 |
| 規約の公開 | 3.10.11 |

閲覧（通報の中身・利用者のメールアドレス・操作の記録）は上の 60 分で守る。

### 認証アプリを失ったとき

画面からは復旧できない。**自分の factor を削除する導線は作らない**（作ると、そこが二段階確認の抜け道になる）。開発者が Supabase の管理 API（service_role）で当該ユーザーの factor を削除し、登録し直す。

つまり **Supabase コンソールとサービスキーを持つ人の守りが、管理画面の守りの上限**になる。要件 7.2 の「外部サービスのアカウント」に、Google・GitHub・Vercel・Supabase の 4 つへ二段階確認を設定することを運用上の必須として書いた。

### 採用しなかった案

**パスキー（WebAuthn）を第 2 要素にする**案は採らない。Supabase Auth のパスキーは 2026-09 時点で experimental であり、かつ「第 2 要素」ではなく**主たる認証手段**として提供されているため、`aal2` の判定に使えない。TOTP には「6 桁を本人に読み上げさせて中継する攻撃を防げない」（パスキーと違い接続先に縛られない）弱点が残るので、上の「重い操作の前の再確認」で被害の範囲を狭める。

### 変えないこと

- `is_admin` の付与は画面からは行わない。Supabase コンソールから開発者が直接設定する（運用手順は要件 3.10.1。9 章 未決定事項 No.4 は 2026-09-29 に決定済みとした）。
- `users.is_admin` カラムは F-AC-01 で定義済みで、本ストーリーで新たなマイグレーションは行わない。**二段階確認の状態は Supabase Auth 側（`auth.mfa_factors`）が持つので、自前のテーブルも増やさない。**
- 管理者ダッシュボード（SC-16、[admin-dashboard.md](admin-dashboard.md)）への着地。二段階確認が未登録・期限切れのときは SC-32 を挟み、通ったら元の行き先へ進める。

## 受入条件

- [ ] `is_admin` が false、または未ログインの状態で `/admin` 配下の URL へアクセスすると 404 が返ること
- [ ] `is_admin` が true のユーザーがログインすると、管理者ダッシュボード（SC-16）に遷移すること
- [ ] 管理者ログインが一般ユーザーと同じ Google 認証フローで完了すること（管理者専用のログイン画面が存在しないこと）
- [ ] `is_admin` が true でも認証アプリを登録していない管理者は管理画面に入れず、SC-32 で QR コードから登録して 6 桁を入れると SC-16 に着地すること（要件 8 章 80）
- [ ] SC-32 を含む `/admin` 配下・`/api/admin` 配下のすべてで、`is_admin` が false と未ログインは 404 になること（要件 8 章 81）
- [ ] 二段階確認から 60 分を過ぎると管理画面で聞き直され、通ると元の行き先に進めること。このとき利用者としてはログアウトされておらず、一般の画面はそのまま使えること（要件 8 章 82）
- [ ] 削除／停止・解除・仮停止の確定・取り消し／ストライクの取り消し／規約の公開を確定するとき、直近 10 分以内に 6 桁を入れていなければ確定前に聞き直され、間違った 6 桁では操作が実行されないこと（要件 8 章 83）
- [ ] 認証アプリを失った管理者を Supabase の管理 API から復旧できること。画面からは自分の factor を削除できないこと（要件 8 章 84）
